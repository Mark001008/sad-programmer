## 一、Spring Framework：IoC 容器

### 1.1 为什么需要 IoC

传统开发中，对象的创建和依赖关系由程序员手动管理：

```java
// 没有 IoC 的世界
public class OrderService {
    private final OrderRepository repository = new OrderRepository(); // 自己 new
    private final PaymentService paymentService = new PaymentService(); // 自己 new
}
```

问题：
- **强耦合**：OrderService 直接依赖具体实现，换实现必须改代码
- **难测试**：无法在测试中替换为 Mock 对象
- **生命周期不可控**：对象何时创建、何时销毁、是否单例，全由代码写死

IoC（控制反转）的核心思想：**把对象的创建和管理交给容器，程序员只声明依赖关系。**

```java
// IoC 的世界
@Service
public class OrderService {
    private final OrderRepository repository;
    private final PaymentService paymentService;

    @Autowired // 容器自动注入
    public OrderService(OrderRepository repository, PaymentService paymentService) {
        this.repository = repository;
        this.paymentService = paymentService;
    }
}
```

**控制反转的含义**：对象的控制权从程序员反转到了容器。程序员从"我来创建对象"变成"我来描述依赖，容器帮我创建"。

### 1.2 BeanFactory 与 ApplicationContext

Spring IoC 容器有两个核心接口：

```
BeanFactory（最基础的容器接口）
    ├── getBean()           // 获取 Bean
    ├── containsBean()      // 是否包含 Bean
    └── isSingleton()       // 是否单例

ApplicationContext（扩展了 BeanFactory）
    ├── 继承 BeanFactory 所有能力
    ├── 国际化（MessageSource）
    ├── 事件发布（ApplicationEventPublisher）
    ├── 资源加载（ResourcePatternResolver）
    └── 环境抽象（Environment）
```

**为什么不直接用 BeanFactory？**

BeanFactory 是懒加载——只有 getBean() 时才创建对象。ApplicationContext 默认启动时就创建所有单例 Bean，好处是：
- 启动时就能发现配置错误，而不是运行时才发现
- 支持事件机制、AOP 等高级特性

**生产中的选择**：ApplicationContext。Spring Boot 中的 `AnnotationConfigServletWebServerApplicationContext` 就是它的实现。

### 1.3 Bean 的生命周期

一个 Bean 从创建到销毁的完整过程：

```
1. 实例化（Instantiation）
   容器通过构造函数创建对象（此时属性都是默认值）

2. 属性赋值（Populate Properties）
   容器注入依赖的其他 Bean、@Value 值等

3. Aware 回调
   如果 Bean 实现了 BeanNameAware、BeanFactoryAware 等接口，
   容器会回调相应方法，让 Bean 感知自己在容器中的信息

4. BeanPostProcessor#postProcessBeforeInitialization
   容器级别的钩子，所有 Bean 初始化前都会执行

5. 初始化（Initialization）
   ├── @PostConstruct 注解方法
   ├── InitializingBean#afterPropertiesSet()
   └── 自定义 init-method

6. BeanPostProcessor#postProcessAfterInitialization
   容器级别的钩子，AOP 代理就在这一步生成

7. Bean 就绪，可以使用

8. 销毁（Destroy）
   ├── @PreDestroy 注解方法
   ├── DisposableBean#destroy()
   └── 自定义 destroy-method
```

**为什么 BeanPostProcessor 这么重要？**

Spring 的很多核心功能都是通过 BeanPostProcessor 实现的：
- **AOP 代理**：`AbstractAutoProxyCreator` 在 `postProcessAfterInitialization` 中创建代理
- **@Autowired**：`AutowiredAnnotationBeanPostProcessor` 在属性赋值阶段处理
- **@Transactional**：`InfrastructureAdvisorAutoProxyCreator` 创建事务代理

理解了 BeanPostProcessor，就理解了 Spring 的扩展机制。

### 1.4 循环依赖与三级缓存

**什么是循环依赖？**

```java
@Service
public class A {
    @Autowired private B b;
}

@Service
public class B {
    @Autowired private A a;
}
```

A 依赖 B，B 又依赖 A，形成环。

**Spring 如何解决？三级缓存：**

```java
// DefaultSingletonBeanRegistry 中的三级缓存
/** 一级缓存：存放完整的 Bean（已实例化、已属性赋值、已初始化） */
Map<String, Object> singletonObjects = new ConcurrentHashMap<>();

/** 二级缓存：存放早期暴露的 Bean（已实例化，未属性赋值） */
Map<String, Object> earlySingletonObjects = new ConcurrentHashMap<>();

/** 三级缓存：存放 Bean 的 ObjectFactory（延迟生成早期引用） */
Map<String, ObjectFactory<?>> singletonFactories = new ConcurrentHashMap<>();
```

**解决流程（A 创建过程中发现依赖 B）：**

```
1. 创建 A → 实例化 A → 将 A 的 ObjectFactory 放入三级缓存
2. 填充属性 → 发现依赖 B → 去创建 B
3. 创建 B → 实例化 B → 将 B 的 ObjectFactory 放入三级缓存
4. 填充属性 → 发现依赖 A → 先查一级缓存（没有）→ 查二级缓存（没有）
   → 查三级缓存（找到 A 的 ObjectFactory）→ 调用 getObject() 获取早期引用
   → 将早期引用放入二级缓存，删除三级缓存
5. B 创建完成 → 放入一级缓存
6. A 获得 B 的引用 → A 创建完成 → 放入一级缓存
```

**三级缓存解决不了的情况：**
- 构造器注入的循环依赖（因为实例化阶段就需要依赖，无法提前暴露引用）
- @Async 方法的循环依赖（因为 @Async 是在 BeanPostProcessor 阶段生成代理，此时 Bean 已经放入一级缓存）

**实际生产建议**：循环依赖说明设计有问题。优先通过重构（提取公共逻辑、引入事件机制）消除循环依赖，而不是依赖三级缓存。

### 1.5 Spring 中的设计模式

| 设计模式 | Spring 中的体现 | 核心思想 |
|----------|-----------------|----------|
| **工厂模式** | BeanFactory、FactoryBean | 封装对象创建过程 |
| **单例模式** | Bean 默认 scope=singleton | 一个 Bean 定义只有一个实例 |
| **代理模式** | AOP（JDK 动态代理 / CGLIB） | 不修改原代码增强功能 |
| **模板方法** | JdbcTemplate、RestTemplate | 定义算法骨架，子类实现具体步骤 |
| **观察者模式** | ApplicationEvent + ApplicationListener | 事件发布与监听，解耦 |
| **适配器模式** | HandlerAdapter | 将不同类型的 Handler 统一调用 |
| **策略模式** | Resource 接口多种实现 | 不同资源加载策略 |
| **装饰器模式** | BeanWrapper | 增强对象功能 |

## 二、Spring AOP：面向切面编程

### 2.1 AOP 解决什么问题

很多逻辑是横切多个业务模块的：
- 日志记录：每个方法调用都要记录入参、出参、耗时
- 事务管理：每个数据库操作都要开启/提交/回滚事务
- 权限校验：每个接口都要检查用户是否有权限
- 性能监控：每个方法都要统计执行时间

如果没有 AOP，这些逻辑会散落在每个业务方法中，导致：
- 代码重复
- 业务逻辑与非业务逻辑混杂
- 修改一处要改几十个地方

**AOP 的核心思想**：把横切关注点从业务代码中抽离出来，以"切面"的形式统一管理。

### 2.2 核心概念

| 概念 | 含义 | 示例 |
|------|------|------|
| **切面（Aspect）** | 横切关注点的模块化 | 日志切面、事务切面 |
| **连接点（JoinPoint）** | 程序执行的某个点 | 方法调用、异常抛出 |
| **切入点（Pointcut）** | 匹配连接点的表达式 | `execution(* com.sad..*Service.*(..))` |
| **通知（Advice）** | 在切入点执行的动作 | @Before、@After、@Around |
| **织入（Weaving）** | 将切面应用到目标对象的过程 | 编译时/类加载时/运行时 |

### 2.3 JDK 动态代理 vs CGLIB

Spring AOP 的两种代理方式：

**JDK 动态代理**：
- 基于接口：目标类必须实现接口
- 原理：`java.lang.reflect.Proxy` 在运行时生成接口的实现类
- 性能：方法调用通过反射，有一定开销

**CGLIB 代理**：
- 基于继承：目标类不需要实现接口
- 原理：`ASM` 字节码框架在运行时生成目标类的子类
- 性能：方法调用通过 FastClass 索引，比反射快
- 限制：不能代理 final 类和 final 方法

**Spring 的选择策略**：
- 如果目标类实现了接口 → 默认使用 JDK 动态代理
- 如果目标类没有实现接口 → 使用 CGLIB
- Spring Boot 2.x 默认使用 CGLIB（`spring.aop.proxy-target-class=true`）

**为什么 Spring Boot 默认用 CGLIB？**

JDK 动态代理要求注入时用接口类型，如果用具体类注入会报 `ClassCastException`。CGLIB 代理的对象可以直接用具体类接收，对使用者更友好。

### 2.4 @Transactional 的工作原理

```java
@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    accountRepository.debit(fromId, amount);
    accountRepository.credit(toId, amount);
}
```

**背后发生了什么？**

```
1. Spring 启动时，扫描到 @Transactional 注解
2. InfrastructureAdvisorAutoProxyCreator（BeanPostProcessor）
   为该 Bean 创建代理对象
3. 调用 transfer() 时，实际执行的是代理对象的方法
4. 代理拦截器 TransactionInterceptor 执行：
   ├── 获取数据库连接
   ├── 设置 connection.setAutoCommit(false)
   ├── 执行业务方法（debit + credit）
   ├── 如果正常 → connection.commit()
   └── 如果异常 → connection.rollback()
```

**@Transactional 失效的常见场景：**

| 场景 | 原因 | 解决 |
|------|------|------|
| 方法不是 public | Spring AOP 默认只代理 public 方法 | 改为 public 或用 AspectJ |
| 同类方法调用 | this.method() 绕过了代理 | 注入自身或用 AopContext |
| 异常被 catch 吞掉 | 事务管理器感知不到异常 | 不要吞异常或手动 setRollbackOnly |
| 抛出 checked 异常 | 默认只回滚 RuntimeException | @Transactional(rollbackFor=Exception.class) |
| 数据库引擎不支持 | MyISAM 不支持事务 | 用 InnoDB |

### 2.5 事务传播行为

当一个 @Transactional 方法调用另一个 @Transactional 方法时，事务怎么处理？

| 传播行为 | 含义 | 使用场景 |
|----------|------|----------|
| **REQUIRED**（默认） | 如果当前有事务，加入；没有，创建新事务 | 大多数业务方法 |
| **REQUIRES_NEW** | 总是创建新事务，挂起当前事务 | 日志记录（即使业务回滚，日志也要保留） |
| **NESTED** | 如果当前有事务，创建嵌套事务（savepoint） | 部分失败不影响整体 |
| **SUPPORTS** | 如果当前有事务，加入；没有，非事务执行 | 查询方法 |
| **NOT_SUPPORTED** | 非事务执行，挂起当前事务 | 不需要事务的操作 |
| **MANDATORY** | 必须在事务中调用，否则抛异常 | 强制要求事务上下文 |
| **NEVER** | 必须在非事务中调用，否则抛异常 | 不允许事务 |

**REQUIRED vs NESTED 的区别：**

```java
@Transactional
public void outer() {
    try {
        inner(); // REQUIRED: inner 的异常会导致 outer 也回滚
                 // NESTED: inner 的异常只回滚 inner，outer 可以 catch 住继续执行
    } catch (Exception e) {
        // REQUIRED: 这里 catch 住也没用，事务已经被标记为 rollback-only
        // NESTED: 这里 catch 住，outer 事务可以继续提交
    }
}

@Transactional(propagation = Propagation.REQUIRED) // 或 NESTED
public void inner() {
    // 业务逻辑
    throw new RuntimeException("error");
}
```

## 三、Spring Boot：自动配置

### 3.1 Spring Boot 解决什么问题

传统 Spring 项目的问题：
- 大量 XML 配置（spring-context.xml、spring-mvc.xml、web.xml...）
- 依赖版本冲突（Spring 5.3.2 + MyBatis 3.5.7 + Jackson 2.12.3 能不能一起用？）
- 部署复杂（打 war 包，部署到 Tomcat）

Spring Boot 的核心价值：**约定优于配置，起步即运行。**

### 3.2 @SpringBootApplication 的本质

```java
@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

`@SpringBootApplication` 是一个组合注解：

```java
@SpringBootConfiguration  // 标记为配置类（本质是 @Configuration）
@EnableAutoConfiguration  // 开启自动配置
@ComponentScan            // 扫描当前包及子包的组件
public @interface SpringBootApplication {}
```

**自动配置的核心：@EnableAutoConfiguration**

```java
@Import(AutoConfigurationImportSelector.class)
public @interface EnableAutoConfiguration {}
```

`AutoConfigurationImportSelector` 会读取 `META-INF/spring.factories`（Spring Boot 2.x）或 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`（Spring Boot 3.x）中的配置类列表，根据条件注解决定是否加载。

### 3.3 自动配置的条件注解

| 注解 | 含义 | 示例 |
|------|------|------|
| @ConditionalOnClass | classpath 中存在指定类 | 有 MyBatis 类才配置 MyBatis |
| @ConditionalOnMissingBean | 容器中没有指定 Bean | 用户没自定义才用默认的 |
| @ConditionalOnProperty | 配置文件中有指定属性 | `spring.datasource.url` 存在才配置数据源 |
| @ConditionalOnWebApplication | 当前是 Web 应用 | 只在 Web 环境下配置 DispatcherServlet |

**以 DataSourceAutoConfiguration 为例：**

```java
@ConditionalOnClass({DataSource.class, EmbeddedDatabaseType.class})
@ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory")
@EnableConfigurationProperties(DataSourceProperties.class)
@Import({DataSourcePoolMetadataProvidersConfiguration.class,
         DataSourceInitializationConfiguration.class})
public class DataSourceAutoConfiguration {

    @Conditional(PooledDataSourceCondition.class)
    @ConditionalOnMissingBean({DataSource.class, XADataSource.class})
    protected static class PooledDataSourceConfiguration {
        // 自动配置 HikariCP 连接池
    }
}
```

意思是：如果 classpath 有 DataSource 类，且用户没有自己定义 DataSource Bean，就自动配置连接池。

### 3.4 SPI 机制与 spring.factories

**Java SPI（Service Provider Interface）：**

```
1. 定义接口：public interface Logger { void log(String msg); }
2. 实现类：public class FileLogger implements Logger { ... }
3. 注册：META-INF/services/com.example.Logger 文件内容为 com.example.FileLogger
4. 使用：ServiceLoader<Logger> loaders = ServiceLoader.load(Logger.class);
```

**Spring Boot 的 SPI：**

Spring Boot 没有用 Java 原生 SPI，而是用自己的 `spring.factories`：

```properties
# META-INF/spring.factories
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
  org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration,\
  org.springframework.boot.autoconfigure.orm.jpa.HibernateJpaAutoConfiguration,\
  org.springframework.boot.autoconfigure.web.servlet.WebMvcAutoConfiguration
```

**为什么不用 Java 原生 SPI？**
- Java SPI 会一次加载所有实现类，无法按条件过滤
- Spring 的 spring.factories 配合 @Conditional 注解，可以按需加载

### 3.5 Starter 的本质

Starter 就是一个 Maven 依赖包，包含：
1. 该框架需要的所有依赖（版本已经帮你选好，不会冲突）
2. 自动配置类（通过 spring.factories 注册）
3. 默认配置值（通过 @ConfigurationProperties 绑定）

例如 `spring-boot-starter-web` 包含：
- Spring MVC（spring-webmvc）
- Tomcat（内嵌容器）
- Jackson（JSON 序列化）
- 自动配置：WebMvcAutoConfiguration（配置 DispatcherServlet、消息转换器等）

**自定义 Starter 的步骤：**

```
1. 创建 autoconfigure 模块：
   - 编写配置类（@Configuration + @Conditional）
   - 编写属性类（@ConfigurationProperties）
   - 注册到 META-INF/spring.factories

2. 创建 starter 模块：
   - 依赖 autoconfigure 模块
   - 依赖框架本身的 jar 包

3. 使用方只需要引入 starter 依赖，零配置即可使用
```

## 四、Spring MVC：Web 请求处理

### 4.1 请求处理流程

```
客户端请求
    ↓
DispatcherServlet（前端控制器，所有请求入口）
    ↓
HandlerMapping（根据 URL 找到对应的 Controller 方法）
    ↓
HandlerAdapter（适配不同类型的 Handler：@RequestMapping、函数式等）
    ↓
拦截器 preHandle（按注册顺序执行）
    ↓
Controller 方法执行
    ↓
返回 ModelAndView / @ResponseBody
    ↓
拦截器 postHandle（按注册顺序反向执行）
    ↓
视图解析 + 渲染（或 HttpMessageConverter 序列化 JSON）
    ↓
拦截器 afterCompletion（按注册顺序反向执行）
    ↓
响应客户端
```

### 4.2 HandlerMapping 与 HandlerAdapter

**为什么不直接调用 Controller 方法？**

因为 Controller 的写法多种多样：
- `@RequestMapping` 注解方式
- 实现 `Controller` 接口方式
- 函数式端点（RouterFunction）

DispatcherServlet 不可能为每种写法都写一套调用逻辑。所以：
- HandlerMapping 负责"找到"处理器（URL → 方法的映射）
- HandlerAdapter 负责"调用"处理器（统一的调用接口）

**设计模式**：策略模式。DispatcherServlet 持有多个 HandlerMapping 和 HandlerAdapter，按优先级尝试。

### 4.3 HttpMessageConverter

当方法标注了 `@ResponseBody` 时，返回值不会走视图解析，而是通过 HttpMessageConverter 序列化为响应体。

```java
@GetMapping("/api/order/{id}")
@ResponseBody
public Order getOrder(@PathVariable Long id) {
    return orderService.findById(id);
    // 返回 Order 对象 → HttpMessageConverter → JSON 字符串 → 响应体
}
```

**常见实现：**

| Converter | 处理的媒体类型 | 序列化框架 |
|-----------|---------------|-----------|
| MappingJackson2HttpMessageConverter | application/json | Jackson |
| StringHttpMessageConverter | text/plain | String |
| ByteArrayHttpMessageConverter | application/octet-stream | byte[] |

### 4.4 异常处理机制

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    /**
     * 业务异常 → 400
     */
    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ErrorResponse> handleBusiness(BusinessException e) {
        return ResponseEntity.badRequest()
            .body(new ErrorResponse(e.getCode(), e.getMessage()));
    }

    /**
     * 参数校验异常 → 400
     */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException e) {
        String message = e.getBindingResult().getFieldErrors().stream()
            .map(f -> f.getField() + ": " + f.getDefaultMessage())
            .collect(Collectors.joining("; "));
        return ResponseEntity.badRequest()
            .body(new ErrorResponse("VALIDATION_ERROR", message));
    }

    /**
     * 未知异常 → 500
     */
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleUnknown(Exception e) {
        log.error("未知异常", e);
        return ResponseEntity.status(500)
            .body(new ErrorResponse("INTERNAL_ERROR", "系统内部错误"));
    }
}
```

**异常处理的优先级**：
1. Controller 方法内的 try-catch
2. @ExceptionHandler（当前 Controller 内的）
3. @ControllerAdvice 中的 @ExceptionHandler（全局）
4. ErrorController（兜底，处理 /error 路径）

## 五、Dubbo：RPC 框架

### 5.1 RPC 解决什么问题

在单体应用中，方法调用是本地的：

```java
// 单体应用：本地调用
OrderService orderService = new OrderService();
orderService.createOrder(request); // 直接调用
```

在微服务架构中，服务部署在不同的进程/机器上，方法调用需要跨网络：

```java
// 微服务架构：远程调用
// OrderService 部署在 192.168.1.10:20880
// PaymentService 部署在 192.168.1.11:20880
// OrderService 需要调用 PaymentService，但不在同一个进程
```

**RPC（Remote Procedure Call）的核心目标**：让远程调用看起来像本地调用。

### 5.2 Dubbo 的架构

```
Provider（服务提供方）
    ↓ 注册服务地址
Registry（注册中心：Zookeeper / Nacos）
    ↓ 订阅服务地址
Consumer（服务消费方）
    ↓ 直接调用（不经过 Registry）
Provider

Monitor（监控中心：统计调用次数、耗时）
```

**调用流程：**

```
1. Provider 启动，向 Registry 注册服务地址
2. Consumer 启动，向 Registry 订阅服务地址
3. Registry 返回 Provider 地址列表给 Consumer
4. Consumer 根据负载均衡策略选择一个 Provider 直接调用
5. Provider 或 Consumer 向 Monitor 上报调用数据
```

**关键点**：注册中心只负责地址注册和发现，不参与实际调用。Consumer 和 Provider 之间是直连的。

### 5.3 Dubbo 协议

Dubbo 默认使用自定义的 dubbo 协议：

```
 0     1     2     3     4     5     6     7     8
+-----+-----+-----+-----+-----+-----+-----+-----+
| magic high    | magic low     | serialization   |
+-----+-----+-----+-----+-----+-----+-----+-----+
| status        | request id (8 bytes)             |
+-----+-----+-----+-----+-----+-----+-----+-----+
| data length (4 bytes)                             |
+-----+-----+-----+-----+-----+-----+-----+-----+
| data ...                                          |
+-----+-----+-----+-----+-----+-----+-----+-----+
```

- **魔数**（2字节）：0xdabb，用于快速识别是否是 Dubbo 协议
- **序列化方式**（1字节）：Hessian2 / Kryo / Protobuf 等
- **请求 ID**（8字节）：用于匹配请求和响应
- **数据长度**（4字节）：请求体长度

**为什么不用 HTTP？**
- Dubbo 协议更紧凑，少了 HTTP 头部开销
- 二进制序列化比 JSON 更高效
- 支持长连接复用，减少握手开销

### 5.4 负载均衡

Consumer 有多个 Provider 可选时，如何选择？

| 策略 | 算法 | 适用场景 |
|------|------|----------|
| **Random**（默认） | 加权随机 | 通用场景 |
| **RoundRobin** | 加权轮询 | 机器配置均匀 |
| **LeastActive** | 最少活跃调用数 | 避免慢机器堆积请求 |
| **ConsistentHash** | 一致性哈希 | 需要会话亲和性 |

**LeastActive 的核心思想：**

```
Provider A 当前正在处理 5 个请求
Provider B 当前正在处理 2 个请求
Provider C 当前正在处理 8 个请求

新请求到来 → 选择 Provider B（活跃数最少）
```

这比 RoundRobin 更智能：如果某台机器处理慢，它的活跃数会升高，新请求就会自动避开它。

### 5.5 集群容错

调用 Provider 失败时，如何处理？

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| **Failover**（默认） | 失败自动重试其他节点 | 读操作（幂等） |
| **Failfast** | 快速失败，不重试 | 写操作（非幂等） |
| **Failsafe** | 失败安全，忽略异常 | 日志、审计等不关键操作 |
| **Failback** | 失败自动恢复，定时重试 | 消息推送等异步操作 |
| **Forking** | 并行调用多个节点，一个成功即返回 | 实时性要求高的场景 |

**Failover vs Failfast 的选择依据：**

```java
// 读操作 → Failover（允许重试）
@DubboReference(cluster = "failover", retries = 2)
private AccountQueryService accountQueryService;

// 写操作 → Failfast（不允许重试，避免重复扣款）
@DubboReference(cluster = "failfast", retries = 0)
private AccountTransferService accountTransferService;
```

### 5.6 Dubbo 与 Spring Boot 的集成

```java
// 服务提供方
@DubboService(version = "1.0.0", group = "payment")
public class PaymentServiceImpl implements PaymentService {
    @Override
    public PayResult pay(PayRequest request) {
        // 支付逻辑
    }
}

// 服务消费方
@RestController
public class OrderController {
    @DubboReference(version = "1.0.0", group = "payment")
    private PaymentService paymentService;

    @PostMapping("/order/create")
    public OrderResult createOrder(@RequestBody OrderRequest request) {
        // 像调用本地方法一样调用远程服务
        PayResult payResult = paymentService.pay(request.toPayRequest());
        return new OrderResult(payResult);
    }
}
```

**version 和 group 的作用：**
- **group**：服务分组。同一接口有多种实现时用 group 区分（如"国内支付"和"国际支付"）
- **version**：版本号。灰度发布时，新旧版本可以同时注册，Consumer 指定调用哪个版本

## 六、MyBatis：ORM 框架

### 6.1 MyBatis 解决什么问题

直接用 JDBC 操作数据库的痛点：

```java
// 原生 JDBC
Connection conn = dataSource.getConnection();
PreparedStatement ps = conn.prepareStatement(
    "SELECT id, name, amount FROM orders WHERE user_id = ?");
ps.setLong(1, userId);
ResultSet rs = ps.executeQuery();
List<Order> orders = new ArrayList<>();
while (rs.next()) {
    Order order = new Order();
    order.setId(rs.getLong("id"));
    order.setName(rs.getString("name"));
    order.setAmount(rs.getBigDecimal("amount"));
    orders.add(order);
}
rs.close();
ps.close();
conn.close();
```

问题：
- 手动设置参数（ps.setLong、ps.setString），容易出错
- 手动映射结果集（rs.getLong → order.setId），大量重复代码
- 资源管理（close）容易遗漏
- SQL 与代码混杂，不易维护

**MyBatis 的核心价值**：SQL 与代码分离，自动完成参数设置和结果映射。

### 6.2 核心组件

```
SqlSessionFactory（全局单例）
    └── SqlSession（一次数据库会话，非线程安全）
            └── Executor（SQL 执行器）
                    └── StatementHandler（JDBC Statement 处理）
                            └── ParameterHandler（参数设置）
                            └── ResultSetHandler（结果映射）

Configuration（全局配置，包含所有 MappedStatement、TypeHandler 等）
```

**SqlSession 的线程安全问题：**

SqlSession 不是线程安全的，因为它持有一个 Connection。多线程共享 SqlSession 会导致：
- 事务混乱（一个线程 commit 影响另一个线程）
- 数据错乱（多个线程共用同一个 ResultSet）

**最佳实践**：每次数据库操作都获取新的 SqlSession，用完立即关闭。Spring 集成 MyBatis 后，SqlSession 的生命周期由 Spring 管理（通过 SqlSessionTemplate）。

### 6.3 Mapper 代理机制

```java
public interface OrderMapper {
    Order selectById(Long id);
}
```

MyBatis 为 Mapper 接口生成代理对象，调用 `selectById(1L)` 时：

```
1. MapperProxy.invoke() 被调用
2. 从 Configuration 中找到对应的 MappedStatement（包含 SQL 和映射规则）
3. 创建 SqlSession（或从 Spring 事务中获取）
4. 委托 Executor 执行 SQL
5. 返回结果
```

**MapperProxy 的实现：**

```java
public class MapperProxy<T> implements InvocationHandler {
    private final SqlSession sqlSession;
    private final Class<T> mapperInterface;

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) {
        // 如果是 Object 方法（toString、hashCode），直接调用
        if (Object.class.equals(method.getDeclaringClass())) {
            return method.invoke(this, args);
        }
        // 从缓存中获取 MapperMethod，执行
        MapperMethod mapperMethod = new MapperMethod(mapperInterface, method, sqlSession.getConfiguration());
        return mapperMethod.execute(sqlSession, args);
    }
}
```

### 6.4 一级缓存与二级缓存

**一级缓存（SqlSession 级别）：**

```java
SqlSession session = sqlSessionFactory.openSession();
OrderMapper mapper = session.getMapper(OrderMapper.class);

Order order1 = mapper.selectById(1L); // 查询数据库
Order order2 = mapper.selectById(1L); // 从一级缓存获取，不查数据库

session.close();
```

一级缓存默认开启，同一个 SqlSession 中，相同查询直接返回缓存结果。

**一级缓存失效的场景：**
- 执行了 insert/update/delete
- 调用了 clearCache()
- SqlSession 不同

**二级缓存（Mapper 级别）：**

```xml
<!-- OrderMapper.xml -->
<cache eviction="LRU" flushInterval="60000" size="1024" readOnly="true"/>
```

二级缓存在 SqlSession 关闭或提交后，缓存数据会从一级缓存转移到二级缓存。同一个 Mapper 的不同 SqlSession 可以共享二级缓存。

**二级缓存的问题：**
- **脏读**：如果多个 Mapper 操作同一张表，一个 Mapper 的缓存更新了，另一个 Mapper 的缓存还是旧数据
- **分布式环境失效**：二级缓存是进程内的，多实例部署时缓存不一致

**生产建议**：关闭二级缓存（默认就是关闭的），用 Redis 做分布式缓存。

### 6.5 动态 SQL

MyBatis 的动态 SQL 通过 XML 标签实现条件拼接：

```xml
<select id="selectOrders" resultType="Order">
    SELECT * FROM orders
    <where>
        <if test="userId != null">
            AND user_id = #{userId}
        </if>
        <if test="status != null">
            AND status = #{status}
        </if>
        <if test="minAmount != null">
            AND amount >= #{minAmount}
        </if>
        <if test="maxAmount != null">
            AND amount <= #{maxAmount}
        </if>
    </where>
    <choose>
        <when test="orderBy == 'amount'">
            ORDER BY amount DESC
        </when>
        <when test="orderBy == 'createTime'">
            ORDER BY create_time DESC
        </when>
        <otherwise>
            ORDER BY id DESC
        </otherwise>
    </choose>
    <if test="pageSize != null">
        LIMIT #{offset}, #{pageSize}
    </if>
</select>
```

**核心标签：**

| 标签 | 作用 | 说明 |
|------|------|------|
| `<if>` | 条件判断 | test 属性为 OGNL 表达式 |
| `<choose>/<when>/<otherwise>` | 多条件选择 | 类似 switch-case |
| `<where>` | 自动处理 WHERE AND/OR | 去掉多余的 AND |
| `<set>` | 自动处理 SET 逗号 | 去掉多余的逗号 |
| `<foreach>` | 遍历集合 | IN 查询、批量插入 |
| `<trim>` | 自定义前缀/后缀 | 更灵活的 SQL 拼接 |

### 6.6 MyBatis 插件机制

MyBatis 允许在四大对象的执行链路上插入自定义逻辑：

| 可拦截对象 | 拦截方法 | 典型应用 |
|-----------|----------|----------|
| **Executor** | update / query / commit | 分页插件、缓存插件 |
| **StatementHandler** | prepare / parameterize | SQL 改写（分页 SQL） |
| **ParameterHandler** | setParameters | 参数加密 |
| **ResultSetHandler** | handleResultSets | 结果集脱敏 |

**分页插件的原理：**

```java
@Intercepts({
    @Signature(type = StatementHandler.class, method = "prepare", args = {Connection.class, Integer.class})
})
public class PageInterceptor implements Interceptor {

    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        StatementHandler handler = (StatementHandler) invocation.getTarget();
        MetaObject metaObject = SystemMetaObject.forObject(handler);

        // 检查是否有分页参数
        Page page = PageHelper.getLocalPage();
        if (page != null) {
            // 获取原始 SQL
            String originalSql = (String) metaObject.getValue("delegate.boundSql.sql");
            // 改写为分页 SQL
            String pageSql = originalSql + " LIMIT " + page.getOffset() + ", " + page.getPageSize();
            metaObject.setValue("delegate.boundSql.sql", pageSql);
        }

        return invocation.proceed();
    }
}
```

以电信财务公司一笔跨行支付为例，展示三个框架如何协作：

```

   业务方法正常返回 → Spring AOP 代理提交事务
   → connection.commit()
```

## 八、生产实战问题

### 8.1 Spring Bean 的线程安全

**问题**：Spring Bean 默认是单例的，如果 Bean 有可变状态，多线程并发修改会导致数据错乱。

```java
@Service
public class OrderService {
    private int count = 0; // 可变状态！多线程不安全

    public void process() {
        count++; // 竞态条件
    }
}
```

**解决方案**：
1. **无状态设计**：不要在 Bean 中定义可变成员变量
2. **ThreadLocal**：每个线程独立的状态副本
3. **@Scope("prototype")**：每次注入都创建新实例（不推荐，破坏单例优势）
4. **并发工具**：AtomicInteger、ConcurrentHashMap 等

### 8.2 Dubbo 超时与重试的陷阱

```java
// 服务提供方
@DubboService(timeout = 3000) // 3 秒超时
public class PaymentServiceImpl implements PaymentService {
    public PayResult pay(PayRequest request) {
        // 调用银行接口，可能耗时 5 秒
    }
}

// 服务消费方
@DubboReference(timeout = 5000, retries = 2) // 5 秒超时，重试 2 次
private PaymentService paymentService;
```

**陷阱**：Provider 设置了 3 秒超时，Consumer 设置了 5 秒超时。Dubbo 的规则是：**谁是消费者谁说了算**。所以实际超时是 5 秒。

**更大的陷阱**：重试 + 非幂等操作。

```
Consumer 发起支付请求 → Provider 处理中（银行扣款成功，但响应超时）
→ Consumer 认为失败，重试 → Provider 再次处理 → 银行再次扣款
→ 用户被扣了两次钱！
```

**解决方案**：
- 非幂等操作设置 `retries = 0`
- 服务端做幂等校验（根据订单号去重）
- 使用分布式事务保证一致性

### 8.3 MyBatis 批量操作的性能

```java
// 错误做法：逐条插入
for (Order order : orders) {
    orderMapper.insert(order); // 每次都执行一次 SQL，1000 条 = 1000 次网络往返
}

// 正确做法：批量插入
orderMapper.batchInsert(orders); // 一次 SQL 插入多条
```

```xml
<!-- 批量插入 SQL -->
<insert id="batchInsert" parameterType="list">
    INSERT INTO orders (user_id, amount, status) VALUES
    <foreach collection="list" item="order" separator=",">
        (#{order.userId}, #{order.amount}, #{order.status})
    </foreach>
</insert>
```

**注意**：MySQL 的 `max_allowed_packet` 限制了单条 SQL 的大小，批量插入数据量太大时需要分批（每批 500-1000 条）。

## 九、循环依赖与三级缓存

### 9.1 什么是循环依赖

两个或多个 Bean 互相持有对方的引用，形成依赖环：

```java
@Service
public class OrderService {
    @Autowired
    private PaymentService paymentService; // OrderService → PaymentService
}

@Service
public class PaymentService {
    @Autowired
    private OrderService orderService; // PaymentService → OrderService
}
```

创建 OrderService 时需要注入 PaymentService，创建 PaymentService 时又需要注入 OrderService。如果没有任何处理机制，会无限递归直到栈溢出。

### 9.2 三级缓存的设计

Spring 用三级缓存解决单例 Bean 的属性注入循环依赖：

| 缓存 | 名称 | 存储内容 | 作用 |
|------|------|----------|------|
| **一级** | singletonObjects | 完全初始化好的 Bean | 成品仓库 |
| **二级** | earlySingletonObjects | 提前暴露的 Bean（可能是代理对象） | 半成品仓库 |
| **三级** | singletonFactories | ObjectFactory（Lambda，用于创建早期引用） | 工厂仓库 |

**为什么需要三级，两级不行吗？**

关键在于 AOP。如果 Bean 被 AOP 代理，注入的必须是代理对象而不是原始对象。三级缓存的 ObjectFactory 在被调用时才决定是否需要创建代理：

```java
// Spring 源码简化
addSingletonFactory(beanName, () -> getEarlyBeanReference(beanName, mbd, bean));

// getEarlyBeanReference 内部：
// 如果有 SmartInstantiationAwareBeanPostProcessor（AOP 代理就是通过它实现的），
// 会提前创建代理对象并放入二级缓存
```

如果只用两级缓存（直接把早期对象放二级），就无法区分"需要代理"和"不需要代理"的情况。三级缓存把代理的创建延迟到真正需要时，既解决了循环依赖，又保证了 AOP 代理的正确性。

### 9.3 解决流程（属性注入）

以 OrderService ↔ PaymentService 为例：

```
1. 创建 OrderService
   ├── 实例化 OrderService（调用构造函数，此时属性都是 null）
   ├── 将 ObjectFactory 放入三级缓存：singletonFactories["orderService"] = () -> getEarlyBeanReference(...)
   ├── 属性填充：发现需要 PaymentService

2. 创建 PaymentService
   ├── 实例化 PaymentService
   ├── 将 ObjectFactory 放入三级缓存：singletonFactories["paymentService"] = () -> getEarlyBeanReference(...)
   ├── 属性填充：发现需要 OrderService
   ├── 从三级缓存获取 OrderService 的早期引用：
   │   ├── 调用 ObjectFactory.getObject()
   │   ├── 如果 OrderService 需要 AOP 代理，此时创建代理对象
   │   ├── 将结果放入二级缓存：earlySingletonObjects["orderService"] = 代理对象或原始对象
   │   └── 删除三级缓存中的 ObjectFactory
   ├── 注入完成，PaymentService 初始化完成
   ├── 放入一级缓存：singletonObjects["paymentService"] = paymentService
   └── 清除二级、三级缓存

3. 回到 OrderService
   ├── 属性填充完成（拿到的是 PaymentService 的完全初始化对象）
   ├── OrderService 初始化完成
   ├── 放入一级缓存：singletonObjects["orderService"] = orderService
   └── 清除二级、三级缓存
```

### 9.4 解决不了的场景

**构造器注入的循环依赖无法解决：**

```java
@Service
public class OrderService {
    public OrderService(PaymentService paymentService) {
        // 构造时就需要 PaymentService，此时 OrderService 还没实例化完
        // 三级缓存帮不上忙——缓存里根本没有 OrderService 的早期引用
    }
}
```

Spring 会直接抛 `BeanCurrentlyInCreationException`。

**解决方案：**
1. 用字段注入或 Setter 注入代替构造器注入（不推荐，丧失不可变性优势）
2. 用 `@Lazy` 延迟注入：注入的不是真实对象，而是一个代理，首次使用时才解析
3. 重构设计，消除循环依赖（推荐）

```java
// @Lazy 解决方案
@Service
public class OrderService {
    private final PaymentService paymentService;

    public OrderService(@Lazy PaymentService paymentService) {
        this.paymentService = paymentService; // 注入的是代理，首次调用时才解析真实 Bean
    }
}
```

### 9.5 prototype 作用域不支持循环依赖

prototype Bean 每次获取都创建新实例，Spring 不会缓存它。如果两个 prototype Bean 循环依赖，会无限创建：

```
getBean("A") → 创建 A → 需要 B → getBean("B") → 创建 B → 需要 A → getBean("A") → 创建 A → ...
```

Spring 对 prototype 的循环依赖直接抛异常，不做任何处理。

## 十、Spring 事件机制

### 10.1 观察者模式的框架实现

Spring 事件机制是观察者模式的生产级实现。核心角色：

```
事件（ApplicationEvent）     — 观察者模式中的"主题状态变化"
事件发布（ApplicationEventPublisher） — 通知观察者的渠道
事件监听（ApplicationListener）       — 观察者
```

与手写观察者模式相比，Spring 事件机制的优势：
- **解耦彻底**：发布者不需要知道监听者是谁
- **支持异步**：监听者可以在独立线程中处理事件
- **支持事务感知**：事务提交后才触发事件
- **支持顺序控制**：通过 @Order 注解控制监听器执行顺序

### 10.2 自定义事件与监听

```java
// 1. 定义事件
public class OrderCreatedEvent extends ApplicationEvent {
    private final String orderId;
    private final BigDecimal amount;

    public OrderCreatedEvent(Object source, String orderId, BigDecimal amount) {
        super(source);
        this.orderId = orderId;
        this.amount = amount;
    }

    public String getOrderId() { return orderId; }
    public BigDecimal getAmount() { return amount; }
}

// 2. 发布事件
@Service
public class OrderService {
    @Autowired
    private ApplicationEventPublisher eventPublisher;

    @Transactional
    public Order createOrder(CreateOrderRequest request) {
        Order order = Order.from(request);
        orderRepository.save(order);

        // 发布事件：不关心谁在监听
        eventPublisher.publishEvent(new OrderCreatedEvent(this, order.getId(), order.getAmount()));
        return order;
    }
}

// 3. 监听事件
@Component
public class OrderEventListener {

    @EventListener
    public void onOrderCreated(OrderCreatedEvent event) {
        // 扣减库存
        inventoryService.deduct(event.getOrderId());
    }

    @EventListener
    @Order(2) // 执行顺序
    public void sendNotification(OrderCreatedEvent event) {
        // 发送通知
        notificationService.send("订单 " + event.getOrderId() + " 创建成功");
    }
}
```

### 10.3 @TransactionalEventListener

事务事件监听器解决了"事件发布了但事务还没提交，监听者查不到数据"的问题。

```java
@Service
public class OrderService {
    @Autowired
    private ApplicationEventPublisher eventPublisher;

    @Transactional
    public Order createOrder(CreateOrderRequest request) {
        Order order = Order.from(request);
        orderRepository.save(order);
        // 此时 order 刚保存，事务还没提交
        eventPublisher.publishEvent(new OrderCreatedEvent(this, order.getId()));
        return order;
    }
}

@Component
public class InventoryListener {

    // 问题：如果用 @EventListener，此时事务可能还没提交
    // 监听者去查 order 表，可能查不到这条记录

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onOrderCreated(OrderCreatedEvent event) {
        // 事务提交后才执行，此时 order 已经在数据库中
        inventoryService.deduct(event.getOrderId());
    }
}
```

**phase 的四个阶段：**

| 阶段 | 含义 | 使用场景 |
|------|------|----------|
| BEFORE_COMMIT | 事务提交前执行 | 需要在同一事务中处理 |
| AFTER_COMMIT（默认） | 事务提交后执行 | 事务外的异步操作（发消息、通知） |
| AFTER_ROLLBACK | 事务回滚后执行 | 回滚后的补偿操作 |
| AFTER_COMPLETION | 事务完成后执行（不论提交还是回滚） | 清理工作 |

### 10.4 异步事件

默认情况下，事件监听器在发布者线程中同步执行。如果监听逻辑耗时（如发邮件、调用外部接口），会阻塞主流程。

```java
@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean("eventExecutor")
    public Executor eventExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);
        executor.setMaxPoolSize(8);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("event-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.initialize();
        return executor;
    }
}

@Component
public class OrderEventListener {

    @Async("eventExecutor")
    @EventListener
    public void sendNotification(OrderCreatedEvent event) {
        // 在独立线程中执行，不阻塞订单创建主流程
        notificationService.send("订单 " + event.getOrderId() + " 创建成功");
    }
}
```

**异步事件的陷阱：**

| 问题 | 原因 | 解决 |
|------|------|------|
| 监听器拿不到事务上下文 | 异步线程不在原事务中 | 用 @TransactionalEventListener + AFTER_COMMIT |
| 异常被吞掉 | @Async 默认不抛异常 | 配置 AsyncUncaughtExceptionHandler |
| 顺序不保证 | 多线程并发执行 | 异步场景下不要依赖顺序 |
| 主线程已返回，监听器还在执行 | 异步的本质 | 如需等待，用 CompletableFuture 或事件回调 |

### 10.5 生产实践：事件驱动的订单流程

电信财务公司的典型场景——一笔贷款发放后，需要触发多个后续操作：

```
贷款发放成功
    ├── 更新台账（同步，在同一事务中）
    ├── 发送短信通知（异步）
    ├── 生成会计分录（异步）
    ├── 更新监管报表数据（异步）
    └── 触发风控扫描（异步）
```

事件驱动的优势：
- **主流程不阻塞**：贷款发放的核心逻辑（扣款、放款）完成后立即返回
- **新增操作不改主流程**：需要新增"审计日志"，只需加一个监听器
- **失败隔离**：短信发送失败不影响贷款发放的结果

### 11.8 责任链模式 — Filter / Interceptor

请求处理链路中，Filter 和 Interceptor 都是责任链模式：

```

                                                                    ↑
                                                              可以中断链条
```

**Filter vs Interceptor 的区别**：

| 维度 | Filter | Interceptor |
|------|--------|-------------|
| 规范 | Servlet 规范 | Spring 框架 |
| 作用范围 | 所有请求（包括静态资源） | 只有 DispatcherServlet 处理的请求 |
| 能否获取 Spring Bean | 不能（Filter 由 Servlet 容器管理） | 可以（由 Spring 管理） |
| 执行顺序 | 在 Interceptor 之前 | 在 Filter 之后 |
| 典型应用 | 编码设置、CORS、安全过滤 | 权限校验、日志、限流 |

**生产中的责任链实践**：

```java
// 支付网关的责任链
public interface PaymentHandler {
    void handle(PaymentContext context);
    int getOrder(); // 执行顺序
}

@Component
public class ParamValidationHandler implements PaymentHandler {
    public void handle(PaymentContext ctx) { /* 参数校验 */ }
    public int getOrder() { return 1; }
}

@Component
public class RiskCheckHandler implements PaymentHandler {
    public void handle(PaymentContext ctx) { /* 风控检查 */ }
    public int getOrder() { return 2; }
}

@Component
public class DeductBalanceHandler implements PaymentHandler {
    public void handle(PaymentContext ctx) { /* 余额扣减 */ }
    public int getOrder() { return 3; }
}

// 业务代码
@Autowired
private List<PaymentHandler> handlers; // Spring 自动注入所有实现

public PayResult pay(PayRequest request) {
    PaymentContext ctx = new PaymentContext(request);
    handlers.stream()
        .sorted(Comparator.comparingInt(PaymentHandler::getOrder))
        .forEach(h -> h.handle(ctx));
    return ctx.getResult();
}
```

新增一个支付步骤，只需要加一个 `PaymentHandler` 实现类，业务代码零修改。这就是开闭原则的体现。

## 十二、手写数据库连接池

### 12.1 为什么需要连接池

每次数据库操作都创建和销毁连接的代价：

```
TCP 三次握手 → MySQL 认证 → 执行 SQL → 关闭连接 → TCP 四次挥手
```

一次 TCP 握手约 1-3ms，MySQL 认证（含 SSL 握手）约 5-10ms。如果每秒 1000 次查询，仅连接创建就消耗 6-13 秒。

**连接池的本质**：用空间换时间。预先创建一批连接放在池里，用完归还而非销毁。

```
无池：请求 → 创建连接 → SQL → 销毁连接（每次 10ms）
有池：请求 → 借出连接 → SQL → 归还连接（每次 0.1ms）
```

### 12.2 核心数据结构

```java
// 空闲连接队列：线程安全的双端队列
private final ConcurrentLinkedDeque<Connection> idleConnections;

// 总连接计数（空闲 + 借出）
private final AtomicInteger totalCount = new AtomicInteger(0);

// 借出连接计数
private final AtomicInteger activeCount = new AtomicInteger(0);

// 池关闭标志
private final AtomicBoolean closed = new AtomicBoolean(false);
```

**为什么用 ConcurrentLinkedDeque 而不是 BlockingQueue？**

| 数据结构 | 特点 | 适用场景 |
|---------|------|---------|
| `LinkedBlockingQueue` | 有界阻塞，take() 会阻塞 | 简单场景，但无法动态扩池 |
| `ConcurrentLinkedDeque` | 无锁，poll() 立即返回 | 需要自己控制等待逻辑，更灵活 |
| `ArrayBlockingQueue` | 有界数组，固定大小 | 池大小固定的场景 |

HikariCP 用 `ConcurrentLinkedDeque`，Druid 用数组 + ReentrantLock。我们的实现选择与 HikariCP 一致。

### 12.3 借出流程

```
getConnection()
    │
    ├─ 1. idleConnections.poll()  →  取到？验证有效性 → 返回池化连接
    │
    ├─ 2. totalCount < maxActive？ →  创建新连接 → 返回池化连接
    │
    └─ 3. 阻塞等待（Thread.sleep 轮询） →  超时抛异常
```

关键代码：

```java
public Connection getConnection() {
    checkNotClosed();

    // 1. 从空闲队列取连接
    Connection conn = idleConnections.poll();
    if (conn != null) {
        if (isValid(conn)) {
            activeCount.incrementAndGet();
            return wrapConnection(conn);
        }
        // 连接无效，丢弃并递归重试
        totalCount.decrementAndGet();
        closeQuietly(conn);
        return getConnection();
    }

    // 2. 队列为空，尝试创建新连接
    if (totalCount.get() < config.getMaxActive()) {
        conn = createRealConnection();
        if (conn != null) {
            totalCount.incrementAndGet();
            activeCount.incrementAndGet();
            return wrapConnection(conn);
        }
    }

    // 3. 已达上限，阻塞等待
    return waitForConnection();
}
```

**CAS 竞争问题**：多线程同时调用 getConnection() 时，totalCount.get() < maxActive 检查和 totalCount.incrementAndGet() 之间存在竞态条件。生产级实现（如 HikariCP）使用 CAS 循环：

```java
// HikariCP 的做法（简化）
while (true) {
    int current = totalCount.get();
    if (current >= maxActive) {
        return waitForConnection();
    }
    if (totalCount.compareAndSet(current, current + 1)) {
        // CAS 成功，创建连接
        break;
    }
    // CAS 失败，重试
}
```

我们的实现用 AtomicInteger 但没有 CAS 循环，在极高并发下可能超过 maxActive。这是 demo 与生产级的差距。

### 12.4 归还流程

```java
public void returnConnection(Connection conn) {
    if (conn == null) return;

    activeCount.decrementAndGet();

    // 池已关闭，直接销毁
    if (closed.get()) {
        closeQuietly(conn);
        totalCount.decrementAndGet();
        return;
    }

    // 重置连接状态
    try {
        if (!conn.getAutoCommit()) {
            conn.setAutoCommit(true);
        }
    } catch (Exception e) {
        // 连接损坏，丢弃
        closeQuietly(conn);
        totalCount.decrementAndGet();
        return;
    }

    // 归还到空闲队列
    idleConnections.offer(conn);
}
```

**为什么要重置 autoCommit？** 防止上一个使用者开了事务没提交，下一个使用者拿到连接后自动提交了别人的事务。

### 12.5 池化连接代理

连接池的灵魂：**close() 不是关闭连接，而是归还连接。**

```java
public static Connection wrap(final Connection realConnection,
                              final MiniConnectionPool pool) {
    return (Connection) Proxy.newProxyInstance(
        Connection.class.getClassLoader(),
        new Class[]{Connection.class},
        new PooledConnectionHandler(realConnection, pool)
    );
}

// InvocationHandler 核心逻辑
public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
    if ("close".equals(method.getName())) {
        if (!returned) {
            returned = true;
            pool.returnConnection(realConnection);  // 归还，不是关闭
        }
        return null;
    }

    if ("isClosed".equals(method.getName())) {
        return returned;  // 归还后返回 true
    }

    if (returned) {
        throw new RuntimeException("连接已归还，无法调用方法: " + method.getName());
    }

    return method.invoke(realConnection, args);  // 其他方法委托给真实连接
}
```

应用代码可以正常使用 try-with-resources：

```java
try (Connection conn = dataSource.getConnection()) {
    // 使用连接
} // 自动调用 close() → 归还到池
```

### 12.6 连接有效性验证

```java
private boolean isValid(Connection conn) {
    try {
        return conn != null && !conn.isClosed() && conn.isValid(1);
    } catch (Exception e) {
        return false;
    }
}
```

**Connection.isValid(timeout)** 的实现：
- 底层发送 `SELECT 1` 或 MySQL 的 ping 命令
- timeout 参数控制超时秒数，避免长时间阻塞
- 比 `connection.createStatement().execute("SELECT 1")` 更轻量

**验证时机**：
| 策略 | 优点 | 缺点 |
|------|------|------|
| 借出时验证 | 保证拿到的连接一定有效 | 每次借出都有网络开销 |
| 空闲时定期验证 | 借出速度快 | 可能拿到刚过期的连接 |
| 不验证 | 最快 | 可能拿到无效连接，业务报错 |

HikariCP 默认不验证（靠 maxLifetime 控制），Druid 默认借出时验证。

### 12.7 生产级连接池对比

| 特性 | 我们的实现 | HikariCP | Druid |
|------|-----------|----------|-------|
| 队列结构 | ConcurrentLinkedDeque | ConcurrentLinkedDeque | 数组 + ReentrantLock |
| 扩池方式 | AtomicInteger（有竞态） | CAS 循环 | synchronized |
| 等待机制 | Thread.sleep 轮询 | 自定义 ConcurrentBag | Condition.await |
| 连接验证 | isValid() | 不验证（靠 maxLifetime） | validationQuery |
| 泄漏检测 | borrowTime 记录 | 同左 | 同左 |
| 监控 | 无 | JMX Metrics | 内置 StatFilter |
| 连接复用 | FIFO（队首取） | LIFO（队尾取，缓存友好） | FIFO |

**为什么 HikariCP 比 Druid 快？**

1. **字节码优化**：用 Javassist 生成 FastList（避免 ArrayList 的 rangeCheck）
2. **无锁设计**：ConcurrentBag + CAS，避免 synchronized
3. **JIT 友好**：代码路径短，热点方法内联概率高
4. **LIFO 复用**：最后归还的连接最先被借出，缓存命中率高

## 十三、手写 MyBatis

### 13.1 MyBatis 的本质

MyBatis 不是 ORM（它不自动生成 SQL），而是 **SQL Mapping Framework**。核心工作：

```
接口方法调用 → 定位 SQL → 设置参数 → 执行 → 结果映射 → 返回对象
```

与 Hibernate 的对比：

| 维度 | MyBatis | Hibernate |
|------|---------|-----------|
| SQL 控制 | 手写 SQL | 自动生成 HQL/SQL |
| 学习曲线 | 低（会 SQL 就会用） | 高（要学 HQL、Criteria） |
| 灵活性 | 高（复杂 SQL 随便写） | 低（复杂查询要绕） |
| 适用场景 | 互联网公司（SQL 优化是核心） | 传统企业（快速开发） |
| 国内使用率 | 极高（阿里系标配） | 较低 |

### 13.2 注解驱动的 SQL 定义

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface MiniSelect {
    String value();  // SQL 语句
}

// 使用
public interface UserMapper {
    @MiniSelect("SELECT id, name, email FROM users WHERE id = #{id}")
    User selectById(Long id);
}
```

**#{} 与 ${} 的区别**：

```
#{id}  →  PreparedStatement 参数占位符 "?"  →  防 SQL 注入
${id}  →  字符串直接替换  →  有 SQL 注入风险
```

MyBatis 的 #{} 解析过程：

```java
// 原始 SQL
"SELECT * FROM users WHERE id = #{id} AND name = #{name}"

// 解析后
"SELECT * FROM users WHERE id = ? AND name = ?"

// 参数列表
[1, "张三"]
```

### 13.3 Configuration：全局配置中心

```java
public class MiniConfiguration {
    // Mapper 接口 → MappedStatement 映射
    private final Map<String, MiniMappedStatement> mappedStatements = new HashMap<>();

    // 解析 Mapper 接口，注册所有 SQL 方法
    public <T> void addMapper(Class<T> mapperType) {
        for (Method method : mapperType.getMethods()) {
            if (method.isAnnotationPresent(MiniSelect.class)) {
                String sql = method.getAnnotation(MiniSelect.class).value();
                String id = mapperType.getName() + "." + method.getName();

                MiniMappedStatement ms = new MiniMappedStatement();
                ms.setId(id);
                ms.setSql(sql);
                ms.setResultType(method.getReturnType());
                ms.setParameterType(method.getParameterTypes());

                mappedStatements.put(id, ms);
            }
            // 同理处理 @MiniInsert、@MiniUpdate、@MiniDelete
        }
    }
}
```

**MappedStatement 的结构**：

```java
public class MiniMappedStatement {
    private String id;                    // 全限定方法名
    private String sql;                   // 原始 SQL（含 #{}）
    private String parsedSql;             // 解析后的 SQL（#{} → ?）
    private Class<?> resultType;          // 返回类型
    private Class<?>[] parameterType;     // 参数类型
    private List<String> paramNames;      // #{} 中的参数名列表
}
```

### 13.4 SqlSession：一次数据库会话

```java
public class MiniSqlSession {
    private final MiniConfiguration configuration;
    private final MiniExecutor executor;

    // 获取 Mapper 代理
    public <T> T getMapper(Class<T> type) {
        return MiniMapperProxy.newProxy(type, configuration, this);
    }

    // 查询单条
    public <T> T selectOne(String statementId, Object parameter) {
        List<T> results = selectList(statementId, parameter);
        return results.isEmpty() ? null : results.get(0);
    }

    // 查询列表
    public <T> List<T> selectList(String statementId, Object parameter) {
        MiniMappedStatement ms = configuration.getMappedStatement(statementId);
        return executor.query(ms, parameter);
    }
}
```

**SqlSession 的线程安全问题**：

```
线程A: selectById(1) → 获得 Connection → 执行 SQL
线程B: selectById(2) → 复用同一个 Connection → 事务混乱！
```

所以 SqlSession 不能共享，每次操作应该创建新的。

### 13.5 MapperProxy：JDK 动态代理

```java
public class MiniMapperProxy<T> implements InvocationHandler {
    private final Class<T> mapperInterface;
    private final MiniConfiguration configuration;
    private final MiniSqlSession sqlSession;

    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // Object 方法直接调用
        if (Object.class.equals(method.getDeclaringClass())) {
            return method.invoke(this, args);
        }

        // 构造 statementId: com.xxx.UserMapper.selectById
        String statementId = mapperInterface.getName() + "." + method.getName();

        // 获取 MappedStatement
        MiniMappedStatement ms = configuration.getMappedStatement(statementId);

        // 根据 SQL 类型分发
        String sql = ms.getParsedSql();
        if (ms.getSql().startsWith("SELECT")) {
            // 判断返回类型是否为 List
            if (List.class.isAssignableFrom(method.getReturnType())) {
                return sqlSession.selectList(statementId, args);
            }
            return sqlSession.selectOne(statementId, args);
        } else {
            return sqlSession.update(statementId, args);
        }
    }
}
```

### 13.6 Executor：JDBC 执行器

```java
public class MiniExecutor {
    private final Connection connection;

    public <T> List<T> query(MiniMappedStatement ms, Object parameter) throws Exception {
        PreparedStatement ps = null;
        ResultSet rs = null;
        try {
            // 1. 创建 PreparedStatement
            ps = connection.prepareStatement(ms.getParsedSql());

            // 2. 设置参数
            setParameters(ps, ms, parameter);

            // 3. 执行查询
            rs = ps.executeQuery();

            // 4. 结果映射
            return resultSetToList(rs, ms.getResultType());
        } finally {
            if (rs != null) rs.close();
            if (ps != null) ps.close();
        }
    }

    // 参数绑定
    private void setParameters(PreparedStatement ps, MiniMappedStatement ms,
                               Object parameter) throws Exception {
        if (parameter == null) return;

        if (parameter instanceof Object[]) {
            Object[] params = (Object[]) parameter;
            for (int i = 0; i < params.length; i++) {
                ps.setObject(i + 1, params[i]);
            }
        } else {
            ps.setObject(1, parameter);
        }
    }

    // ResultSet → List<Object>
    private <T> List<T> resultSetToList(ResultSet rs, Class<T> resultType) throws Exception {
        List<T> list = new ArrayList<>();
        ResultSetMetaData meta = rs.getMetaData();
        int columnCount = meta.getColumnCount();

        while (rs.next()) {
            // 通过无参构造创建对象
            T obj = resultType.newInstance();

            for (int i = 1; i <= columnCount; i++) {
                String columnName = meta.getColumnLabel(i);
                // 下划线转驼峰：user_name → userName
                String fieldName = underscoreToCamel(columnName);
                Object value = rs.getObject(i);

                // 反射设置字段值
                try {
                    Field field = resultType.getDeclaredField(fieldName);
                    field.setAccessible(true);
                    field.set(obj, value);
                } catch (NoSuchFieldException e) {
                    // 字段不存在，忽略
                }
            }
            list.add(obj);
        }
        return list;
    }

    // 下划线转驼峰
    private String underscoreToCamel(String name) {
        StringBuilder sb = new StringBuilder();
        boolean nextUpper = false;
        for (char c : name.toCharArray()) {
            if (c == '_') {
                nextUpper = true;
            } else {
                sb.append(nextUpper ? Character.toUpperCase(c) : c);
                nextUpper = false;
            }
        }
        return sb.toString();
    }
}
```

### 13.7 手写 MyBatis 与生产级的差距

| 特性 | 我们的实现 | 生产级 MyBatis |
|------|-----------|---------------|
| SQL 解析 | 简单 #{} 替换 | 完整的 OGNL 表达式 |
| 动态 SQL | 不支持 | `<if>/<where>/<foreach>` |
| 结果映射 | 反射 + 下划线转驼峰 | ResultMap、嵌套查询、延迟加载 |
| 缓存 | 无 | 一级缓存 + 二级缓存 |
| 插件 | 无 | Interceptor 链（分页、性能监控） |
| 连接管理 | 手动传入 Connection | 与 Spring 事务集成 |
| 类型处理 | 直接 setObject | TypeHandler 体系（日期、枚举、JSON） |
| XML 支持 | 不支持 | XML + 注解双模式 |

**MyBatis 源码中的关键设计**：

```
SqlSessionFactoryBuilder
    → 解析 XML 配置
    → 创建 SqlSessionFactory（单例）

SqlSessionFactory
    → openSession() 创建 SqlSession
    → 持有 Configuration（全局配置）

SqlSession
    → getMapper() 返回代理
    → selectOne/selectList/insert/update/delete
    → commit/rollback/close

Configuration
    → MappedStatement Registry
    → TypeHandler Registry
    → Mapper Registry
    → Interceptor Chain
```

### 13.8 与 Spring 集成的原理

MyBatis-Spring 的核心：`SqlSessionTemplate` + `MapperScannerConfigurer`

```java
// SqlSessionTemplate 是 SqlSession 的代理
// 每次调用自动创建新的 SqlSession，用完自动关闭
public class SqlSessionTemplate implements SqlSession {
    private final SqlSessionFactory sqlSessionFactory;

    @Override
    public <T> T selectOne(String statement, Object parameter) {
        SqlSession session = sqlSessionFactory.openSession();
        try {
            return session.selectOne(statement, parameter);
        } finally {
            session.close(); // 自动关闭
        }
    }
}

// MapperScannerConfigurer 扫描 Mapper 接口，注册为 Spring Bean
@Bean
public MapperScannerConfigurer mapperScannerConfigurer() {
    MapperScannerConfigurer configurer = new MapperScannerConfigurer();
    configurer.setBasePackage("com.example.mapper");
    return configurer;
}
```

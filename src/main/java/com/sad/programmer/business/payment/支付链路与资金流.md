# 支付链路与资金流

> 从一笔扫码支付开始，逐层拆解资金如何在银行、清算机构、支付机构、商户之间流转，再延伸到集团财务公司的归集下拨、贷款发放等场景。

---

## 一、一笔扫码支付背后发生了什么

用户在早餐店用支付宝扫了商户的收款码，付了 10 块钱。这个动作看似简单，背后至少经过了 6 个系统、4 个机构，资金在 T+1 日才真正到达商户的银行账户。

### 1.1 信息流（T 日，实时）

```
用户手机（支付宝APP）
    ↓ 扫码，确认支付
支付宝服务器
    ↓ 生成交易请求，签名加密
网联清算平台
    ↓ 转接扣款请求
用户发卡行（工行）
    ↓ 校验余额、风控、扣款
工行 → 网联 → 支付宝（扣款结果回传）
    ↓
支付宝更新交易状态为"已支付"
    ↓
通知商户"用户已付款"
```

**关键点**：这一步只是"信息流"，告诉各方"用户已付款"，但钱还没到商户账户。信息流是实时的（秒级），资金流是滞后的（T+1）。

### 1.2 资金流（T+1 日终，批量清算）

```
工行清算账户 -100元（工行从用户卡上扣的钱，集中在这里）
    ↓ 网联日终批量清算
网联清算账户（轧差后净额划转）
    ↓
支付宝在网联的备付金账户 +100元
    ↓ 支付宝扣除手续费0.6元
支付宝在合作银行的备付金账户 -99.4元
    ↓ 银行代付
商户银行账户（招行） +99.4元
```

**为什么是 T+1 而不是实时到账？**

1. **清算机制**：银联/网联采用"日终批量轧差"模式，白天只记账，晚上统一清算。这样效率最高——白天交易量大，逐笔实时清算成本太高。
2. **风控缓冲**：T+1 期间，支付机构可以拦截欺诈交易。如果实时到账，资金到了商户账户就很难追回。
3. **资金沉淀**：100 元在支付宝备付金账户里躺了一天，支付宝可以赚一天的利息。全平台日均沉淀资金千亿级，利息收入可观。
4. **合规要求**：央行要求备付金集中存管，支付机构不能随意挪用，但清算周期本身给了缓冲时间。

### 1.3 手续费去哪了

用户付了 10 块钱，商户实收 9.94 元，差额 0.06 元是手续费。这 0.06 元怎么分？

```
手续费 0.06 元 = 0.6%
  ├── 发卡行（工行）：0.035 元（35%）—— 提供资金来源，承担信用风险
  ├── 清算机构（网联）：0.005 元（5%）—— 提供转接清算服务
  └── 收单机构（支付宝）：0.02 元（20%）—— 提供商户接入、风控、结算
```

**行业费率参考**：
- 标准商户费率：0.6%（餐饮、零售）
- 民生类费率：0.38%（水电煤、交通）
- 公益类费率：0%（医院、学校）
- 优惠类费率：0.38%-0.48%（加油站、超市）

## 二、从扫码支付到电商支付：链路怎么变复杂了

扫码支付是"面对面"场景，用户和商户在同一物理空间。电商支付是"远程"场景，引入了订单系统、收银台、异步回调等环节。

### 2.1 电商支付全链路

```
用户在电商平台下单
    ↓
电商平台创建订单（状态：待支付）
    ↓
跳转收银台，展示支付方式（支付宝/微信/银行卡/余额）
    ↓ 用户选择支付宝
电商平台调用支付宝"统一收单下单接口"
    ↓ 返回支付链接/二维码
用户在支付宝完成支付（同场景一的扫码支付流程）
    ↓
支付宝异步回调电商平台："支付成功"
    ↓
电商平台更新订单状态为"已支付"
    ↓
通知用户"支付成功"，通知商户"用户已付款"
```

### 2.2 电商支付比扫码支付多了什么

| 环节 | 扫码支付 | 电商支付 | 为什么多 |
|------|----------|----------|----------|
| 订单系统 | 无（即时交易） | 有（创建订单→支付→发货→确认） | 电商交易有生命周期，不是即时完成 |
| 收银台 | 无（直接扫码） | 有（选择支付方式） | 多种支付方式需要统一入口 |
| 异步回调 | 商户现场确认 | 异步回调+重试 | 远程场景不能实时确认，靠回调通知 |
| 支付单 | 无 | 有（独立于订单） | 订单和支付是两个系统，解耦设计 |
| 对账 | 简单（逐笔） | 复杂（批量） | 电商交易量大，需要批量对账 |

### 2.3 为什么需要独立的支付单

```
订单（Order）：记录"用户买了什么"
  - 商品信息、数量、金额、收货地址
  - 生命周期：下单→发货→收货→完成

支付单（Payment）：记录"用户怎么付的钱"
  - 支付方式、支付渠道、支付金额、支付状态
  - 生命周期：创建→支付→回调→对账
```

**为什么要分开？**

1. **一个订单可能多次支付**：用户第一次支付失败（银行卡余额不足），换一张卡重试，产生两个支付单
2. **一个订单可能分次支付**：分期付款、组合支付（余额+银行卡）
3. **支付系统独立演进**：支付系统要对接多个渠道、做对账、做风控，和订单系统职责完全不同
4. **对账独立**：支付系统和渠道对账，不需要知道订单详情

## 三、资金在支付机构内部怎么流转

用户付了钱，钱进了支付宝的备付金账户。但这笔钱在支付宝内部经历了什么？

### 3.1 支付宝内部账户体系

```
用户A余额账户：100元
用户B余额账户：50元
商户C待结算账户：200元（已收到但未提现）
商户D待结算账户：150元

支付宝备付金总账户（在央行）：500元 = 100+50+200+150
```

**关键理解**：支付宝是一个"账务系统"，用户看到的"余额"只是一个数字，真正的钱在央行的备付金账户里。支付宝做的所有操作，都是在内部账户之间记账。

### 3.2 一笔支付的内部记账

```
用户A用余额支付100元给商户C：

内部记账：
  用户A余额账户：-100元
  商户C待结算账户：+100元

央行备付金账户：不变（钱还在支付宝体系内）
```

### 3.3 商户提现的内部记账

```
商户C提现200元到银行卡：

内部记账：
  商户C待结算账户：-200元
  支付宝代付账户：+200元

央行备付金账户：-200元（钱出了支付宝体系）
  → 银行代付 → 商户C银行账户 +200元
```

### 3.4 为什么要有"待结算账户"

商户收到钱后，不是立刻可以提现。T+1 结算后，资金从"待结算"变为"可提现"。

```
T日：商户收到100元 → 进入待结算账户
T+1日：结算完成 → 待结算100元 → 可提现100元

为什么要这样设计？
1. 风控缓冲：T+1期间发现欺诈，可以拦截
2. 退款扣款：如果用户退款，直接从待结算扣，不需要商户先垫钱
3. 资金安全：防止商户收到钱立刻转走，留下未处理的退款纠纷
```

## 四、银行在支付链路中扮演什么角色

很多人以为银行只是"扣款"和"收款"，其实银行在支付链路中有多个角色。

### 4.1 发卡行（Issuer）

```
用户用工行卡付款 → 工行就是发卡行

工行的职责：
1. 验证卡号、有效期、CVV
2. 校验余额/额度
3. 风控拦截（可疑交易）
4. 执行扣款
5. 返回扣款结果
```

### 4.2 收单行（Acquirer）

```
商户在招行开户 → 招行就是收单行

招行的职责：
1. 为商户提供收款账户
2. 接收支付机构的结算指令
3. 将资金入账到商户账户
4. 提供对账单
```

### 4.3 清算机构（银联/网联）

```
工行（发卡行）←→ 银联/网联 ←→ 招行（收单行）

清算机构的职责：
1. 转接：把工行的扣款请求转给招行（或反向）
2. 清算：日终计算各方应收应付金额
3. 轧差：汇总后计算净额，减少资金调拨次数
```

### 4.4 一个支付机构可能同时是发卡行和收单行

```
用户用工行卡在支付宝付款：
  - 工行是发卡行
  - 支付宝是收单机构（不是银行，但承担收单职能）

商户在支付宝收款：
  - 支付宝是收单机构
  - 商户的开户行是收单行
```

## 五、集团财务公司的支付链路

财务公司的支付链路和第三方支付完全不同。第三方支付是"对外"的（面向公众），财务公司是"对内"的（面向集团成员单位）。

### 5.1 内部转账：钱不出集团

```
江苏电信要转500万给广东电信：

传统银行路径：江苏电信银行账户 → 工行 → 银联 → 广东电信银行账户
  - 走银行系统，有手续费，有延迟

财务公司路径：江苏电信在财务公司的存款账户 → 财务公司账务系统 → 广东电信在财务公司的存款账户
  - 资金不出集团，无手续费，实时到账
```

**内部记账**：

```
财务公司账务系统：
  江苏电信活期存款账户：-500万
  广东电信活期存款账户：+500万

财务公司总资产不变（左口袋到右口袋）
```

**这是财务公司存在的核心价值**：集团内部资金流转不需要走银行，节省手续费，提高效率，资金在集团内部闭环。

### 5.2 资金归集：把分散的钱收回来

```
背景：电信集团有200+成员单位，每个单位在各地银行有自己的账户。
问题：资金分散在各银行，集团无法统一调度。
目标：每天日终，把各成员单位银行账户的钱归集到财务公司。
```

**归集链路**：

```
步骤1：财务公司司库制定归集计划
  - 江苏电信：归集比例80%（保留20%日常周转）
  - 广东电信：归集比例90%
  - 浙江电信：归集比例85%

步骤2：日终，财务公司系统通过银企直连向银行发送归集指令
  - 指令内容：从江苏电信工行账户扣款X万元，划入财务公司工行归集账户

步骤3：银行执行扣款
  - 工行江苏分行：江苏电信账户 -X万
  - 工行总行：财务公司归集账户 +X万

步骤4：财务公司内部记账
  - 江苏电信在财务公司的活期存款账户 +X万
  - 财务公司银行存款 +X万

步骤5：银行返回扣款结果，财务公司更新台账
```

**资金流**：

```
江苏电信银行账户（工行江苏分行）-X万
    ↓ 银企直连（工行内部划转）
财务公司在工行的归集账户 +X万
    ↓ 内部记账
江苏电信在财务公司的活期存款账户 +X万
```

**为什么归集比例不是100%？**

成员单位需要保留一部分资金在银行账户，用于日常对外支付（发工资、付供应商款）。归集比例由财务公司和成员单位协商确定，通常在70%-90%。

### 5.3 资金下拨：把钱拨回去

```
背景：江苏电信需要支付供应商1000万，但银行账户只有200万。
目标：从财务公司下拨800万到江苏电信银行账户。
```

**下拨链路**：

```
步骤1：江苏电信在网银发起下拨申请（或财务公司根据预算自动下拨）

步骤2：财务公司审批
  - 检查：江苏电信在财务公司存款余额 ≥ 800万
  - 检查：是否在预算范围内
  - 检查：是否超过单笔/日累计限额

步骤3：审批通过，财务公司内部记账
  - 江苏电信在财务公司的活期存款账户 -800万

步骤4：财务公司通过银企直连向银行发送付款指令
  - 指令内容：从财务公司工行归集账户付款800万到江苏电信工行账户

步骤5：银行执行付款
  - 财务公司工行归集账户 -800万
  - 江苏电信工行账户 +800万

步骤6：银行返回结果，财务公司更新台账
```

**资金流**：

```
江苏电信在财务公司的活期存款 -800万
    ↓ 内部记账
财务公司工行归集账户 -800万
    ↓ 银企直连
江苏电信工行账户 +800万
```

### 5.4 贷款发放：钱从哪来

成员单位向财务公司贷款5000万，这笔钱从哪来？

**场景A：贷款资金留在财务公司**

```
江苏电信贷款5000万，用于支付集团内另一成员单位的货款：

财务公司记账：
  资产端：贷款资产 +5000万（江苏电信欠财务公司5000万）
  负债端：江苏电信活期存款 +5000万（江苏电信在财务公司多了5000万）

资金未流出财务公司。
江苏电信可以用这5000万在集团内部转账、支付货款。
```

**场景B：贷款资金下拨到银行**

```
江苏电信贷款5000万，需要支付外部供应商：

财务公司记账：
  资产端：贷款资产 +5000万
  负债端：江苏电信活期存款 +5000万

江苏电信申请下拨5000万：
  江苏电信活期存款 -5000万
  财务公司银行存款 -5000万
  银企直连付款 → 江苏电信银行账户 +5000万
```

**关键理解**：财务公司发放贷款时，贷款资产和存款负债同时增加，会计恒等式成立（资产=负债+所有者权益）。资金是否流出集团，取决于成员单位是内部使用还是对外支付。

## 六、第三方支付与财务公司的结合

成员单位既在财务公司有存款，也在银行有账户，还可能通过支付宝/微信收款。这三条资金流怎么汇合？

### 6.1 话费收款的完整资金流

```
用户在江苏电信营业厅扫码付100元话费：

T日：
  用户工行卡 -100元
  工行 → 网联 → 支付宝备付金 +100元（信息流完成，用户已付款）

T+1日：
  支付宝扣除手续费0.6元
  支付宝 → 网联 → 江苏电信银行账户（工行江苏分行） +99.4元

日终归集：
  财务公司通过银企直连，将江苏电信银行账户的99.4元归集到财务公司
  财务公司工行归集账户 +99.4元
  江苏电信在财务公司活期存款 +99.4元

最终结果：
  用户银行卡 -100元
  江苏电信在财务公司存款 +99.4元
  支付宝手续费收入 +0.6元
```

### 6.2 为什么不能直接归集到财务公司

```
用户扫码支付 → 支付宝 → 能不能直接到财务公司？

不能。原因：
1. 财务公司不是银行，不能接入银联/网联
2. 财务公司不能对外收单（牌照限制）
3. 支付宝只能结算到银行账户，不能结算到财务公司账户

所以必须：用户 → 支付宝 → 成员单位银行账户 → 银企直连归集 → 财务公司
```

## 七、退款的资金流：钱怎么退回去

### 7.1 原路退款的链路

```
用户申请退款100元：

步骤1：商户确认退款
步骤2：平台调用支付宝退款接口
步骤3：支付宝从商户待结算账户扣100元
步骤4：支付宝 → 网联 → 工行（退款到用户原支付卡）
步骤5：工行将100元退回用户银行卡

资金流：
  商户待结算账户 -100元
  → 支付宝退款处理
  → 工行用户卡 +100元
```

**退款为什么不退手续费？**

大多数支付机构的规则：退款时手续费不退。原因：
1. 清算机构已经收了清算费，不退
2. 发卡行已经收了发卡费，不退
3. 支付机构的风控成本已经发生，不退

### 7.2 退款资金不足怎么办

```
商户待结算账户只有50元，用户申请退款100元：

情况1：退款失败（提示商户余额不足）
情况2：从商户可提现余额扣（需要商户授权）
情况3：商户充值后再退
```

### 7.3 财务公司内部退款

```
江苏电信误转500万给广东电信，申请退款：

原交易：江苏电信 -500万 → 广东电信 +500万
退款：  广东电信 -500万 → 江苏电信 +500万

财务公司内部记账，资金不出集团，无手续费。
```

## 八、对账：怎么发现资金不一致

### 8.1 为什么需要对账

```
场景：用户支付100元，支付宝扣款成功，但回调丢失。

平台视角：用户未支付（没收到回调）
支付宝视角：用户已支付（扣款成功）
用户视角：钱已扣，但订单显示未支付

如果没有对账，这笔交易就会"失踪"：
  用户付了钱，平台没发货，商户没收到钱。
```

### 8.2 对账流程

```
日终对账（T+1凌晨执行）：

步骤1：下载渠道对账文件
  支付宝：下载T日交易明细（CSV文件，每笔交易一行）
  微信：下载T日交易明细
  银联：下载T日交易明细
  银企直连：下载T日银行流水

步骤2：解析对账文件，生成渠道侧账单

步骤3：拉取本地交易记录（T日）

步骤4：逐笔比对
  以交易号为主键：
  - 本地有，渠道有，金额一致 → 正常
  - 本地有，渠道无 → 长款（渠道可能延迟，T+1再对）
  - 本地无，渠道有 → 短款（回调丢失，需要补单）
  - 金额不一致 → 差异（手续费计算差异，人工确认）

步骤5：差异处理
  短款：根据渠道流水号，在本地补创建支付记录，通知业务系统
  长款：标记为待确认，T+1再对一次
  金额差异：核对手续费，差异通常在1分钱内
```

### 8.3 财务公司对账

```
财务公司日终对账：

银行流水对账：
  财务公司记录的银企直连交易 vs 银行提供的交易流水
  核对：归集金额、下拨金额、手续费

内部账务对账：
  各成员单位存款余额合计 vs 财务公司总账
  贷款资产合计 vs 贷款分户账
  利息收支核对

监管报送：
  1104报表数据准备
  资本充足率、流动性比例计算
```

## 九、资金在途与挂账

### 9.1 什么是在途资金

```
用户发起提现100元 → 支付渠道处理中 → 银行尚未入账

这段时间（可能几秒，也可能几小时），资金处于"在途"状态：
  用户视角：钱已扣，但银行卡没到账
  平台视角：提现处理中，不知道最终结果
  银行视角：清算中，资金还没到
```

**在途资金的风险**：

```
如果平台在"在途"状态就认为提现成功，更新用户余额：
  风险：银行可能最终返回"失败"（银行卡异常、账户冻结）
  后果：用户余额已扣，但银行卡没到账，用户投诉

正确做法：等银行明确返回"成功"后，才更新状态。
```

### 9.2 挂账处理

```
资金无法入账时（如收款账户已销户），资金"挂账"在中间账户：

用户转账100元 → 银行 → 收款账户异常
  ↓
资金挂账在银行的"待处理账户"（挂账）
  ↓
银行通知付款方，要求提供正确收款信息
  ↓
提供正确信息后，重新入账
  ↓
如果长时间无人处理，资金原路退回
```

## 十、手续费分润：谁在赚钱

### 10.1 一笔支付的手续费分配

```
用户支付100元，商户实收99.4元，手续费0.6元：

发卡行（工行）：0.35元 —— 提供资金来源，承担信用风险
清算机构（网联）：0.05元 —— 提供转接清算服务
收单机构（支付宝）：0.20元 —— 提供商户接入、风控、结算

为什么发卡行拿最多？
  1. 用户资金存在发卡行，发卡行有资金成本
  2. 发卡行承担信用风险（信用卡拒付）
  3. 发卡行提供风控（可疑交易拦截）
```

### 10.2 财务公司的手续费

```
财务公司通过银企直连归集/下拨资金：

手续费：银行按笔收费（如1元/笔）或按金额比例（如0.01%）
内部转账：无手续费（财务公司内部记账）

财务公司的价值：节省集团整体手续费支出。
  原来：成员单位之间转账走银行，每笔收手续费
  现在：走财务公司内部转账，免费
```

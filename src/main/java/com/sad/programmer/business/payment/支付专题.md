# 支付专题

> 适用场景：支付中台、收银台、聚合支付、金融核心
> 核心考点：渠道路由、幂等回调、对账机制、退款设计、资金安全、防重放

---

## 一、支付架构篇

### Q1：支付系统的整体架构是怎样的？

> **深度回答**：
>
> **五层架构**：
>
> ```
> ┌──────────────────────────────────────────────────────────┐
> │                     业务接入层                             │
> │  电商订单 │ 充值订单 │ 生活缴费 │ 转账 │ 提现            │
> └──────────────────────────────────────────────────────────┘
>          ↓
> ┌──────────────────────────────────────────────────────────┐
> │                     收银台层                              │
> │  支付方式选择 │ 优惠展示 │ 支付密码 │ 风控校验            │
> └──────────────────────────────────────────────────────────┘
>          ↓
> ┌──────────────────────────────────────────────────────────┐
> │                   支付网关层                              │
> │  签名验签 │ 加解密 │ 幂等校验 │ 风控拦截 │ 流量控制       │
> └──────────────────────────────────────────────────────────┘
>          ↓
> ┌──────────────────────────────────────────────────────────┐
> │                   支付引擎层                              │
> │  渠道路由 │ 支付执行 │ 异步回调 │ 退款 │ 对账            │
> └──────────────────────────────────────────────────────────┘
>          ↓
> ┌──────────────────────────────────────────────────────────┐
> │                   渠道适配层                              │
> │  支付宝适配 │ 微信适配 │ 银联适配 │ 网银适配 │ 虚拟支付    │
> └──────────────────────────────────────────────────────────┘
> ```
>
> **核心设计原则**：
>
> | 原则 | 说明 |
> |------|------|
> | **幂等** | 所有接口幂等，重复调用返回同一结果 |
> | **一致** | 支付状态与业务订单状态最终一致 |
> | **安全** | 敏感信息加密传输，防重放、防篡改 |
> | **可追溯** | 全链路 traceId，每笔交易可追溯 |
> | **对账** | 日终对账，差异自动处理 |
>
> **面试追问**：为什么要分收银台和支付引擎？
>
> 收银台关注用户体验（展示支付方式、优惠信息），支付引擎关注资金安全（幂等、对账、风控）。职责分离后，收银台可以独立迭代 UI，支付引擎可以独立扩展渠道。

### Q2：支付单和订单是什么关系？为什么需要独立的支付单？

> **深度回答**：
>
> **支付单 vs 订单**：
>
> | 维度 | 订单（Order） | 支付单（Payment） |
> |------|--------------|-------------------|
> | 关注点 | 商品交易 | 资金流转 |
> | 归属 | 业务系统 | 支付系统 |
> | 生命周期 | 下单→发货→收货→完成 | 创建→支付→回调→对账 |
> | 金额 | 商品金额（含优惠） | 实际支付金额 |
> | 状态 | 待支付/已支付/已取消 | 待支付/支付中/成功/失败 |
>
> **为什么不直接在订单上记录支付信息？**
>
> 1. **职责分离**：订单关注商品交易，支付关注资金流转，耦合后改支付逻辑要改订单表
> 2. **一单多付**：部分场景一个订单分多次支付（分期付款、组合支付）
> 3. **支付重试**：同一订单可以发起多次支付（前一次失败），每次生成新的支付单
> 4. **对账独立**：支付系统独立对账，不依赖订单系统
>
> **支付单表设计**：
> ```sql
> CREATE TABLE payment_order (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     payment_no VARCHAR(64) NOT NULL UNIQUE COMMENT '支付单号（幂等键）',
>     biz_order_no VARCHAR(64) NOT NULL COMMENT '业务订单号',
>     biz_type VARCHAR(32) NOT NULL COMMENT '业务类型：ORDER/RECHARGE/TRANSFER',
>     user_id BIGINT NOT NULL COMMENT '支付用户ID',
>     amount DECIMAL(12,2) NOT NULL COMMENT '支付金额',
>     currency VARCHAR(3) NOT NULL DEFAULT 'CNY' COMMENT '币种',
>     payment_method VARCHAR(32) NOT NULL COMMENT '支付方式：ALIPAY/WECHAT/UNIONPAY/BALANCE',
>     channel_code VARCHAR(32) COMMENT '支付渠道编码',
>     channel_payment_no VARCHAR(128) COMMENT '渠道支付流水号（回调时回填）',
>     payment_status TINYINT NOT NULL DEFAULT 0 COMMENT '0-待支付 1-支付中 2-成功 3-失败 4-已关闭',
>     pay_time DATETIME COMMENT '支付成功时间',
>     expire_time DATETIME COMMENT '支付截止时间',
>     notify_url VARCHAR(256) NOT NULL COMMENT '异步回调地址',
>     return_url VARCHAR(256) COMMENT '同步跳转地址',
>     extra_params JSON COMMENT '扩展参数',
>     version INT NOT NULL DEFAULT 0,
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_biz_order_no (biz_order_no),
>     INDEX idx_user_id (user_id),
>     INDEX idx_payment_status (payment_status),
>     INDEX idx_create_time (create_time)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='支付单表';
> ```
>
> **面试追问**：biz_order_no 为什么不设唯一约束？
>
> 同一业务订单可能发起多次支付（前一次失败重试），每次生成新的 payment_no。biz_order_no 是多对一关系，不能唯一。

## 二、渠道路由篇

### Q3：支付渠道路由怎么设计？

> **深度回答**：
>
> **渠道路由**：根据规则自动选择最优支付渠道。
>
> **路由规则**：
>
> | 维度 | 规则 | 示例 |
> |------|------|------|
> | **支付方式** | 用户选择的支付方式 | 微信支付 → 微信直连/微信银联 |
> | **金额区间** | 不同金额走不同渠道 | < 5万走快捷，≥ 5万走网银 |
> | **银行** | 用户绑定的银行卡 | 工商银行 → 工行直连/银联 |
> | **成功率** | 优先选成功率高的渠道 | 渠道A成功率99%，渠道B 95% → 选A |
> | **成本** | 优先选费率低的渠道 | 渠道A费率0.6%，渠道B 0.38% → 选B |
> | **权重** | 运营配置的权重 | A:B = 7:3，按权重随机 |
>
> **路由引擎实现**：
> ```java
> /**
> * 支付渠道路由引擎，按优先级链式匹配。
> */
> public class ChannelRouter {
>
>     private final List<RouteRule> rules; // 按优先级排序
>
>     public ChannelRouteResult route(PaymentContext context) {
>         List<ChannelCandidate> candidates = loadCandidates(context);
>
>         for (RouteRule rule : rules) {
>             candidates = rule.filter(candidates, context);
>             if (candidates.size() == 1) break; // 唯一确定
>         }
>
>         if (candidates.isEmpty()) {
>             throw new NoAvailableChannelException("无可用渠道");
>         }
>
>         // 多个候选时按权重随机
>         return weightedRandom(candidates);
>     }
> }
>
> /**
> * 渠道候选（从数据库加载，支持动态配置）。
> */
> public class ChannelCandidate {
>     private String channelCode;      // 渠道编码
>     private String channelName;      // 渠道名称
>     private BigDecimal feeRate;      // 费率
>     private BigDecimal successRate;  // 最近1小时成功率
>     private int weight;              // 权重
>     private boolean enabled;         // 是否启用
> }
> ```
>
> **渠道降级**：
> ```
> 主渠道（微信直连）→ 备用渠道1（微信银联）→ 备用渠道2（微信银行）
> ```
> 主渠道失败时自动切换到备用渠道，对用户无感。
>
> **面试追问**：渠道成功率怎么统计？
>
> 滑动窗口统计：每分钟统计该渠道的成功率，存入 Redis。路由时读取最近 5 分钟的加权平均成功率。成功率低于阈值（如 90%）自动降级。

### Q4：支付渠道适配层怎么设计？怎么统一不同渠道的接口差异？

> **深度回答**：
>
> **适配器模式**：
>
> ```java
> /**
> * 渠道适配器接口，所有渠道实现此接口。
> */
> public interface ChannelAdapter {
>
>     /** 渠道编码 */
>     String getChannelCode();
>
>     /** 创建支付（返回渠道侧的支付链接/参数） */
>     ChannelPayResult createPayment(ChannelPayRequest request);
>
>     /** 查询支付状态 */
>     ChannelQueryResult queryPayment(String channelPaymentNo);
>
>     /** 发起退款 */
>     ChannelRefundResult refund(ChannelRefundRequest request);
>
>     /** 查询退款状态 */
>     ChannelRefundQueryResult queryRefund(String channelRefundNo);
>
>     /** 验签回调 */
>     boolean verifyNotify(Map<String, String> params, String signature);
> }
>
> /**
> * 支付宝适配器。
> */
> public class AlipayChannelAdapter implements ChannelAdapter {
>
>     @Override
>     public String getChannelCode() { return "ALIPAY"; }
>
>     @Override
>     public ChannelPayResult createPayment(ChannelPayRequest request) {
>         // 调用支付宝 SDK
>         AlipayTradePayRequest alipayReq = new AlipayTradePayRequest();
>         alipayReq.setTotalAmount(request.getAmount().toString());
>         alipayReq.setSubject(request.getSubject());
>         // ... 其他参数映射
>
>         AlipayTradePayResponse response = alipayClient.execute(alipayReq);
>         // 转换为统一结果
>         return ChannelPayResult.builder()
>             .channelPaymentNo(response.getTradeNo())
>             .payUrl(response.getQrCode())
>             .status(mapStatus(response.getTradeStatus()))
>             .build();
>     }
> }
> ```
>
> **渠道注册表**：
> ```java
> /**
> * 渠道适配器注册中心，启动时自动扫描注册。
> */
> @Component
> public class ChannelAdapterRegistry {
>
>     private final Map<String, ChannelAdapter> adapters = new ConcurrentHashMap<>();
>
>     @Autowired
>     public ChannelAdapterRegistry(List<ChannelAdapter> adapterList) {
>         for (ChannelAdapter adapter : adapterList) {
>             adapters.put(adapter.getChannelCode(), adapter);
>         }
>     }
>
>     public ChannelAdapter getAdapter(String channelCode) {
>         ChannelAdapter adapter = adapters.get(channelCode);
>         if (adapter == null) throw new IllegalArgumentException("未知渠道: " + channelCode);
>         return adapter;
>     }
> }
> ```
>
> **面试追问**：新增一个支付渠道需要改多少代码？
>
> 只需新增一个 `XxxChannelAdapter` 实现类，加上 `@Component` 注解，自动注册到注册中心。支付引擎、对账、退款等上层逻辑零修改。这就是适配器模式的价值。

## 三、支付流程篇

### Q5：支付回调怎么保证幂等？重复通知怎么处理？

> **深度回答**：
>
> **三层幂等保障**：
>
> ```
> 渠道回调（可能重复）
>     ↓
> 1. 签名验证（防伪造）
>     ↓
> 2. 幂等检查（Redis + 数据库双重校验）
>     ↓
> 3. 状态机控制（只处理合法状态变更）
> ```
>
> **幂等实现**：
> ```java
> @Transactional
> public PaymentNotifyResult handleNotify(PaymentNotifyRequest request) {
>     // 1. 验签
>     ChannelAdapter adapter = adapterRegistry.getAdapter(request.getChannelCode());
>     if (!adapter.verifyNotify(request.getParams(), request.getSignature())) {
>         return PaymentNotifyResult.fail("验签失败");
>     }
>
>     // 2. 查询支付单
>     PaymentOrder payment = paymentMapper.selectByPaymentNo(request.getPaymentNo());
>     if (payment == null) {
>         return PaymentNotifyResult.fail("支付单不存在");
>     }
>
>     // 3. 幂等检查：已成功则直接返回成功
>     if (payment.getPaymentStatus() == PaymentStatus.SUCCESS) {
>         return PaymentNotifyResult.success("已处理");
>     }
>
>     // 4. 状态机校验：只有待支付/支付中才能变更为成功
>     if (payment.getPaymentStatus() != PaymentStatus.PENDING
>         && payment.getPaymentStatus() != PaymentStatus.PROCESSING) {
>         return PaymentNotifyResult.fail("状态不允许: " + payment.getPaymentStatus());
>     }
>
>     // 5. 更新支付单状态（乐观锁）
>     int rows = paymentMapper.updateStatus(
>         payment.getPaymentNo(),
>         PaymentStatus.SUCCESS,        // 目标状态
>         payment.getPaymentStatus(),    // 当前状态
>         request.getChannelPaymentNo(), // 渠道流水号
>         payment.getVersion()
>     );
>     if (rows == 0) {
>         return PaymentNotifyResult.success("并发处理，已成功"); // 并发场景，乐观锁失败
>     }
>
>     // 6. 通知业务系统（异步）
>     mqProducer.send("payment.success", new PaymentSuccessEvent(
>         payment.getPaymentNo(),
>         payment.getBizOrderNo(),
>         payment.getAmount()
>     ));
>
>     return PaymentNotifyResult.success("处理成功");
> }
> ```
>
> **关键设计点**：
>
> | 设计点 | 方案 | 原因 |
> |--------|------|------|
> | 验签 | RSA/MD5 签名验证 | 防止伪造回调 |
> | 幂等检查 | 先查状态再更新 | 已成功直接返回 |
> | 乐观锁 | version + 状态条件 | 防止并发重复处理 |
> | 异步通知 | MQ 异步解耦 | 支付系统快速响应渠道 |
>
> **面试追问**：渠道要求回调必须返回特定格式，否则会重试怎么办？
>
> 支付系统收到回调后，先落库（防丢失），然后快速返回渠道要求的成功响应，再异步处理业务逻辑。如果业务逻辑失败（如通知订单系统失败），有定时任务重试。

### Q6：支付超时怎么处理？

> **深度回答**：
>
> **超时场景**：
>
> | 场景 | 处理方式 |
> |------|----------|
> | 用户未完成支付 | 支付单超时关闭，释放库存 |
> | 渠道长时间未回调 | 主动查询渠道状态 |
> | 渠道返回处理中 | 轮询查询直到终态 |
>
> **超时处理流程**：
>
> ```java
> /**
> * 支付超时处理任务。
> */
> @Scheduled(fixedDelay = 60000) // 每分钟执行
> public void handlePaymentTimeout() {
>     // 1. 查询已超时的支付单
>     List<PaymentOrder> expiredPayments = paymentMapper.selectExpired(
>         PaymentStatus.PENDING,
>         LocalDateTime.now().minusMinutes(30),
>         100 // 每批100条
>     );
>
>     for (PaymentOrder payment : expiredPayments) {
>         try {
>             // 2. 先查询渠道确认最终状态
>             ChannelAdapter adapter = adapterRegistry.getAdapter(payment.getChannelCode());
>             ChannelQueryResult result = adapter.queryPayment(payment.getPaymentNo());
>
>             if (result.isSuccess()) {
>                 // 渠道侧已成功，补发回调
>                 handleNotify(buildNotifyFromQuery(result));
>             } else if (result.isProcessing()) {
>                 // 仍在处理中，延长超时时间
>                 paymentMapper.extendExpireTime(payment.getPaymentNo(), 10);
>             } else {
>                 // 确认失败或未支付，关闭支付单
>                 closePayment(payment.getPaymentNo(), "超时关闭");
>             }
>         } catch (Exception e) {
>             log.error("处理支付超时异常: {}", payment.getPaymentNo(), e);
>             // 异常不阻塞，下次重试
>         }
>     }
> }
> ```
>
> **面试追问**：为什么要先查询渠道再关闭？
>
> 防止"渠道已成功但回调丢失"的场景。如果直接关闭，用户付了钱但订单被取消，造成资损。先查渠道确认真实状态，再做相应处理。

## 四、对账机制篇

### Q7：支付对账怎么做？差异怎么处理？

> **深度回答**：
>
> **对账流程**：
>
> ```
> 日终对账任务（T+1 凌晨 2:00 触发）
>     ↓
> 下载渠道对账文件（支付宝/微信/银联）
>     ↓
> 解析对账文件 → 渠道侧账单明细
>     ↓
> 拉取本地支付记录（T日成功/退款）
>     ↓
> 逐笔比对（金额、状态、时间）
>     ↓
> 输出对账结果：
>   ├── 一致（正常）
>   ├── 本地有渠道无（长款 → 人工确认）
>   ├── 本地无渠道有（短款 → 补单/退款）
>   └── 金额不一致（差异 → 人工处理）
> ```
>
> **对账表设计**：
> ```sql
> CREATE TABLE reconciliation_record (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     recon_date DATE NOT NULL COMMENT '对账日期',
>     channel_code VARCHAR(32) NOT NULL COMMENT '渠道编码',
>     payment_no VARCHAR(64) COMMENT '本地支付单号',
>     channel_payment_no VARCHAR(128) COMMENT '渠道流水号',
>     local_amount DECIMAL(12,2) COMMENT '本地金额',
>     channel_amount DECIMAL(12,2) COMMENT '渠道金额',
>     recon_result TINYINT NOT NULL COMMENT '对账结果：1-一致 2-长款 3-短款 4-金额不一致',
>     handle_status TINYINT NOT NULL DEFAULT 0 COMMENT '处理状态：0-待处理 1-已处理 2-忽略',
>     handle_remark VARCHAR(512) COMMENT '处理说明',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     INDEX idx_recon_date_channel (recon_date, channel_code),
>     INDEX idx_recon_result (recon_result)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='对账记录表';
> ```
>
> **差异处理策略**：
>
> | 差异类型 | 原因 | 处理方式 |
> |----------|------|----------|
> | **长款**（本地有，渠道无） | 渠道对账文件延迟、渠道漏报 | T+1 再对一次，仍存在则人工确认 |
> | **短款**（本地无，渠道有） | 回调丢失、本地未记录 | 补单：根据渠道流水号创建本地记录，通知业务系统 |
> | **金额不一致** | 手续费计算差异、汇率差异 | 核对手续费，差异金额一般在1分钱内（精度问题） |
>
> **面试追问**：对账文件下载失败怎么办？
>
> 1. 重试3次，每次间隔5分钟
> 2. 仍失败则告警，人工介入
> 3. 支持手动上传对账文件补对
> 4. 对账任务幂等，重复执行只覆盖不重复

### Q8：资金安全怎么保证？怎么防止资金损失？

> **深度回答**：
>
> **资金安全七道防线**：
>
> ```
> ┌────────────────────────────────────────────────────────────┐
> │ 1. 签名验签：防止请求伪造                                   │
> │ 2. 金额校验：服务端计算，不信任前端                          │
> │ 3. 幂等控制：防止重复扣款                                    │
> │ 4. 状态机：防止非法状态变更                                  │
> │ 5. 对账：发现不一致                                          │
> │ 6. 限额：单笔/日累计/月累计限额                              │
> │ 7. 风控：异常交易拦截                                        │
> └────────────────────────────────────────────────────────────┘
> ```
>
> **金额校验链**：
>
> ```java
> /**
> * 支付前金额校验，四重验证。
> */
> public void validateAmount(PaymentOrder payment, BigDecimal requestAmount) {
>     // 1. 支付单金额 == 请求金额
>     if (payment.getAmount().compareTo(requestAmount) != 0) {
>         throw new BizException("支付单金额不匹配");
>     }
>
>     // 2. 支付单金额 == 业务订单金额（从订单系统查询）
>     BigDecimal orderAmount = orderService.getPayableAmount(payment.getBizOrderNo());
>     if (payment.getAmount().compareTo(orderAmount) != 0) {
>         throw new BizException("订单金额不匹配");
>     }
>
>     // 3. 回调金额 == 支付单金额（渠道回调时校验）
>     // 在 handleNotify 方法中校验
>
>     // 4. 退款累计金额 <= 支付金额（退款时校验）
>     BigDecimal totalRefund = refundService.getTotalRefundAmount(payment.getPaymentNo());
>     if (totalRefund.compareTo(payment.getAmount()) > 0) {
>         throw new BizException("退款金额超过支付金额");
>     }
> }
> ```
>
> **限额设计**：
> ```sql
> CREATE TABLE payment_limit (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     user_id BIGINT NOT NULL COMMENT '用户ID',
>     limit_type TINYINT NOT NULL COMMENT '限额类型：1-单笔 2-日累计 3-月累计',
>     max_amount DECIMAL(12,2) NOT NULL COMMENT '限额金额',
>     used_amount DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '已用额度',
>     limit_date DATE COMMENT '额度日期（日限额用）',
>     limit_month VARCHAR(7) COMMENT '额度月份（月限额用）',
>     UNIQUE KEY uk_user_type_date (user_id, limit_type, limit_date),
>     INDEX idx_user_id (user_id)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='支付限额表';
> ```
>
> **面试追问**：限额并发扣减怎么防超限？
>
> Redis 原子操作 + 数据库乐观锁兜底。
> ```lua
> -- Lua 脚本原子校验并扣减
> local used = tonumber(redis.call('GET', KEYS[1]) or '0')
> local max = tonumber(ARGV[1])
> local amount = tonumber(ARGV[2])
> if used + amount > max then
>     return 0  -- 超限
> end
> redis.call('INCRBYFLOAT', KEYS[1], amount)
> return 1
> ```

>     amount DECIMAL(12,2) NOT NULL COMMENT '该方式支付金额',
>     channel_code VARCHAR(32) COMMENT '渠道编码',
>     channel_payment_no VARCHAR(128) COMMENT '渠道流水号',
>     detail_status TINYINT NOT NULL DEFAULT 0 COMMENT '0-待支付 1-成功 2-失败',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     INDEX idx_payment_no (payment_no)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='组合支付明细表';
> ```
>
> **组合支付流程**：
>
> ```
> 用户选择：余额扣30元 + 微信付70元
>     ↓
> 创建支付主单（100元）+ 2条明细
>     ↓
> 先扣余额（内部操作，实时确认）
>     ↓
> 余额扣成功 → 再调微信支付（70元）
>     ↓
> 微信回调成功 → 更新主单状态为成功
>     ↓
> 通知业务系统
> ```
>
> **异常处理**：
>
> | 异常场景 | 处理方式 |
> |----------|----------|
> | 余额扣成功，微信支付失败 | 回滚余额，主单标记失败 |
> | 余额扣成功，微信支付超时 | 定时任务查询微信状态，确认失败则回滚余额 |
> | 微信回调成功，通知业务系统失败 | 重试通知，保证最终一致 |
>
> **面试追问**：为什么先扣余额再调外部渠道？
>
> 余额是内部操作，可以精确控制和回滚。外部渠道有不确定性（超时、失败）。先扣内部再调外部，失败时只需回滚内部。如果反过来，外部扣成功但内部扣失败，需要调用外部退款接口，增加复杂度和风险。

## 五、清算与资金流转篇

### Q11：支付清算和结算有什么区别？T+0 和 T+1 是什么？

> **深度回答**：
>
> **清算 vs 结算**：
>
> | 维度 | 清算（Clearing） | 结算（Settlement） |
> |------|-----------------|-------------------|
> | 本质 | 计算谁欠谁多少 | 实际资金划转 |
> | 时机 | 交易发生后实时/批量 | T+1 或 T+2 |
> | 参与方 | 支付网联/银联 | 商户开户行 |
> | 结果 | 清算文件（轧差后净额） | 资金到账 |
>
> **一笔回购宝支付的资金流转**：
>
> ```
> 用户（工行卡）→ 扣款100元 → 工行 → 银联/网联 → 支付宝备付金账户
>                                                           ↓
>                                              T+1 结算给商户（扣除手续费）
>                                                           ↓
>                                              商户银行账户到账99.4元（费率0.6%）
> ```
>
> **T+1 结算的含义**：
>
> | 术语 | 含义 | 示例 |
> |------|------|------|
> | T+0 | 实时到账 | 余额支付、内部转账 |
> | T+1 | 下一个工作日到账 | 大部分第三方支付 |
> | T+2 | 下两个工作日到账 | 跨境支付、高风险行业 |
>
> **为什么商户资金不实时到账？**
>
> 1. **风控缓冲**：T+1 期间可以拦截欺诈交易，资金还没划走可以原路退回
> 2. **清算周期**：银联/网联日终批量清算，不是逐笔实时
> 3. **资金成本**：沉淀资金可以赚取利息（支付公司的商业模式之一）
> 4. **合规要求**：央行要求备付金集中存管，不能随意挪用
>
> **面试追问**：网联和银联有什么区别？
>
> | 维度 | 银联 | 网联 |
> |------|------|------|
> | 定位 | 银行卡跨行清算 | 第三方支付网络清算 |
> | 接入方 | 银行 | 支付宝、微信、京东等 |
> | 交易类型 | 银行卡刷卡/转账 | 扫码支付、快捷支付、网银支付 |
> | 监管 | 央行直属 | 央行推动成立 |
>
> 2018年后，第三方支付必须通过网联/银联清算，不得直连银行（断直连）。

### Q12：分账系统怎么设计？电商平台怎么给多商户分钱？

> **深度回答**：
>
> **分账场景**：用户在平台下单买了3个店铺的商品，支付100元，平台需要分给3个商户。
>
> **分账模式对比**：
>
> | 模式 | 流程 | 优点 | 缺点 | 合规风险 |
> |------|------|------|------|----------|
> | **二清模式** | 平台收全款 → 平台分账给商户 | 灵活 | **违规** | 无支付牌照做资金清算 = 二清 |
> | **支付机构分账** | 支付机构收款 → 按指令分账给商户 | 合规 | 依赖支付机构 | 无 |
> | **银行分账** | 银行托管 → 按指令分账 | 最合规 | 灵活度低 | 无 |
>
> **推荐：支付机构分账（如微信支付分账、支付宝分账）**
>
> **分账表设计**：
> ```sql
> CREATE TABLE split_order (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     split_no VARCHAR(64) NOT NULL UNIQUE COMMENT '分账单号',
>     payment_no VARCHAR(64) NOT NULL COMMENT '原支付单号',
>     receiver_type TINYINT NOT NULL COMMENT '接收方类型：1-商户 2-个人 3-平台',
>     receiver_account VARCHAR(128) NOT NULL COMMENT '接收方账户（商户号/银行卡）',
>     split_amount DECIMAL(12,2) NOT NULL COMMENT '分账金额',
>     platform_fee DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '平台手续费',
>     split_status TINYINT NOT NULL DEFAULT 0 COMMENT '0-待分账 1-分账中 2-成功 3-失败',
>     channel_split_no VARCHAR(128) COMMENT '渠道分账流水号',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_payment_no (payment_no),
>     INDEX idx_receiver (receiver_type, receiver_account)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='分账单表';
> ```
>
> **分账流程**：
>
> ```
> 用户支付100元
>     ↓
> 资金进入平台在支付机构的待分账账户（不是平台银行账户）
>     ↓
> 平台发起分账指令：
>   - 商户A：45元（扣除平台佣金5元）
>   - 商户B：30元（扣除平台佣金3元）
>   - 商户C：20元（扣除平台佣金2元）
>   - 平台：5+3+2=10元（佣金收入）
>     ↓
> 支付机构执行分账，资金从待分账账户划转到各方
>     ↓
> 分账完成，商户资金到账
> ```
>
> **分账金额校验**：
> ```java
> /**
>  * 分账前校验：分账总额不能超过支付金额。
>  */
> public void validateSplitAmount(String paymentNo, List<SplitItem> items) {
>     PaymentOrder payment = paymentMapper.selectByPaymentNo(paymentNo);
>     BigDecimal totalSplit = items.stream()
>         .map(SplitItem::getAmount)
>         .reduce(BigDecimal.ZERO, BigDecimal::add);
>
>     // 分账总额 = 各商户金额 + 平台佣金，不能超过支付金额
>     if (totalSplit.compareTo(payment.getAmount()) > 0) {
>         throw new BizException("分账总额超过支付金额");
>     }
>
>     // 已分账金额 + 本次分账金额不能超过支付金额
>     BigDecimal alreadySplit = splitOrderMapper.getTotalSplitAmount(paymentNo);
>     if (alreadySplit.add(totalSplit).compareTo(payment.getAmount()) > 0) {
>         throw new BizException("累计分账金额超过支付金额");
>     }
> }
> ```
>
> **面试追问**：什么是二清？为什么违规？
>
> **二清**：没有支付牌照的平台，先把用户资金收到自己账户，再转给商户。本质是平台在做"清算"业务，但没有清算资质。
>
> **违规原因**：
> 1. 平台可能挪用商户资金（卷款跑路）
> 2. 资金池模式下，商户资金和平台资金混同
> 3. 央行《关于进一步加强无证经营支付业务整治的通知》明确禁止
>
> **合规方案**：资金必须通过持牌支付机构（如微信支付、支付宝、银联）进行分账，平台不触碰资金。

### Q13：备付金是什么？为什么央行要求集中存管？

> **深度回答**：
>
> **备付金定义**：用户充值到支付账户但尚未使用的资金（如支付宝余额、微信零钱）。
>
> **备付金集中存管前**：
>
> ```
> 用户充值100元 → 资金进入支付宝在各银行的备付金账户
>     ↓
> 支付宝可以：
>   - 用备付金买理财产品（赚利息）
>   - 用备付金做短期投资
>   - 把备付金存在利率高的银行（议价）
>     ↓
> 风险：如果投资亏损，用户资金可能无法取出
> ```
>
> **备付金集中存管后（2019年1月起）**：
>
> ```
> 用户充值100元 → 资金进入支付机构在央行的集中存管账户
>     ↓
> 支付机构不能：
>   - 挪用备付金
>   - 用备付金投资
>   - 自行选择存放银行
>     ↓
> 央行按0.35%利率付利息给支付机构（以前是3%-5%）
> ```
>
> **对支付公司商业模式的影响**：
>
> | 影响 | 说明 |
> |------|------|
> | 利息收入大幅下降 | 从3%-5%降到0.35%，支付宝/微信损失百亿级利息收入 |
> | 商业模式转向 | 从"吃利息"转向"收手续费"和"增值服务" |
> | 合规成本上升 | 需要建设备付金管理系统、报送系统 |
> | 用户资金更安全 | 即使支付公司倒闭，备付金也在央行，用户可取回 |
>
> **面试追问**：这对技术系统有什么影响？
>
> 1. **备付金报送系统**：每日向央行报送备付金余额、交易明细
> 2. **集中存管对账**：系统与央行存管账户逐日对账
> 3. **资金调拨**：跨行支付需要实时调拨备付金，增加系统复杂度

## 六、支付风控篇

### Q14：支付风控系统怎么设计？规则引擎怎么做？

> **深度回答**：
>
> **风控拦截点**：
>
> ```
> 用户发起支付
>     ↓
> ┌──────────────────────────────────────────┐
> │ 风控引擎                                  │
> │                                          │
> │ 1. 黑名单检查（IP/设备/卡号/手机号）      │
> │ 2. 限额检查（单笔/日累计/月累计）          │
> │ 3. 频率检查（同用户/同设备/同IP）          │
> │ 4. 规则引擎（组合条件判断）                │
> │ 5. 机器学习模型（异常行为检测）            │
> │                                          │
> │ 结果：通过 / 拒绝 / 人工审核              │
> └──────────────────────────────────────────┘
>     ↓
> 通过 → 继续支付
> 拒绝 → 返回"交易受限"
> 人工审核 → 冻结资金，等待人工处理
> ```
>
> **风控规则示例**：
>
> | 规则 | 条件 | 动作 |
> |------|------|------|
> | 大额交易 | 单笔 > 5万 | 人工审核 |
> | 高频交易 | 同用户1小时内 > 10笔 | 拒绝 |
> | 异地登录 | IP归属地与常用地址不一致 | 短信验证 |
> | 新设备支付 | 首次使用该设备 | 人脸识别 |
> | 深夜交易 | 00:00 - 06:00 且金额 > 1万 | 人工审核 |
> | 可疑卡号 | 短时间内多张卡绑定同一账户 | 拒绝 |
>
> **规则引擎实现**：
> ```java
> /**
> * 风控规则引擎，支持动态配置。
> */
> public class RiskRuleEngine {
>
>     private final List<RiskRule> rules; // 从数据库/配置中心加载
>
>     public RiskResult evaluate(RiskContext context) {
>         // 1. 黑名单检查（命中即拒绝，不继续评估）
>         if (blacklistService.isBlacklisted(context)) {
>             return RiskResult.reject("命中黑名单");
>         }
>
>         // 2. 限额检查
>         LimitResult limitResult = limitService.check(context);
>         if (!limitResult.isPass()) {
>             return RiskResult.reject("超限: " + limitResult.getReason());
>         }
>
>         // 3. 规则引擎评分
>         int riskScore = 0;
>         List<String> hitRules = new ArrayList<>();
>         for (RiskRule rule : rules) {
>             if (rule.matches(context)) {
>                 riskScore += rule.getScore();
>                 hitRules.add(rule.getRuleName());
>             }
>         }
>
>         // 4. 根据评分决策
>         if (riskScore >= 80) {
>             return RiskResult.reject("风险评分过高: " + riskScore);
>         } else if (riskScore >= 50) {
>             return RiskResult.review("需人工审核", riskScore, hitRules);
>         } else {
>             return RiskResult.pass();
>         }
>     }
> }
> ```
>
> **规则配置表**：
> ```sql
> CREATE TABLE risk_rule (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     rule_code VARCHAR(64) NOT NULL UNIQUE COMMENT '规则编码',
>     rule_name VARCHAR(128) NOT NULL COMMENT '规则名称',
>     rule_type TINYINT NOT NULL COMMENT '规则类型：1-黑名单 2-限额 3-频率 4-组合',
>     condition_expr TEXT NOT NULL COMMENT '条件表达式（JSON/SpEL）',
>     score INT NOT NULL COMMENT '命中得分',
>     action VARCHAR(32) NOT NULL COMMENT '动作：PASS/REVIEW/REJECT',
>     priority INT NOT NULL DEFAULT 0 COMMENT '优先级（数字越大越先执行）',
>     status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1-启用 0-禁用',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_status_priority (status, priority DESC)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='风控规则表';
> ```
>
> **面试追问**：规则引擎和机器学习模型怎么配合？
>
> 1. **规则引擎**处理确定性规则（黑名单、限额、频率），速度快（<10ms）
> 2. **ML模型**处理模糊场景（异常行为模式识别），需要特征工程
> 3. **决策融合**：规则引擎先过，通过的再走ML模型评分，两者加权决策
> 4. **实时反馈**：人工审核结果反馈给ML模型，持续优化

### Q15：风控中的设备指纹是什么？怎么采集？

> **深度回答**：
>
> **设备指纹**：通过采集设备的硬件、软件、网络等信息生成的唯一标识，用于识别"同一台设备"。
>
> **采集维度**：
>
> | 维度 | 信息 | 用途 |
> |------|------|------|
> | 硬件 | IMEI、MAC地址、屏幕分辨率、CPU型号 | 设备唯一标识 |
> | 软件 | 操作系统版本、浏览器版本、字体列表 | 环境特征 |
> | 网络 | IP地址、运营商、网络类型 | 地理位置 |
> | 行为 | 触摸压力、滑动速度、打字节奏 | 人机识别 |
>
> **设备指纹生成**：
>
> ```
> 采集信息 → 特征提取 → 哈希生成 → 设备指纹ID
> ```
>
> ```java
> /**
> * 设备指纹生成器，基于多维度信息生成唯一标识。
> */
> public class DeviceFingerprintGenerator {
>
>     public String generate(DeviceInfo info) {
>         StringBuilder sb = new StringBuilder();
>         // 拼接关键维度（选择稳定不变的维度）
>         sb.append(info.getImei() != null ? info.getImei() : "");
>         sb.append("|").append(info.getMacAddress() != null ? info.getMacAddress() : "");
>         sb.append("|").append(info.getScreenWidth()).append("x").append(info.getScreenHeight());
>         sb.append("|").append(info.getOsVersion());
>         sb.append("|").append(info.getBrowserFingerprint());
>
>         // SHA-256 生成指纹ID
>         return DigestUtils.sha256Hex(sb.toString());
>     }
> }
> ```
>
> **风控应用场景**：
>
> | 场景 | 判断逻辑 |
> |------|----------|
> | 新设备支付 | 同一用户从未在该设备上支付过 |
> | 多账户同设备 | 同一设备绑定了多个用户账户（薅羊毛） |
> | 设备聚集 | 同一IP下有大量不同设备指纹（刷单） |
> | 模拟器检测 | 设备指纹特征匹配模拟器（黑产） |
>
> **面试追问**：设备指纹会变吗？怎么处理变化？
>
> 会变。恢复出厂设置、系统升级、更换零件都会改变指纹。解决方案：
> 1. **模糊匹配**：核心维度（IMEI+MAC）匹配80%即认为同一设备
> 2. **设备指纹库**：用户首次登录时绑定设备指纹，后续登录比对
> 3. **多指纹共存**：同一用户可以绑定多个设备指纹（手机+电脑+平板）

## 七、支付高可用篇

### Q16：支付系统怎么做限流和熔断？

> **深度回答**：
>
> **限流策略**：
>
> | 维度 | 阈值 | 说明 |
> |------|------|------|
> | 全局 QPS | 10000 | 支付系统总 QPS |
> | 单渠道 QPS | 3000 | 防止单渠道被打爆 |
> | 单用户 QPS | 10 | 防止单用户刷接口 |
> | 单商户 QPS | 100 | 防止单商户异常调用 |
>
> **限流算法对比**：
>
> | 算法 | 特点 | 适用场景 |
> |------|------|----------|
> | **令牌桶** | 允许突发流量 | 用户维度限流 |
> | **漏桶** | 匀速处理 | 渠道维度限流 |
> | **滑动窗口** | 精确统计 | 全局限流 |
>
> **熔断策略**：
>
> ```
> 渠道A成功率 < 90%（连续5分钟）
>     ↓
> 熔断：自动切换到渠道B
>     ↓
> 30秒后半开：试探性放行10%流量到渠道A
>     ↓
> 成功率恢复 > 95% → 关闭熔断，恢复渠道A
> 成功率仍低 → 继续熔断
> ```
>
> **熔断器实现**：
> ```java
> /**
> * 滑动窗口熔断器。
> */
> public class CircuitBreaker {
>
>     private final String channelCode;
>     private final int failureThreshold;      // 失败率阈值（%）
>     private final int slowCallThreshold;     // 慢调用率阈值（%）
>     private final long windowSizeMs;         // 窗口大小（毫秒）
>     private final long halfOpenDurationMs;   // 半开持续时间
>
>     private final AtomicReference<State> state = new AtomicReference<>(State.CLOSED);
>     private final SlidingWindowCounter counter; // 滑动窗口计数器
>
>     public enum State { CLOSED, OPEN, HALF_OPEN }
>
>     /**
>      * 判断是否允许调用。
>      */
>     public boolean allowCall() {
>         State currentState = state.get();
>         if (currentState == State.CLOSED) return true;
>         if (currentState == State.OPEN) {
>             // 检查是否可以进入半开状态
>             if (System.currentTimeMillis() - openTime > halfOpenDurationMs) {
>                 state.compareAndSet(State.OPEN, State.HALF_OPEN);
>                 return true;
>             }
>             return false;
>         }
>         if (currentState == State.HALF_OPEN) {
>             return ThreadLocalRandom.current().nextInt(100) < 10; // 放行10%
>         }
>         return false;
>     }
>
>     /**
>      * 记录调用结果。
>      */
>     public void recordResult(boolean success, long durationMs) {
>         counter.increment(success, durationMs);
>
>         if (state.get() == State.CLOSED) {
>             double failureRate = counter.getFailureRate();
>             double slowCallRate = counter.getSlowCallRate();
>             if (failureRate > failureThreshold || slowCallRate > slowCallThreshold) {
>                 state.compareAndSet(State.CLOSED, State.OPEN);
>                 openTime = System.currentTimeMillis();
>             }
>         } else if (state.get() == State.HALF_OPEN) {
>             if (!success) {
>                 state.compareAndSet(State.HALF_OPEN, State.OPEN);
>                 openTime = System.currentTimeMillis();
>             }
>             // 半开状态下连续成功N次，关闭熔断
>         }
>     }
> }
> ```
>
> **面试追问**：熔断后支付请求怎么处理？
>
> 1. **渠道路由降级**：自动切换到备用渠道
> 2. **排队等待**：熔断期间请求进入队列，恢复后处理
> 3. **快速失败**：直接返回"系统繁忙，请稍后重试"
> 4. **异步通知**：告诉用户"支付处理中"，后台异步处理

### Q17：支付系统怎么做容灾？双活怎么设计？

> **深度回答**：
>
> **容灾架构**：
>
> ```
> ┌─────────────────────────────────────────────────────────┐
> │                    同城双活                              │
> │                                                         │
> │  机房A（主）                    机房B（备）              │
> │  ┌──────────┐                 ┌──────────┐             │
> │  │ 支付服务  │ ←── 数据同步 ──→│ 支付服务  │             │
> │  │ 数据库主  │ ←── 主从复制 ──→│ 数据库从  │             │
> │  │ Redis主   │ ←── 哨兵同步 ──→│ Redis从   │             │
> │  └──────────┘                 └──────────┘             │
> │       ↑                            ↑                    │
> │       └────── F5 负载均衡 ──────────┘                    │
> └─────────────────────────────────────────────────────────┘
>                          ↓
> ┌─────────────────────────────────────────────────────────┐
> │                    异地灾备                              │
> │                                                         │
> │  机房C（异地灾备）                                       │
> │  ┌──────────┐                                           │
> │  │ 支付服务  │ ←── 异步复制（延迟5分钟）                 │
> │  │ 数据库从  │                                           │
> │  └──────────┘                                           │
> └─────────────────────────────────────────────────────────┘
> ```
>
> **RPO/RTO 指标**：
>
> | 指标 | 同城双活 | 异地灾备 |
> |------|----------|----------|
> | RPO（数据丢失量） | 0 | < 5分钟 |
> | RTO（恢复时间） | < 30秒 | < 30分钟 |
>
> **数据库双活方案**：
>
> ```
> 机房A数据库 ←── 双向同步 ──→ 机房B数据库
> ```
>
> **关键问题：如何避免双写冲突？**
>
> | 方案 | 实现 | 适用场景 |
> |------|------|----------|
> | **分片路由** | 用户ID奇数走A，偶数走B | 用户维度操作 |
> | **全局锁** | 分布式锁保证同一条记录只在一个机房写 | 强一致场景 |
> | **最终一致** | 双写+冲突检测+补偿 | 允许短暂不一致 |
>
> **支付系统推荐**：分片路由 + 单边写入
>
> ```java
> /**
> * 根据用户ID路由到对应机房。
> */
> public String routeToDatacenter(long userId) {
>     // 用户ID哈希取模，固定路由到一个机房
>     return (userId % 2 == 0) ? "DC_A" : "DC_B";
> }
> // 该用户的所有支付操作都路由到同一机房，避免双写冲突
> ```
>
> **面试追问**：机房A挂了，机房B怎么接管？
>
> 1. F5 检测到机房A不可用，自动将流量切到机房B
> 2. 机房B的数据库从库提升为主库
> 3. 支付系统检测到主库变更，自动切换数据源
> 4. 切换期间的支付请求（在途交易）通过对账机制补偿

## 八、合规与安全篇

### Q18：支付系统有哪些安全要求？PCI-DSS 是什么？

> **深度回答**：
>
> **PCI-DSS（支付卡行业数据安全标准）**：
>
> | 要求 | 说明 | 技术实现 |
> |------|------|----------|
> | 持卡人数据加密 | 卡号、有效期、CVV 必须加密存储 | AES-256 加密，密钥独立管理 |
> | 传输加密 | 数据传输必须 TLS 1.2+ | HTTPS 强制，证书固定 |
> | 访问控制 | 敏感数据访问需要权限控制 | RBAC + 数据脱敏 |
> | 安全审计 | 所有访问敏感数据的操作必须记录 | 审计日志，不可篡改 |
> | 漏洞管理 | 定期扫描和修复安全漏洞 | SAST/DAST 工具 |
>
> **敏感数据处理**：
>
> ```java
> /**
> * 敏感数据脱敏工具。
> */
> public class SensitiveDataMasker {
>
>     /**
>      * 卡号脱敏：只显示前6后4。
>      * 6225881234567890 → 622588******7890
>      */
>     public static String maskCardNo(String cardNo) {
>         if (cardNo == null || cardNo.length() < 8) return "****";
>         return cardNo.substring(0, 6) + "******" + cardNo.substring(cardNo.length() - 4);
>     }
>
>     /**
>      * 手机号脱敏。
>      * 13812345678 → 138****5678
>      */
>     public static String maskPhone(String phone) {
>         if (phone == null || phone.length() != 11) return "****";
>         return phone.substring(0, 3) + "****" + phone.substring(7);
>     }
> }
> ```
>
> **面试追问**：卡号能存数据库吗？
>
> 可以，但必须满足PCI-DSS要求：
> 1. 存储时AES加密
> 2. 查询时解密，返回时脱敏
> 3. 密钥不能和数据存在同一数据库
> 4. 定期轮换密钥
> 5. 访问日志审计

### Q19：支付接口怎么做防重放攻击？

> **深度回答**：
>
> **重放攻击**：攻击者截获合法请求，重复发送（如重复扣款）。
>
> **防重放三要素**：
>
> | 要素 | 作用 | 实现 |
> |------|------|------|
> | **时间戳** | 限制请求有效期 | 请求时间与服务器时间差 < 5分钟 |
> | **随机数（Nonce）** | 保证请求唯一 | 每次请求生成唯一随机数，服务器缓存 |
> | **签名** | 防止篡改 | HMAC-SHA256 签名 |
>
> **防重放实现**：
>
> ```java
> /**
> * 支付请求防重放校验。
> */
> public class AntiReplayValidator {
>
>     private final RedisTemplate<String, String> redis;
>
>     /**
>      * 校验请求是否为重放攻击。
>      */
>     public void validate(PaymentRequest request) {
>         // 1. 时间戳校验（5分钟有效期）
>         long requestTime = request.getTimestamp();
>         long currentTime = System.currentTimeMillis();
>         if (Math.abs(currentTime - requestTime) > 5 * 60 * 1000) {
>             throw new BizException("请求已过期");
>         }
>
>         // 2. Nonce 校验（唯一性）
>         String nonce = request.getNonce();
>         String nonceKey = "payment:nonce:" + nonce;
>         Boolean isNew = redis.opsForValue().setIfAbsent(nonceKey, "1", 10, TimeUnit.MINUTES);
>         if (!Boolean.TRUE.equals(isNew)) {
>             throw new BizException("重复请求");
>         }
>
>         // 3. 签名校验
>         String expectedSign = sign(request);
>         if (!expectedSign.equals(request.getSignature())) {
>             throw new BizException("签名错误");
>         }
>     }
>
>     /**
>      * 生成签名：将参数按字母排序拼接后 HMAC-SHA256。
>      */
>     private String sign(PaymentRequest request) {
>         StringBuilder sb = new StringBuilder();
>         sb.append("amount=").append(request.getAmount());
>         sb.append("&nonce=").append(request.getNonce());
>         sb.append("&payment_no=").append(request.getPaymentNo());
>         sb.append("&timestamp=").append(request.getTimestamp());
>         sb.append("&key=").append(request.getSecretKey());
>
>         return HmacUtils.hmacSha256Hex(request.getSecretKey(), sb.toString());
>     }
> }
> ```
>
> **面试追问**：幂等和防重放有什么区别？
>
> | 维度 | 幂等 | 防重放 |
> |------|------|--------|
> | 防护层 | 业务层 | 协议层 |
> | 目标 | 重复请求返回同一结果 | 阻止重复请求到达业务层 |
> | 实现 | 数据库唯一约束、乐观锁 | 时间戳+Nonce+签名 |
> | 关系 | 互补 | 互补 |
>
> 防重放是第一道防线（协议层拦截），幂等是第二道防线（业务层兜底）。

### Q20：提现接口怎么设计？银行卡提现的资金流转是什么？

> **深度回答**：
>
> **提现全流程**：
>
> ```
> 用户发起提现100元
>     ↓
> 1. 风控校验（限额、频率、黑名单）
>     ↓
> 2. 冻结余额（available -= 100, frozen += 100）
>     ↓
> 3. 创建提现单（状态：处理中）
>     ↓
> 4. 调用支付渠道提现接口（代付到银行卡）
>     ↓
> 5. 渠道异步回调
>     ↓
> 成功 → 冻结扣减（frozen -= 100），通知用户
> 失败 → 冻结释放（frozen -= 100, available += 100），通知用户
> 超时 → 定时任务查询渠道状态，确认后处理
> ```
>
> **提现单表设计**：
> ```sql
> CREATE TABLE withdraw_order (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     withdraw_no VARCHAR(64) NOT NULL UNIQUE COMMENT '提现单号',
>     user_id BIGINT NOT NULL COMMENT '用户ID',
>     amount DECIMAL(12,2) NOT NULL COMMENT '提现金额',
>     fee DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '手续费',
>     actual_amount DECIMAL(12,2) NOT NULL COMMENT '实际到账金额 = amount - fee',
>     bank_code VARCHAR(32) NOT NULL COMMENT '银行编码',
>     bank_account_no VARCHAR(64) NOT NULL COMMENT '银行卡号（加密存储）',
>     bank_account_name VARCHAR(64) NOT NULL COMMENT '持卡人姓名',
>     channel_code VARCHAR(32) COMMENT '提现渠道',
>     channel_withdraw_no VARCHAR(128) COMMENT '渠道提现流水号',
>     status TINYINT NOT NULL DEFAULT 0 COMMENT '0-待处理 1-处理中 2-成功 3-失败 4-已退回',
>     fail_reason VARCHAR(256) COMMENT '失败原因',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_user_id (user_id),
>     INDEX idx_status (status),
>     INDEX idx_create_time (create_time)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='提现单表';
> ```
>
> **提现资金流转**：
>
> ```
> 用户余额账户（冻结100元）
>     ↓
> 平台在支付机构的备付金账户（-100元）
>     ↓
> 支付机构代付到用户银行卡
>     ↓
> 银行入账（到账99元，扣除1元手续费）
> ```
>
> **面试追问**：提现到银行卡失败，钱去哪了？
>
> 1. **渠道侧失败**：资金未划出，平台解冻即可
> 2. **银行退票**（卡号错误、账户冻结）：资金原路退回平台备付金账户，平台解冻用户余额
> 3. **在途挂起**：资金在银行间清算中，需要等待清算结果再处理
>
> 关键：提现失败不能直接把钱还给用户，必须先确认资金状态。资金确认回来前，保持冻结状态。

## 九、设计思想篇

### Q21：支付系统的核心设计思想是什么？

> **深度回答**：
>
> **六个核心思想**：
>
> | 思想 | 说明 | 实践 |
> |------|------|------|
> | **资金安全第一** | 任何功能设计都不能牺牲资金安全 | 多重校验、对账、限额 |
> | **幂等设计** | 所有接口必须幂等 | 唯一约束、乐观锁、状态机 |
> | **异步解耦** | 支付与业务异步解耦 | MQ通知、最终一致性 |
> | **渠道抽象** | 统一渠道接口，屏蔽差异 | 适配器模式、注册中心 |
> | **可追溯** | 每笔交易全链路可追溯 | traceId、审计日志 |
> | **对账兜底** | 所有不一致通过对账发现和修复 | 日终对账、差异处理 |
>
> **架构设计原则**：
>
> ```
> 1. 核心系统不直接暴露外部
> 2. 银行对接统一走渠道层
> 3. 资金操作必须有审计日志
> 4. 敏感数据加密存储和传输
> 5. 所有资金操作必须有对账机制
> ```
>
> **面试追问**：如果让你从零设计一个支付系统，你会怎么做？
>
> 1. **第一步：理清业务**——支付方式、资金流转、对账需求
> 2. **第二步：设计模型**——支付单、退款单、分账单、对账单
> 3. **第三步：设计渠道层**——统一接口、适配器模式
> 4. **第四步：设计安全层**——签名验签、幂等、防重放
> 5. **第五步：设计对账**——日终对账、差异处理
> 6. **第六步：设计监控**——成功率、耗时、渠道健康度
> 7. **第七步：设计容灾**——双活、熔断、限流

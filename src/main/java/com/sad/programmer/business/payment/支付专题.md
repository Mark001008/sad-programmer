# 支付专题

> 适用场景：支付中台、收银台、聚合支付、金融核心
> 核心考点：渠道路由、幂等回调、对账机制、退款设计、资金安全、防重放

---

## 一、支付架构篇

### Q1：支付系统的整体架构是怎样的？

> **深度回答**：
>
> **五层架构**：
>
> ```
> ┌──────────────────────────────────────────────────────────┐
> │                     业务接入层                             │
> │  电商订单 │ 充值订单 │ 生活缴费 │ 转账 │ 提现            │
> └──────────────────────────────────────────────────────────┘
>          ↓
> ┌──────────────────────────────────────────────────────────┐
> │                     收银台层                              │
> │  支付方式选择 │ 优惠展示 │ 支付密码 │ 风控校验            │
> └──────────────────────────────────────────────────────────┘
>          ↓
> ┌──────────────────────────────────────────────────────────┐
> │                   支付网关层                              │
> │  签名验签 │ 加解密 │ 幂等校验 │ 风控拦截 │ 流量控制       │
> └──────────────────────────────────────────────────────────┘
>          ↓
> ┌──────────────────────────────────────────────────────────┐
> │                   支付引擎层                              │
> │  渠道路由 │ 支付执行 │ 异步回调 │ 退款 │ 对账            │
> └──────────────────────────────────────────────────────────┘
>          ↓
> ┌──────────────────────────────────────────────────────────┐
> │                   渠道适配层                              │
> │  支付宝适配 │ 微信适配 │ 银联适配 │ 网银适配 │ 虚拟支付    │
> └──────────────────────────────────────────────────────────┘
> ```
>
> **核心设计原则**：
>
> | 原则 | 说明 |
> |------|------|
> | **幂等** | 所有接口幂等，重复调用返回同一结果 |
> | **一致** | 支付状态与业务订单状态最终一致 |
> | **安全** | 敏感信息加密传输，防重放、防篡改 |
> | **可追溯** | 全链路 traceId，每笔交易可追溯 |
> | **对账** | 日终对账，差异自动处理 |
>
> **面试追问**：为什么要分收银台和支付引擎？
>
> 收银台关注用户体验（展示支付方式、优惠信息），支付引擎关注资金安全（幂等、对账、风控）。职责分离后，收银台可以独立迭代 UI，支付引擎可以独立扩展渠道。

### Q2：支付单和订单是什么关系？为什么需要独立的支付单？

> **深度回答**：
>
> **支付单 vs 订单**：
>
> | 维度 | 订单（Order） | 支付单（Payment） |
> |------|--------------|-------------------|
> | 关注点 | 商品交易 | 资金流转 |
> | 归属 | 业务系统 | 支付系统 |
> | 生命周期 | 下单→发货→收货→完成 | 创建→支付→回调→对账 |
> | 金额 | 商品金额（含优惠） | 实际支付金额 |
> | 状态 | 待支付/已支付/已取消 | 待支付/支付中/成功/失败 |
>
> **为什么不直接在订单上记录支付信息？**
>
> 1. **职责分离**：订单关注商品交易，支付关注资金流转，耦合后改支付逻辑要改订单表
> 2. **一单多付**：部分场景一个订单分多次支付（分期付款、组合支付）
> 3. **支付重试**：同一订单可以发起多次支付（前一次失败），每次生成新的支付单
> 4. **对账独立**：支付系统独立对账，不依赖订单系统
>
> **支付单表设计**：
> ```sql
> CREATE TABLE payment_order (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     payment_no VARCHAR(64) NOT NULL UNIQUE COMMENT '支付单号（幂等键）',
>     biz_order_no VARCHAR(64) NOT NULL COMMENT '业务订单号',
>     biz_type VARCHAR(32) NOT NULL COMMENT '业务类型：ORDER/RECHARGE/TRANSFER',
>     user_id BIGINT NOT NULL COMMENT '支付用户ID',
>     amount DECIMAL(12,2) NOT NULL COMMENT '支付金额',
>     currency VARCHAR(3) NOT NULL DEFAULT 'CNY' COMMENT '币种',
>     payment_method VARCHAR(32) NOT NULL COMMENT '支付方式：ALIPAY/WECHAT/UNIONPAY/BALANCE',
>     channel_code VARCHAR(32) COMMENT '支付渠道编码',
>     channel_payment_no VARCHAR(128) COMMENT '渠道支付流水号（回调时回填）',
>     payment_status TINYINT NOT NULL DEFAULT 0 COMMENT '0-待支付 1-支付中 2-成功 3-失败 4-已关闭',
>     pay_time DATETIME COMMENT '支付成功时间',
>     expire_time DATETIME COMMENT '支付截止时间',
>     notify_url VARCHAR(256) NOT NULL COMMENT '异步回调地址',
>     return_url VARCHAR(256) COMMENT '同步跳转地址',
>     extra_params JSON COMMENT '扩展参数',
>     version INT NOT NULL DEFAULT 0,
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_biz_order_no (biz_order_no),
>     INDEX idx_user_id (user_id),
>     INDEX idx_payment_status (payment_status),
>     INDEX idx_create_time (create_time)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='支付单表';
> ```
>
> **面试追问**：biz_order_no 为什么不设唯一约束？
>
> 同一业务订单可能发起多次支付（前一次失败重试），每次生成新的 payment_no。biz_order_no 是多对一关系，不能唯一。

## 二、渠道路由篇

### Q3：支付渠道路由怎么设计？

> **深度回答**：
>
> **渠道路由**：根据规则自动选择最优支付渠道。
>
> **路由规则**：
>
> | 维度 | 规则 | 示例 |
> |------|------|------|
> | **支付方式** | 用户选择的支付方式 | 微信支付 → 微信直连/微信银联 |
> | **金额区间** | 不同金额走不同渠道 | < 5万走快捷，≥ 5万走网银 |
> | **银行** | 用户绑定的银行卡 | 工商银行 → 工行直连/银联 |
> | **成功率** | 优先选成功率高的渠道 | 渠道A成功率99%，渠道B 95% → 选A |
> | **成本** | 优先选费率低的渠道 | 渠道A费率0.6%，渠道B 0.38% → 选B |
> | **权重** | 运营配置的权重 | A:B = 7:3，按权重随机 |
>
> **路由引擎实现**：
> ```java
> /**
> * 支付渠道路由引擎，按优先级链式匹配。
> */
> public class ChannelRouter {
>
>     private final List<RouteRule> rules; // 按优先级排序
>
>     public ChannelRouteResult route(PaymentContext context) {
>         List<ChannelCandidate> candidates = loadCandidates(context);
>
>         for (RouteRule rule : rules) {
>             candidates = rule.filter(candidates, context);
>             if (candidates.size() == 1) break; // 唯一确定
>         }
>
>         if (candidates.isEmpty()) {
>             throw new NoAvailableChannelException("无可用渠道");
>         }
>
>         // 多个候选时按权重随机
>         return weightedRandom(candidates);
>     }
> }
>
> /**
> * 渠道候选（从数据库加载，支持动态配置）。
> */
> public class ChannelCandidate {
>     private String channelCode;      // 渠道编码
>     private String channelName;      // 渠道名称
>     private BigDecimal feeRate;      // 费率
>     private BigDecimal successRate;  // 最近1小时成功率
>     private int weight;              // 权重
>     private boolean enabled;         // 是否启用
> }
> ```
>
> **渠道降级**：
> ```
> 主渠道（微信直连）→ 备用渠道1（微信银联）→ 备用渠道2（微信银行）
> ```
> 主渠道失败时自动切换到备用渠道，对用户无感。
>
> **面试追问**：渠道成功率怎么统计？
>
> 滑动窗口统计：每分钟统计该渠道的成功率，存入 Redis。路由时读取最近 5 分钟的加权平均成功率。成功率低于阈值（如 90%）自动降级。

### Q4：支付渠道适配层怎么设计？怎么统一不同渠道的接口差异？

> **深度回答**：
>
> **适配器模式**：
>
> ```java
> /**
> * 渠道适配器接口，所有渠道实现此接口。
> */
> public interface ChannelAdapter {
>
>     /** 渠道编码 */
>     String getChannelCode();
>
>     /** 创建支付（返回渠道侧的支付链接/参数） */
>     ChannelPayResult createPayment(ChannelPayRequest request);
>
>     /** 查询支付状态 */
>     ChannelQueryResult queryPayment(String channelPaymentNo);
>
>     /** 发起退款 */
>     ChannelRefundResult refund(ChannelRefundRequest request);
>
>     /** 查询退款状态 */
>     ChannelRefundQueryResult queryRefund(String channelRefundNo);
>
>     /** 验签回调 */
>     boolean verifyNotify(Map<String, String> params, String signature);
> }
>
> /**
> * 支付宝适配器。
> */
> public class AlipayChannelAdapter implements ChannelAdapter {
>
>     @Override
>     public String getChannelCode() { return "ALIPAY"; }
>
>     @Override
>     public ChannelPayResult createPayment(ChannelPayRequest request) {
>         // 调用支付宝 SDK
>         AlipayTradePayRequest alipayReq = new AlipayTradePayRequest();
>         alipayReq.setTotalAmount(request.getAmount().toString());
>         alipayReq.setSubject(request.getSubject());
>         // ... 其他参数映射
>
>         AlipayTradePayResponse response = alipayClient.execute(alipayReq);
>         // 转换为统一结果
>         return ChannelPayResult.builder()
>             .channelPaymentNo(response.getTradeNo())
>             .payUrl(response.getQrCode())
>             .status(mapStatus(response.getTradeStatus()))
>             .build();
>     }
> }
> ```
>
> **渠道注册表**：
> ```java
> /**
> * 渠道适配器注册中心，启动时自动扫描注册。
> */
> @Component
> public class ChannelAdapterRegistry {
>
>     private final Map<String, ChannelAdapter> adapters = new ConcurrentHashMap<>();
>
>     @Autowired
>     public ChannelAdapterRegistry(List<ChannelAdapter> adapterList) {
>         for (ChannelAdapter adapter : adapterList) {
>             adapters.put(adapter.getChannelCode(), adapter);
>         }
>     }
>
>     public ChannelAdapter getAdapter(String channelCode) {
>         ChannelAdapter adapter = adapters.get(channelCode);
>         if (adapter == null) throw new IllegalArgumentException("未知渠道: " + channelCode);
>         return adapter;
>     }
> }
> ```
>
> **面试追问**：新增一个支付渠道需要改多少代码？
>
> 只需新增一个 `XxxChannelAdapter` 实现类，加上 `@Component` 注解，自动注册到注册中心。支付引擎、对账、退款等上层逻辑零修改。这就是适配器模式的价值。

## 三、支付流程篇

### Q5：支付回调怎么保证幂等？重复通知怎么处理？

> **深度回答**：
>
> **三层幂等保障**：
>
> ```
> 渠道回调（可能重复）
>     ↓
> 1. 签名验证（防伪造）
>     ↓
> 2. 幂等检查（Redis + 数据库双重校验）
>     ↓
> 3. 状态机控制（只处理合法状态变更）
> ```
>
> **幂等实现**：
> ```java
> @Transactional
> public PaymentNotifyResult handleNotify(PaymentNotifyRequest request) {
>     // 1. 验签
>     ChannelAdapter adapter = adapterRegistry.getAdapter(request.getChannelCode());
>     if (!adapter.verifyNotify(request.getParams(), request.getSignature())) {
>         return PaymentNotifyResult.fail("验签失败");
>     }
>
>     // 2. 查询支付单
>     PaymentOrder payment = paymentMapper.selectByPaymentNo(request.getPaymentNo());
>     if (payment == null) {
>         return PaymentNotifyResult.fail("支付单不存在");
>     }
>
>     // 3. 幂等检查：已成功则直接返回成功
>     if (payment.getPaymentStatus() == PaymentStatus.SUCCESS) {
>         return PaymentNotifyResult.success("已处理");
>     }
>
>     // 4. 状态机校验：只有待支付/支付中才能变更为成功
>     if (payment.getPaymentStatus() != PaymentStatus.PENDING
>         && payment.getPaymentStatus() != PaymentStatus.PROCESSING) {
>         return PaymentNotifyResult.fail("状态不允许: " + payment.getPaymentStatus());
>     }
>
>     // 5. 更新支付单状态（乐观锁）
>     int rows = paymentMapper.updateStatus(
>         payment.getPaymentNo(),
>         PaymentStatus.SUCCESS,        // 目标状态
>         payment.getPaymentStatus(),    // 当前状态
>         request.getChannelPaymentNo(), // 渠道流水号
>         payment.getVersion()
>     );
>     if (rows == 0) {
>         return PaymentNotifyResult.success("并发处理，已成功"); // 并发场景，乐观锁失败
>     }
>
>     // 6. 通知业务系统（异步）
>     mqProducer.send("payment.success", new PaymentSuccessEvent(
>         payment.getPaymentNo(),
>         payment.getBizOrderNo(),
>         payment.getAmount()
>     ));
>
>     return PaymentNotifyResult.success("处理成功");
> }
> ```
>
> **关键设计点**：
>
> | 设计点 | 方案 | 原因 |
> |--------|------|------|
> | 验签 | RSA/MD5 签名验证 | 防止伪造回调 |
> | 幂等检查 | 先查状态再更新 | 已成功直接返回 |
> | 乐观锁 | version + 状态条件 | 防止并发重复处理 |
> | 异步通知 | MQ 异步解耦 | 支付系统快速响应渠道 |
>
> **面试追问**：渠道要求回调必须返回特定格式，否则会重试怎么办？
>
> 支付系统收到回调后，先落库（防丢失），然后快速返回渠道要求的成功响应，再异步处理业务逻辑。如果业务逻辑失败（如通知订单系统失败），有定时任务重试。

### Q6：支付超时怎么处理？

> **深度回答**：
>
> **超时场景**：
>
> | 场景 | 处理方式 |
> |------|----------|
> | 用户未完成支付 | 支付单超时关闭，释放库存 |
> | 渠道长时间未回调 | 主动查询渠道状态 |
> | 渠道返回处理中 | 轮询查询直到终态 |
>
> **超时处理流程**：
>
> ```java
> /**
> * 支付超时处理任务。
> */
> @Scheduled(fixedDelay = 60000) // 每分钟执行
> public void handlePaymentTimeout() {
>     // 1. 查询已超时的支付单
>     List<PaymentOrder> expiredPayments = paymentMapper.selectExpired(
>         PaymentStatus.PENDING,
>         LocalDateTime.now().minusMinutes(30),
>         100 // 每批100条
>     );
>
>     for (PaymentOrder payment : expiredPayments) {
>         try {
>             // 2. 先查询渠道确认最终状态
>             ChannelAdapter adapter = adapterRegistry.getAdapter(payment.getChannelCode());
>             ChannelQueryResult result = adapter.queryPayment(payment.getPaymentNo());
>
>             if (result.isSuccess()) {
>                 // 渠道侧已成功，补发回调
>                 handleNotify(buildNotifyFromQuery(result));
>             } else if (result.isProcessing()) {
>                 // 仍在处理中，延长超时时间
>                 paymentMapper.extendExpireTime(payment.getPaymentNo(), 10);
>             } else {
>                 // 确认失败或未支付，关闭支付单
>                 closePayment(payment.getPaymentNo(), "超时关闭");
>             }
>         } catch (Exception e) {
>             log.error("处理支付超时异常: {}", payment.getPaymentNo(), e);
>             // 异常不阻塞，下次重试
>         }
>     }
> }
> ```
>
> **面试追问**：为什么要先查询渠道再关闭？
>
> 防止"渠道已成功但回调丢失"的场景。如果直接关闭，用户付了钱但订单被取消，造成资损。先查渠道确认真实状态，再做相应处理。

## 四、对账机制篇

### Q7：支付对账怎么做？差异怎么处理？

> **深度回答**：
>
> **对账流程**：
>
> ```
> 日终对账任务（T+1 凌晨 2:00 触发）
>     ↓
> 下载渠道对账文件（支付宝/微信/银联）
>     ↓
> 解析对账文件 → 渠道侧账单明细
>     ↓
> 拉取本地支付记录（T日成功/退款）
>     ↓
> 逐笔比对（金额、状态、时间）
>     ↓
> 输出对账结果：
>   ├── 一致（正常）
>   ├── 本地有渠道无（长款 → 人工确认）
>   ├── 本地无渠道有（短款 → 补单/退款）
>   └── 金额不一致（差异 → 人工处理）
> ```
>
> **对账表设计**：
> ```sql
> CREATE TABLE reconciliation_record (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     recon_date DATE NOT NULL COMMENT '对账日期',
>     channel_code VARCHAR(32) NOT NULL COMMENT '渠道编码',
>     payment_no VARCHAR(64) COMMENT '本地支付单号',
>     channel_payment_no VARCHAR(128) COMMENT '渠道流水号',
>     local_amount DECIMAL(12,2) COMMENT '本地金额',
>     channel_amount DECIMAL(12,2) COMMENT '渠道金额',
>     recon_result TINYINT NOT NULL COMMENT '对账结果：1-一致 2-长款 3-短款 4-金额不一致',
>     handle_status TINYINT NOT NULL DEFAULT 0 COMMENT '处理状态：0-待处理 1-已处理 2-忽略',
>     handle_remark VARCHAR(512) COMMENT '处理说明',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     INDEX idx_recon_date_channel (recon_date, channel_code),
>     INDEX idx_recon_result (recon_result)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='对账记录表';
> ```
>
> **差异处理策略**：
>
> | 差异类型 | 原因 | 处理方式 |
> |----------|------|----------|
> | **长款**（本地有，渠道无） | 渠道对账文件延迟、渠道漏报 | T+1 再对一次，仍存在则人工确认 |
> | **短款**（本地无，渠道有） | 回调丢失、本地未记录 | 补单：根据渠道流水号创建本地记录，通知业务系统 |
> | **金额不一致** | 手续费计算差异、汇率差异 | 核对手续费，差异金额一般在1分钱内（精度问题） |
>
> **面试追问**：对账文件下载失败怎么办？
>
> 1. 重试3次，每次间隔5分钟
> 2. 仍失败则告警，人工介入
> 3. 支持手动上传对账文件补对
> 4. 对账任务幂等，重复执行只覆盖不重复

### Q8：资金安全怎么保证？怎么防止资金损失？

> **深度回答**：
>
> **资金安全七道防线**：
>
> ```
> ┌────────────────────────────────────────────────────────────┐
> │ 1. 签名验签：防止请求伪造                                   │
> │ 2. 金额校验：服务端计算，不信任前端                          │
> │ 3. 幂等控制：防止重复扣款                                    │
> │ 4. 状态机：防止非法状态变更                                  │
> │ 5. 对账：发现不一致                                          │
> │ 6. 限额：单笔/日累计/月累计限额                              │
> │ 7. 风控：异常交易拦截                                        │
> └────────────────────────────────────────────────────────────┘
> ```
>
> **金额校验链**：
>
> ```java
> /**
> * 支付前金额校验，四重验证。
> */
> public void validateAmount(PaymentOrder payment, BigDecimal requestAmount) {
>     // 1. 支付单金额 == 请求金额
>     if (payment.getAmount().compareTo(requestAmount) != 0) {
>         throw new BizException("支付单金额不匹配");
>     }
>
>     // 2. 支付单金额 == 业务订单金额（从订单系统查询）
>     BigDecimal orderAmount = orderService.getPayableAmount(payment.getBizOrderNo());
>     if (payment.getAmount().compareTo(orderAmount) != 0) {
>         throw new BizException("订单金额不匹配");
>     }
>
>     // 3. 回调金额 == 支付单金额（渠道回调时校验）
>     // 在 handleNotify 方法中校验
>
>     // 4. 退款累计金额 <= 支付金额（退款时校验）
>     BigDecimal totalRefund = refundService.getTotalRefundAmount(payment.getPaymentNo());
>     if (totalRefund.compareTo(payment.getAmount()) > 0) {
>         throw new BizException("退款金额超过支付金额");
>     }
> }
> ```
>
> **限额设计**：
> ```sql
> CREATE TABLE payment_limit (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     user_id BIGINT NOT NULL COMMENT '用户ID',
>     limit_type TINYINT NOT NULL COMMENT '限额类型：1-单笔 2-日累计 3-月累计',
>     max_amount DECIMAL(12,2) NOT NULL COMMENT '限额金额',
>     used_amount DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '已用额度',
>     limit_date DATE COMMENT '额度日期（日限额用）',
>     limit_month VARCHAR(7) COMMENT '额度月份（月限额用）',
>     UNIQUE KEY uk_user_type_date (user_id, limit_type, limit_date),
>     INDEX idx_user_id (user_id)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='支付限额表';
> ```
>
> **面试追问**：限额并发扣减怎么防超限？
>
> Redis 原子操作 + 数据库乐观锁兜底。
> ```lua
> -- Lua 脚本原子校验并扣减
> local used = tonumber(redis.call('GET', KEYS[1]) or '0')
> local max = tonumber(ARGV[1])
> local amount = tonumber(ARGV[2])
> if used + amount > max then
>     return 0  -- 超限
> end
> redis.call('INCRBYFLOAT', KEYS[1], amount)
> return 1
> ```

### Q9：组合支付怎么设计？

> **深度回答**：
>
> **组合支付场景**：余额 + 银行卡、优惠券 + 微信支付。
>
> **支付单拆分**：
>
> ```sql
> -- 组合支付主单
> CREATE TABLE payment_order (
>     payment_no VARCHAR(64) PRIMARY KEY,
>     total_amount DECIMAL(12,2),  -- 总支付金额 100元
>     is_combined TINYINT DEFAULT 0,  -- 是否组合支付
>     payment_status TINYINT
> );
>
> -- 组合支付明细（一个主单对应多个明细）
> CREATE TABLE payment_order_detail (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     payment_no VARCHAR(64) NOT NULL COMMENT '主支付单号',
>     detail_no VARCHAR(64) NOT NULL UNIQUE COMMENT '明细单号',
>     payment_method VARCHAR(32) NOT NULL COMMENT '支付方式：BALANCE/ALIPAY/WECHAT',
>     amount DECIMAL(12,2) NOT NULL COMMENT '该方式支付金额',
>     channel_code VARCHAR(32) COMMENT '渠道编码',
>     channel_payment_no VARCHAR(128) COMMENT '渠道流水号',
>     detail_status TINYINT NOT NULL DEFAULT 0 COMMENT '0-待支付 1-成功 2-失败',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     INDEX idx_payment_no (payment_no)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='组合支付明细表';
> ```
>
> **组合支付流程**：
>
> ```
> 用户选择：余额扣30元 + 微信付70元
>     ↓
> 创建支付主单（100元）+ 2条明细
>     ↓
> 先扣余额（内部操作，实时确认）
>     ↓
> 余额扣成功 → 再调微信支付（70元）
>     ↓
> 微信回调成功 → 更新主单状态为成功
>     ↓
> 通知业务系统
> ```
>
> **异常处理**：
>
> | 异常场景 | 处理方式 |
> |----------|----------|
> | 余额扣成功，微信支付失败 | 回滚余额，主单标记失败 |
> | 余额扣成功，微信支付超时 | 定时任务查询微信状态，确认失败则回滚余额 |
> | 微信回调成功，通知业务系统失败 | 重试通知，保证最终一致 |
>
> **面试追问**：为什么先扣余额再调外部渠道？
>
> 余额是内部操作，可以精确控制和回滚。外部渠道有不确定性（超时、失败）。先扣内部再调外部，失败时只需回滚内部。如果反过来，外部扣成功但内部扣失败，需要调用外部退款接口，增加复杂度和风险。

### Q10：支付系统的监控告警怎么做？

> **深度回答**：
>
> **监控指标体系**：
>
> | 指标 | 告警阈值 | 说明 |
> |------|----------|------|
> | 支付成功率 | < 95% | 渠道异常或系统故障 |
> | 支付耗时 P99 | > 5s | 性能劣化 |
> | 对账差异率 | > 0.1% | 渠道异常或数据问题 |
> | 退款成功率 | < 98% | 退款渠道异常 |
> | 渠道回调延迟 | > 30s | 渠道积压 |
>
> **大屏监控**：
> ```
> ┌────────────────────────────────────────────────────────┐
> │                    支付监控大屏                          │
> ├────────────────────────────────────────────────────────┤
> │ 今日支付笔数：123,456  │  今日支付金额：8,765万        │
> │ 支付成功率：99.2%      │  平均耗时：230ms              │
> │                                                      │
> │ 渠道成功率：                                       │
> │   支付宝：99.5%  微信：99.1%  银联：98.7%            │
> │                                                      │
> │ 实时告警：                                           │
> │   ⚠️ 银联渠道成功率降至97%，请关注                    │
> └────────────────────────────────────────────────────────┘
> ```
>
> **面试追问**：支付成功率怎么定义？
>
> ```
> 支付成功率 = 支付成功笔数 / 发起支付笔数
> ```
> 分子分母都不包括"用户主动取消"。只有"系统发起后失败"才算失败。否则用户犹豫取消会拉低成功率，掩盖真实问题。

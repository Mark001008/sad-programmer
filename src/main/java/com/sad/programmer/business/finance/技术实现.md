## 四、设计决策

### 6.1 为什么拆这么多微服务？

| 维度 | 单体 | 微服务 |
|------|------|--------|
| 变更影响 | 改一行代码影响全局 | 只部署变更的服务 |
| 团队协作 | 代码冲突频繁 | 各组独立开发部署 |
| 故障隔离 | 一个 OOM 全挂 | 单服务故障不影响其他 |
| 技术选型 | 统一技术栈 | 可按场景选型 |

### 6.2 为什么有产品层和核心层两层？

```
存款产品层  → 业务逻辑，变更频繁（产品规则、利率调整）
存款核心      → 账户引擎，变更少（余额计算、冻结解冻）
```

**好处**：产品层频繁迭代不影响核心层稳定性；多个产品层可共享一个核心层。

### 6.3 为什么有入向网关和出口网关？

```
入向网关    → 管"进来"的流量：鉴权、限流、路由
出口网关    → 管"出去"的流量：银行报文、签名验签
```

**好处**：流量管控和银行对接解耦，各司其职。

### 6.4 为什么选 Dubbo 而不是 Spring Cloud？

| 对比维度 | Dubbo | Spring Cloud | 选型理由 |
|----------|-------|--------------|----------|
| 通信协议 | Dubbo 协议（二进制，高性能） | HTTP/REST | 内部服务调用频繁，Dubbo 协议性能更优 |
| 序列化 | Hessian2 / Protobuf | JSON | 大数据量传输场景效率更高 |
| 服务治理 | 内置负载均衡、路由、限流 | 需要额外组件 | 原生支持，减少架构复杂度 |
| 国产化 | 阿里开源，国内生态活跃 | Netflix 开源 | 央企倾向国产化技术方案 |

### 6.5 为什么选 OceanBase 而不是 MySQL？

| 对比维度 | MySQL | OceanBase | 选型理由 |
|----------|-------|-----------|----------|
| 一致性 | 异步复制，可能丢数据 | Paxos 强一致，RPO=0 | 金融场景零数据丢失 |
| 事务 | 单机事务 | 原生分布式事务 | 跨分区转账 ACID |
| 扩展 | 手动分库分表 | 自动分片 | 无需改造应用 |
| 故障恢复 | 手动切换，RTO 分钟级 | 自动切换，RTO < 30s | 7×24 不间断 |
| 兼容性 | 原生 MySQL | MySQL 模式 100% 兼容 | MyBatis 零改造 |
| 国产化 | Oracle 旗下 | 蚂蚁集团自研 | 信创合规 |

### 6.6 为什么选 RocketMQ？

| 对比维度 | RocketMQ | Kafka | RabbitMQ | 选型理由 |
|----------|----------|-------|----------|----------|
| 事务消息 | 原生支持 | 需额外实现 | 不支持 | 金融核心需求 |
| 延迟消息 | 18 个级别 + 自定义 | 需 workaround | TTL + DLX | 资金归集定时触发 |
| 消息回溯 | 按时间回溯 | 按 offset | 不支持 | 对账重跑场景 |
| 国产化 | 阿里金融级验证 | — | — | 央企偏好国产化 |

## 五、技术栈详解

### 7.1 OceanBase

#### 核心优势

**1. 分布式事务 — 跨节点转账的基石**

```
场景：A 省电信公司向 B 省电信公司内部转账 1000 万

┌──────────────────────────────────────────────────────────────────┐
│                    OceanBase 分布式事务                           │
│                                                                  │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐          │
│  │  分区 P1     │    │  分区 P2     │    │  分区 P3     │          │
│  │ (A省账户)    │    │ (B省账户)    │    │ (交易流水)   │          │
│  │ A 账户 -1000│    │ B 账户 +1000│    │ 记录交易流水 │          │
│  └──────┬──────┘    └──────┬──────┘    └──────┬──────┘          │
│         └──────── 2PC 两阶段提交（Paxos 强一致）──────────┘         │
│                                                                  │
│  全部成功 → Commit（三节点多数派确认持久化）                        │
│  任一失败 → Rollback（三节点全部回滚）                             │
└──────────────────────────────────────────────────────────────────┘
```

**2. 强一致复制 — 零数据丢失**

```
MySQL 异步复制：
  Master 写入成功 → 返回客户端
  Master 异步复制 → Slave（可能延迟/丢失）

OceanBase Paxos 复制：
  Leader 写入 → Leader + Follower1（多数派确认）→ 返回客户端
  Leader 异步 → Follower2（最终一致）
  即使 Leader 宕机，Follower1 已有数据，可立即选主，零数据丢失
```

**3. 自动分片 — 告别分库分表**

```
传统 MySQL 分库分表：应用代码 → ShardingSphere → DB1~DB16
  问题：分片键选择困难、跨分片查询差、扩容需数据迁移

OceanBase 自动分片：应用代码 → OceanBase（MySQL 协议兼容）
  优势：应用无感知、自动负载均衡、在线扩容
```

#### 部署架构

```
┌────────────────────────────────────────────────────────────┐
│               OceanBase 集群部署架构                         │
│  Zone 1 (北京主数据中心)                                     │
│  ├── OBServer 1 (Leader for Partitions A-H)                │
│  ├── OBServer 2 (Leader for Partitions I-P)                │
│  └── OBServer 3 (Leader for Partitions Q-Z)                │
│  Zone 2 (北京同城灾备中心)                                   │
│  ├── OBServer 4 (Follower)                                 │
│  ├── OBServer 5 (Follower)                                 │
│  └── OBServer 6 (Follower)                                 │
│  资源配置：CPU 192核 / 内存 768GB / SSD 12TB / 万兆内网     │
└────────────────────────────────────────────────────────────┘
```

#### 踩坑记录

1. **分布式事务性能**：跨分区事务延迟比单分区高 3-5 倍 → 按业务维度合理分区，尽量让同一成员单位的数据在同一分区
2. **SQL 兼容性**：少数 MySQL 语法不兼容（如 `INSERT IGNORE`）→ 改用 `INSERT ... ON DUPLICATE KEY UPDATE`
3. **大事务超时**：月末批量结息事务过大导致超时 → 拆分为小批次事务 + 分片并行

### 7.2 Dubbo

#### 核心使用场景

- 业务层 → 核心层：Dubbo RPC 调用，服务注册在 Nacos
- 渠道层 → 业务层：柜面/网银通过 HTTP 网关接入，司库通过 Dubbo API 调用
- 核心层 → 基础层：本地调用（同一进程内）

#### 踩坑记录

1. **序列化问题**：Hessian2 对 BigDecimal 精度丢失 → 自定义 BigDecimal 序列化器
2. **超时配置**：不同业务场景超时时间不同 → 按接口粒度配置 `timeout`
3. **服务雪崩**：核心层故障导致业务层全部阻塞 → 熔断 + 降级 + 异步化

### 7.3 RocketMQ

#### 核心使用场景

**场景 1：资金归集指令下发（事务消息）**

```
┌──────────┐    1. 发送半消息(Half Message)    ┌──────────────┐
│ 资金归集  │ ──────────────────────────────>  │  RocketMQ    │
│   服务    │    2. 执行本地事务（更新归集状态） │  Broker      │
│          │    3. Commit / Rollback          │              │
└──────────┘                                  └──────┬───────┘
                                              4. 投递消息
                                              ┌──────┴───────┐
                                              │  银企直连     │
                                              │  网关服务     │
                                              └──────────────┘
```

**场景 2：日终批量对账（延迟消息）**

- 每日 18:00 发送延迟消息，22:00 触发对账服务执行
- 延迟级别 14 对应 2 小时延迟

**场景 3：转账状态通知（顺序消息）**

- 通过账户号的 hashCode 选择队列，保证同一账户的所有转账状态变更消息进入同一队列

#### 踩坑记录

1. **事务消息回查失败**：本地事务日志表数据丢失 → 事务日志表与业务表在同一数据库
2. **消息堆积**：日终批量处理时消费速度跟不上 → 增加消费线程数 + 消费端批量处理 + 消费组扩容
3. **消息重复**：网络抖动导致 Broker 重复投递 → 消费端幂等设计（基于业务流水号去重表）
4. **延迟消息精度不够**：预设 18 个延迟级别不满足精确时间 → 结合 XXL-JOB 精确定时

### 7.4 Redis

#### 使用场景

| 场景 | 数据结构 | Key 设计 |
|------|----------|----------|
| 余额缓存 | String | `balance:{memberId}` |
| 利率缓存 | Hash | `rate:{productType}` |
| 分布式锁 | String + SETNX | `lock:{bizType}:{bizId}` |
| 幂等控制 | String + SETNX | `idempotent:{serialNo}` |
| 头寸管理 | Hash | `position:total` |
| 防重放 | String + SETNX | `nonce:{randomStr}` |

#### 分布式锁实现

```java
String lockKey = "fund:collection:lock:" + batchId + ":" + memberId;
String requestId = UUID.randomUUID().toString();

// 获取锁（SET NX EX，原子操作）
boolean locked = redisTemplate.opsForValue()
    .setIfAbsent(lockKey, requestId, 30, TimeUnit.SECONDS);

if (!locked) {
    return false; // 已被其他实例处理
}

try {
    doCollection(batchId, memberId);
    return true;
} finally {
    // Lua 脚本释放锁（只有自己持有的锁才释放）
    String luaScript = 
        "if redis.call('get',KEYS[1]) == ARGV[1] then " +
        "  return redis.call('del',KEYS[1]) " +
        "else " +
        "  return 0 " +
        "end";
    redisTemplate.execute(
        new DefaultRedisScript<>(luaScript, Long.class),
        Collections.singletonList(lockKey),
        requestId
    );
}
```

#### 余额缓存实现

```java
// 优先从 Redis 缓存读取，缓存未命中时查询 OceanBase 并回填
String cacheKey = "account:balance:" + accountNo;
AccountBalance cached = redisTemplate.opsForValue().get(cacheKey);
if (cached != null) {
    return cached;
}
AccountBalance dbResult = accountDao.selectBalance(accountNo);
// 带随机过期时间，防止缓存雪崩
int ttl = 300 + ThreadLocalRandom.current().nextInt(60); // 300-360s
redisTemplate.opsForValue().set(cacheKey, dbResult, ttl, TimeUnit.SECONDS);
```

#### 踩坑记录

1. **缓存穿透**：查询不存在的成员单位编号 → 布隆过滤器 + 空值缓存（TTL 60s）
2. **缓存雪崩**：大量缓存同时过期 → 随机过期时间 + 热点数据永不过期 + 异步刷新
3. **大 Key 问题**：批量归集结果单个 Value 超过 10MB → 拆分为小 Key 或使用 Hash 结构
4. **集群脑裂**：网络分区导致双主写入 → 配置 `min-replicas-to-write 1` + 应用层幂等校验
5. **慢查询阻塞**：`KEYS *` 命令导致 Redis 线程阻塞 → 替换为 `SCAN` 命令分批遍历

### 7.5 XXL-JOB

#### 日终批处理编排

```
22:00 银行对账单下载（分片广播，8家银行并行）
  ↓
22:15 逐笔对账核对（依赖上一步完成）
  ↓
22:30 差异流水处理
  ↓
22:45 利息计提（存款 + 贷款并行）
  ↓
23:00 余额汇总计算
  ↓
23:15 日终报表生成
  ↓
23:30 监管数据报送
```

#### 踩坑记录

1. **分片不均匀**：部分成员单位数据量远大于其他 → 加权分片（大数据量单位分配更多分片）
2. **任务依赖**：上游任务失败导致下游数据不全 → 任务链编排 + 失败阻断 + 告警
3. **执行器宕机**：任务执行中执行器宕机 → 任务超时自动重试 + 故障转移

### 7.6 MyBatis

#### 与 OceanBase 的配合

OceanBase MySQL 模式 100% 兼容 MySQL 协议，MyBatis **零改造**即可使用：

```java
@Mapper
public interface FundFlowMapper {

    @Insert("INSERT INTO t_fund_flow (flow_id, account_no, amount, " +

            "ORDER BY create_time DESC " +

    List<FundFlow> selectByPage(@Param("accountNo") String accountNo,
                                @Param("startDate") String startDate,
                                @Param("endDate") String endDate,
                                @Param("offset") int offset,
                                @Param("limit") int limit);
}
```

## 六、生产级架构设计

### 6.1 接入链路

所有外部访问都经过统一接入链路：

```
用户/机构 → F5 负载均衡 → Nginx 反向代理 → API 网关（认证、鉴权、限流）→ 微服务应用
```

**设计原则**：
- 核心系统不直接暴露给公网或外部机构
- 所有请求必须经过统一认证、鉴权、限流和审计
- F5 负责高可用和负载均衡
- Nginx 负责反向代理和静态资源
- API 网关负责接口治理

### 6.2 服务域拆分

微服务内部按"域"拆分：

| 域 | 职责 | 对应应用 |
|------|------|----------|
| 产品层 | 业务语义编排：存款、贷款、投资、同业、票据、资金池 | 存款产品层、信贷产品层、结算产品层等 |
| 产品中台 | 产品参数、利率规则、计息规则、产品生命周期 | 产品管理与定价、产品工厂 |
| 会员域 | 成员单位管理、客户准入、权限、账户归属 | 客户核心、客户产品 |
| 资产域 | 贷款资产、票据资产、投资资产、外部资产 | 资金池核心、资产交换、外部资产 |
| 运营域 | 审批、复核、日终、运维操作、异常处理 | 工作流、渠道基础服务 |
| 公共能力 | 权限、字典、参数、通知、文件、审计 | 字典、消息中心、回单系统 |

### 6.3 双网关设计

系统区分**入向网关**和**出向通道**：

| 方向 | 组件 | 作用 |
|------|------|------|
| 入向 | 入向网关 | 承接柜面、网银、成员单位、司库 API 请求进入系统 |
| 出向 | 金融网络 | 对接银行、银企直连、外部合作机构 |
| 出向 | 网关桥 | 对接老核心、票据系统、内部系统适配 |
| 出向 | 短信平台 | 短信通知、验证码、告警 |
| 出向 | FTP/SFTP | SAP 文件、司库回单、批量对账、监管报送 |

### 6.4 数据链路

交易系统和分析系统隔离：

```
交易系统（OceanBase）
  ↓ DataX / CDC / ETL
ODS / Hive
  ↓
大数据底座
  ↓
经营分析报表 / 监管报送 / 管理驾驶舱
```

**原则**：经营分析报表不直接查核心交易库，从大数据底座取数，避免报表压交易库。

### 6.5 可观测体系

| 能力 | 工具 | 说明 |
|------|------|------|
| 链路追踪 | SkyWalking | 全链路 trace_id 串联，定位慢请求 |
| 指标监控 | VictoriaMetrics | 交易量、响应时间、错误率 |
| 日志监控 | Loki | 结构化日志检索 |
| 可视化 | Grafana | 统一仪表盘 |
| 告警 | Nightingale | 阈值告警、异常检测 |

**关键设计**：所有链路必须带 global_txn_id / trace_id，确保交易可追踪、异常可定位。

### 6.8 风险点

| 风险 | 说明 | 应对措施 |
|------|------|----------|
| 链路长排查难 | 一笔交易经过 10+ 层 | 全链路 trace_id 串联 |
| 文件交互多 | FTP/SFTP 容易漏传/重复传 | 文件批次号 + 校验和 + 状态机 + 重传机制 |
| 新老系统并存 | 同一笔业务新老状态可能不一致 | 交易号映射表 + 双轨对账 |
| 报表压交易库 | 经营分析直接查 OB | 交易库和分析库隔离，通过 DataX 同步 |

## 九、设计思想

### 9.1 新核心要具备"双网关"能力

**入向网关**：承接柜面、网银、成员单位、司库 API

**出向网关**：对接银行、SAP、短信、监管、司库、票据

### 9.2 交易类系统和分析类系统要隔离

- 交易系统用 OceanBase 支撑在线交易
- 分析系统用 Hive / 大数据底座支撑报表
- 通过 DataX / ETL 同步，避免报表压交易库

### 9.3 银行对接必须集中

- 所有银行调用统一走金融网络或支付结算核心
- 业务系统不直接连银行

## 十、架构设计原则

### 10.1 核心系统不得直接暴露

**原则**：核心系统不得直接暴露公网、成员单位网银、司库 API 或外部机构

**要求**：所有外部访问必须经过统一接入、认证、鉴权、限流、审计和报文转换

### 10.2 金融网络是银行类交易的统一出口

**原则**：银行对接不应该分散在各业务系统里

**要求**：统一成 `业务系统 → 金融网络 / 支付结算核心 → 银行`

**适用场景**：
- 资金归集
- 资金下拨
- 代付供应商
- 贷款放款到外部账户
- 投资买入支付
- 回单获取
- 银行流水查询

### 10.3 网关桥用于新旧系统过渡

**原则**：新核心和老系统之间解耦

**要求**：
- 新核心和票据系统之间适配
- 新核心和内部其他应用之间做协议转换
- 支持系统迁移期间双轨运行

### 10.4 全链路追踪必须贯穿

**原则**：所有链路必须带 global_txn_id / trace_id

**要求**：
- 确保交易可追踪
- 异常可定位
- 数据可对账
- 系统可持续运行

## 十一、一句话总结架构价值

这两张图的核心价值，是把"业务系统架构"补充成了"真实生产级部署架构"：不仅有存款、贷款、资产、核算这些业务能力，还明确了渠道入口、网络通道、银行外联、文件交换、大数据同步、监控告警和新旧系统过渡。

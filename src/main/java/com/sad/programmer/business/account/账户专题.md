## 一、账户模型设计篇

### Q1：账户表怎么设计？可用余额和冻结余额为什么要分开？

> **深度回答**：
> 
> **表结构**：
> ```sql
> CREATE TABLE account (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     account_no VARCHAR(64) NOT NULL UNIQUE COMMENT '账户号',
>     account_type TINYINT NOT NULL COMMENT '账户类型：1-个人 2-商户 3-平台',
>     available_balance BIGINT NOT NULL DEFAULT 0 COMMENT '可用余额（分）',
>     frozen_balance BIGINT NOT NULL DEFAULT 0 COMMENT '冻结余额（分）',
>     total_balance BIGINT GENERATED ALWAYS AS (available_balance + frozen_balance) STORED COMMENT '总余额',
>     version INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
>     status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1-正常 2-冻结 3-注销',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_account_no (account_no),
>     INDEX idx_account_type (account_type)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='账户表';
> ```
> 
> **为什么可用和冻结要分开？**
> 
> | 场景 | 操作 | 影响字段 |
> |------|------|----------|
> | 用户充值 100 元 | 可用 +100 | available_balance |
> | 用户发起提现 50 元（处理中） | 可用 -50, 冻结 +50 | available -= 50, frozen += 50 |
> | 提现成功 | 冻结 -50 | frozen -= 50 |
> | 提现失败 | 冻结 -50, 可用 +50 | frozen -= 50, available += 50 |
> 
> **核心原因**：资金在"处理中"状态时，既不能被用户再次使用（所以从可用扣除），也不能真正消失（所以放入冻结）。只有最终结果确认后，才从冻结中扣除或释放。
> 
> **面试追问**：为什么不直接用一个 balance 字段，加状态流水？
> 
> 因为**查询余额的性能**。如果只有一个 balance 字段，查询可用余额需要遍历所有未完成流水计算。分开后直接读 available_balance，O(1)。

### Q2：账户流水表怎么设计？为什么金额用分不用元？

> **深度回答**：
> 
> **流水表结构**：
> ```sql
> CREATE TABLE account_transaction (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     transaction_id VARCHAR(64) NOT NULL UNIQUE COMMENT '交易流水号（幂等键）',
>     account_no VARCHAR(64) NOT NULL COMMENT '账户号',
>     opposite_account_no VARCHAR(64) COMMENT '对方账户号',
>     transaction_type TINYINT NOT NULL COMMENT '交易类型：1-充值 2-提现 3-转账入 4-转账出 5-冻结 6-解冻',
>     amount BIGINT NOT NULL COMMENT '交易金额（分），正数入账，负数出账',
>     balance_before BIGINT NOT NULL COMMENT '交易前余额',
>     balance_after BIGINT NOT NULL COMMENT '交易后余额',
>     biz_order_no VARCHAR(64) COMMENT '业务订单号',
>     remark VARCHAR(256) COMMENT '备注',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     INDEX idx_account_no (account_no),
>     INDEX idx_biz_order_no (biz_order_no),
>     INDEX idx_create_time (create_time)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='账户流水表';
> ```
> 
> **为什么金额用分不用元？**
> 
> | 类型 | 10.50 元存储 | 计算 | 问题 |
> |------|-------------|------|------|
> | FLOAT/DOUBLE | 10.5 → 10.499999... | 浮点精度丢失 | 资金计算出错，差一分钱对不上账 |
> | DECIMAL(10,2) | "10.50" 字符串 | 数据库层计算 | 精度可控，但仍有舍入风险 |
> | BIGINT（分） | 1050 | 整数运算 | **无精度问题，推荐** |
> 
> **面试追问**：balance_before 和 balance_after 有什么用？
> 
> 1. **对账**：校验 `上一条流水的 balance_after = 本条的 balance_before`
> 2. **审计**：知道交易发生时的余额快照
> 3. **排查**：发现余额异常时，逐条核对

### Q3：流水号为什么是幂等键？怎么生成？

> **深度回答**：
> 
> **为什么是幂等键？**
> 
> 同一笔业务（如同一次支付回调）可能被重复调用，流水号唯一约束保证不会重复入账：
> ```sql
> UNIQUE KEY uk_transaction_id (transaction_id)
> ```
> 重复插入时，唯一约束冲突，事务回滚，余额不变。
> 
> **流水号生成方案**：
> 
> | 方案 | 格式 | 优点 | 缺点 |
> |------|------|------|------|
> | UUID | 32位随机 | 简单 | 无序，索引性能差 |
> | 雪花算法 | 时间戳+机器ID+序列号 | 有序，可追溯 | 时钟回拨问题 |
> | 业务前缀+序列 | PAY20260727001 | 业务可读 | 需要发号器 |
> | Redis INCR | 自增ID | 简单有序 | Redis 依赖 |
> 
> **推荐**：雪花算法 + 业务前缀，兼顾有序性和可读性。
> 
> **面试追问**：雪花算法时钟回拨怎么处理？
> 
> 1. 检测到回拨时抛异常，拒绝生成 ID
> 2. 等待时钟追上后再生成
> 3. 预留一部分位作为扩展位，回拨时用扩展位补偿

## 二、并发安全篇

### Q4：转账操作怎么保证并发安全？

> **深度回答**：
> 
> **核心问题**：A 转给 B 100 元，同时 B 转给 A 100 元，两个事务同时操作两个账户，可能死锁。
> 
> **方案一：固定加锁顺序**（单机 ReentrantLock）
> ```java
> // 按账户号排序，所有线程都从小到大加锁
> TransferAccount first = from.getAccountNo().compareTo(to.getAccountNo()) < 0 ? from : to;
> TransferAccount second = first == from ? to : from;
> 
> first.lock().tryLock(timeout, unit);
> second.lock().tryLock(remainingNanos, TimeUnit.NANOSECONDS);
> ```
> 
> **方案二：数据库乐观锁**（分布式场景）
> ```sql
> -- A 账户扣款
> UPDATE account SET available_balance = available_balance - 100, version = version + 1
> WHERE account_no = 'A' AND available_balance >= 100 AND version = ?
> 
> -- B 账户入账
> UPDATE account SET available_balance = available_balance + 100, version = version + 1
> WHERE account_no = 'B' AND version = ?
> ```
> 
> **方案三：数据库悲观锁**（强一致性场景）
> ```sql
> SELECT * FROM account WHERE account_no = 'A' FOR UPDATE;
> SELECT * FROM account WHERE account_no = 'B' FOR UPDATE;
> ```
> 
> **面试追问**：分布式场景用哪种？
> 
> | 方案 | 适用场景 | 原因 |
> |------|----------|------|
> | 乐观锁 | 高并发，冲突少 | 性能好，失败重试即可 |
> | 悲观锁 | 低并发，强一致 | 阻塞等待，保证成功 |
> | 分布式锁 | 跨服务 | 需要 Redis/Zookeeper |
> 
> **面试再追问**：乐观锁重试几次？
> 
> 通常 3 次。超过 3 次失败说明冲突严重，应降级为悲观锁或异步处理。

### Q5：扣减余额时，available_balance < amount 怎么处理？

> **深度回答**：
> 
> **两种方案**：
> 
> **方案一：SQL 层面校验**
> ```sql
> UPDATE account SET available_balance = available_balance - 100
> WHERE account_no = 'A' AND available_balance >= 100;
> -- 返回 affected rows = 0 表示余额不足
> ```
> 
> **方案二：应用层先查再扣**
> ```java
> Account account = dao.findByAccountNo(conn, accountNo);
> if (account.getAvailableBalance() < amount) {
>     throw new InsufficientBalanceException();
> }
> dao.updateBalance(conn, accountNo, -amount);
> ```
> 
> **方案一更好**，原因：
> 1. **原子性**：一条 SQL 搞定，不需要先查再扣
> 2. **并发安全**：避免先查后扣的间隙被其他事务修改
> 3. **性能**：少一次网络往返
> 
> **面试追问**：如果余额不足，应该抛异常还是返回 false？
> 
> | 方式 | 适用场景 |
> |------|----------|
> | 抛异常 | 业务上不允许的情况（如转账金额超过余额） |
> | 返回 false | 竞争失败的正常情况（如秒杀库存不足） |
> 
> 余额不足是**业务校验失败**，应该抛异常让上层感知。

## 三、幂等设计篇

### Q6：支付回调重复调用，怎么保证不重复入账？

> **深度回答**：
> 
> **问题**：支付网关可能多次回调通知同一笔支付成功，每次回调都会触发入账操作。
> 
> **方案一：流水表唯一约束**
> ```java
> // 同一个 transactionId 只能插入一次
> try {
>     accountDao.insertTransaction(conn, transaction);
>     accountDao.updateBalance(conn, accountNo, amount);
>     conn.commit();
> } catch (DuplicateKeyException e) {
>     // 唯一约束冲突，说明已处理过，直接返回成功
>     conn.rollback();
>     return success();
> }
> ```
> 
> **方案二：先查后插（不推荐）**
> ```java
> // 不推荐！存在并发问题
> if (accountDao.existsTransaction(transactionId)) {
>     return success();  // 已处理
> }
> accountDao.insertTransaction(conn, transaction);  // 并发时可能重复插入
> ```
> 
> **方案二的问题**：两个并发请求同时查到不存在，然后都插入，导致重复入账。
> 
> **面试追问**：为什么方案一没有并发问题？
> 
> 因为唯一约束是数据库层面的原子操作，即使两个事务同时插入，也只有一个成功，另一个触发 DuplicateKeyException。
> 
> **面试再追问**：如果用 Redis 做幂等呢？
> ```java
> boolean firstTime = jedis.setnx(transactionId, "1");
> if (!firstTime) {
>     return success();  // 已处理
> }
> jedis.expire(transactionId, 86400);  // 24小时过期
> ```
> 
> 问题：`setnx` 和 `expire` 不是原子操作，如果 Redis 在两者之间宕机，key 永不过期。应该用 `SET key value EX 86400 NX`。

### Q7：幂等设计有哪些常见陷阱？

> **深度回答**：
> 
> **陷阱一：先查后插的并发问题**
> ```java
> // 错误！两个并发请求可能同时查到不存在
> if (exists(id)) return;
> insert(id);  // 两个都插入了
> ```
> 
> **陷阱二：幂等键不唯一**
> ```java
> // 错误！用 orderId 做幂等键，但同一订单可能有多种操作
> // 如：支付、退款、部分退款，都用同一个 orderId
> ```
> 正确做法：`orderId + operationType` 组合做幂等键。
> 
> **陷阱三：幂等检查和业务操作不在同一个事务**
> ```java
> // 错误！
> if (exists(transactionId)) return;  // 事务1
> insert(transactionId);               // 事务2
> // 两个事务之间可能被其他请求插入
> ```
> 
> **陷阱四：幂等过期时间太短**
> ```
> 支付回调可能延迟几小时甚至几天（对账补单）
> 幂等记录至少保留 7 天
> ```
> 
> **面试追问**：你们的幂等方案是什么？
> 
> 流水表唯一约束 + 事务内操作。重复请求触发 DuplicateKeyException，catch 后直接返回成功。幂等记录永久保留（流水本身就是审计数据）。

## 四、对账机制篇

### Q8：为什么需要对账？对账怎么做？

> **深度回答**：
> 
> **为什么需要对账？**
> 
> 即使有事务保证，仍可能出现数据不一致：
> 1. 网络超时：支付成功但回调丢失
> 2. 系统异常：事务提交后程序崩溃，后续操作未执行
> 3. 人工干预：运营手动修改数据
> 4. Bug：代码逻辑错误
> 
> **对账类型**：
> 
> | 类型 | 说明 | 频率 |
> |------|------|------|
> | 内部对账 | 系统内各表数据一致性 | 每小时 |
> | 外部对账 | 与第三方支付/银行对账 | 每天 |
> | 资金对账 | 账户余额 vs 流水汇总 | 每天 |
> 
> **资金对账实现**：
> ```sql
> -- 校验每个账户的余额是否等于流水汇总
> SELECT a.account_no, a.available_balance, 
>        COALESCE(SUM(t.amount), 0) AS calculated_balance
> FROM account a
> LEFT JOIN account_transaction t ON a.account_no = t.account_no
> GROUP BY a.account_no
> HAVING a.available_balance != calculated_balance;
> ```
> 
> **面试追问**：发现不一致怎么处理？
> 
> 1. **记录差异**：写入对账差异表
> 2. **自动修复**：小额差异自动调整（如差 1 分钱）
> 3. **人工介入**：大额差异告警，人工处理
> 4. **补偿流水**：生成一条补偿流水，调整余额

---

### Q9：外部对账（与银行/支付渠道）怎么做？

> **深度回答**：
> 
> **流程**：
> ```
> 1. 下载渠道对账文件（T+1）
> 2. 解析文件，生成渠道流水
> 3. 逐条比对：本地流水 vs 渠道流水
> 4. 记录差异：本地有渠道无、渠道有本地无、金额不一致
> 5. 差异处理：自动补偿或人工介入
> ```
> 
> **比对逻辑**：
> ```java
> for (ChannelTransaction channelTx : channelTransactions) {
>     LocalTransaction localTx = localMap.get(channelTx.getChannelOrderNo());
>     if (localTx == null) {
>         // 渠道有，本地无 → 可能是回调丢失，需要补单
>         recordDiff("MISSING_LOCAL", channelTx);
>     } else if (localTx.getAmount() != channelTx.getAmount()) {
>         // 金额不一致 → 异常，人工处理
>         recordDiff("AMOUNT_MISMATCH", channelTx, localTx);
>     }
>     // 匹配成功，标记已对账
> }
> 
> for (LocalTransaction localTx : unmatchedLocalTransactions) {
>     // 本地有，渠道无 → 可能是渠道未结算，等待下一天
>     recordDiff("MISSING_CHANNEL", localTx);
> }
> ```
> 
> **面试追问**：对账文件很大（几百万条），怎么处理？
> 
> 1. **分批读取**：流式读取文件，不一次性加载到内存
> 2. **多线程处理**：按账户号分片，并行比对
> 3. **增量对账**：只比对新增流水，不重复比对历史数据

## 五、事务设计篇

### Q10：扣减余额 + 插入流水，怎么保证原子性？

> **深度回答**：
> 
> **方案一：本地事务**
> ```java
> Connection conn = JdbcUtil.getConnection();
> conn.setAutoCommit(false);
> try {
>     // 1. 扣减余额
>     int affected = dao.updateBalance(conn, accountNo, -amount);
>     if (affected == 0) {
>         conn.rollback();
>         throw new InsufficientBalanceException();
>     }
>     
>     // 2. 插入流水
>     dao.insertTransaction(conn, transaction);
>     
>     conn.commit();
> } catch (Exception e) {
>     conn.rollback();
>     throw e;
> } finally {
>     JdbcUtil.close(conn);
> }
> ```
> 
> **方案二：TCC 模式**（分布式场景）
> ```
> Try:    冻结余额（available -= 100, frozen += 100）
> Confirm: 确认扣减（frozen -= 100）
> Cancel:  解冻释放（frozen -= 100, available += 100）
> ```
> 
> **面试追问**：TCC 的空回滚和悬挂怎么处理？
> 
> **空回滚**：Try 没执行，但 Cancel 先到了。
> - 处理：Cancel 时检查是否有冻结记录，没有则跳过
> 
> **悬挂**：Cancel 先执行，Try 后到达。
> - 处理：Cancel 时记录已回滚标记，Try 到达时检查标记，跳过执行
> 
> **面试再追问**：什么场景用 TCC，什么场景用本地事务？
> 
> | 场景 | 方案 | 原因 |
> |------|------|------|
> | 单库操作 | 本地事务 | 简单高效 |
> | 跨库/跨服务 | TCC | 无法用本地事务 |
> | 跨多个服务 | SAGA | TCC 侵入性太强 |

---

### Q11：转账涉及两个账户，怎么保证一致性？

> **深度回答**：
> 
> **单库场景**（两个账户在同一张表）：
> ```sql
> BEGIN;
> UPDATE account SET available_balance = available_balance - 100 WHERE account_no = 'A';
> UPDATE account SET available_balance = available_balance + 100 WHERE account_no = 'B';
> INSERT INTO account_transaction (...) VALUES (...);
> COMMIT;
> ```
> 一个事务搞定，天然一致。
> 
> **分库场景**（账户分布在不同数据库）：
> 
> **方案一：TCC**
> ```
> Try:    A 冻结 100, B 冻结入账 100
> Confirm: A 确认扣减, B 确认入账
> Cancel:  A 解冻, B 解冻
> ```
> 
> **方案二：本地消息表 + MQ**
> ```
> 1. A 库：扣减余额 + 插入消息表（同一事务）
> 2. 定时任务：扫描消息表，发送 MQ
> 3. B 库：消费 MQ，入账余额（幂等）
> ```
> 
> **方案三：SAGA**
> ```
> 正向：A 扣减 → B 入账
> 补偿：A 扣减失败 → 结束；B 入账失败 → A 补偿回滚
> ```
> 
> **面试追问**：你们用哪种？
> 
> 同库用本地事务，跨库用本地消息表 + MQ。TCC 侵入性太强，SAGA 流程太长，都不适合转账这种高频操作。

## 六、安全与风控篇

### Q12：怎么防止账户被恶意盗刷？

> **深度回答**：
> 
> **多层防护**：
> 
> | 层 | 措施 | 说明 |
> |------|------|------|
> | 接口层 | 签名验证 | 请求参数签名，防止篡改 |
> | 接口层 | 时间戳校验 | 请求超过 5 分钟拒绝，防重放 |
> | 接口层 | 幂等校验 | 同一请求只处理一次 |
> | 业务层 | 限额控制 | 单笔/日累计/月累计限额 |
> | 业务层 | 频率控制 | 同一账户 1 分钟内最多 N 笔交易 |
> | 业务层 | 异常检测 | 大额交易、异地登录告警 |
> | 数据层 | 审计日志 | 所有操作记录流水，可追溯 |
> 
> **频率控制实现**（Redis 滑动窗口）：
> ```lua
> -- 滑动窗口限流
> local key = KEYS[1]
> local window = tonumber(ARGV[1])  -- 窗口大小（秒）
> local limit = tonumber(ARGV[2])   -- 限制次数
> local now = tonumber(ARGV[3])     -- 当前时间戳
> 
> -- 移除窗口外的记录
> redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
> -- 统计窗口内的请求数
> local count = redis.call('ZCARD', key)
> if count >= limit then
>     return 0  -- 超限
> end
> -- 添加当前请求
> redis.call('ZADD', key, now, now .. ':' .. math.random())
> redis.call('EXPIRE', key, window)
> return 1  -- 允许
> ```
> 
> **面试追问**：大额交易怎么处理？
> 
> 1. **异步审核**：超过阈值（如 5 万）进入人工审核队列
> 2. **延迟到账**：大额转账延迟 2 小时到账，给风控留时间
> 3. **二次确认**：短信/邮件确认

### Q13：账户冻结和解冻怎么设计？

> **深度回答**：
> 
> **冻结场景**：
> - 司法冻结：法院要求冻结账户
> - 风控冻结：检测到异常交易
> - 用户冻结：用户主动冻结（如挂失）
> - 提现冻结：提现处理中
> 
> **冻结表设计**：
> ```sql
> CREATE TABLE account_freeze_record (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     freeze_id VARCHAR(64) NOT NULL UNIQUE COMMENT '冻结单号',
>     account_no VARCHAR(64) NOT NULL COMMENT '账户号',
>     freeze_type TINYINT NOT NULL COMMENT '冻结类型：1-司法 2-风控 3-用户 4-提现',
>     freeze_amount BIGINT NOT NULL COMMENT '冻结金额（分）',
>     freeze_reason VARCHAR(256) COMMENT '冻结原因',
>     status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1-冻结中 2-已解冻',
>     unfreeze_time DATETIME COMMENT '解冻时间',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     INDEX idx_account_no (account_no),
>     INDEX idx_status (status)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='账户冻结记录';
> ```
> 
> **冻结操作**：
> ```sql
> -- 冻结：可用余额减少，冻结余额增加
> UPDATE account 
> SET available_balance = available_balance - 1000,
>     frozen_balance = frozen_balance + 1000
> WHERE account_no = 'A' AND available_balance >= 1000;
> 
> -- 解冻：冻结余额减少，可用余额增加
> UPDATE account 
> SET frozen_balance = frozen_balance - 1000,
>     available_balance = available_balance + 1000
> WHERE account_no = 'A' AND frozen_balance >= 1000;
> ```
> 
> **面试追问**：司法冻结和提现冻结有什么区别？
> 
> | 类型 | 金额 | 解冻条件 | 谁触发 |
> |------|------|----------|--------|
> | 司法冻结 | 固定金额 | 法院通知解冻 | 外部系统 |
> | 提现冻结 | 提现金额 | 提现成功/失败 | 内部系统 |
> | 风控冻结 | 全部余额 | 风控审核通过 | 风控系统 |

## 七、性能优化篇

### Q14：热点账户（如平台账户）并发扣减性能差怎么办？

> **深度回答**：
> 
> **问题**：所有商户结算都扣平台账户，该行成为热点，大量事务排队等待行锁。
> 
> **方案一：账户分桶**
> ```sql
> -- 将一个平台账户拆成 10 个桶
> INSERT INTO account (account_no, available_balance) VALUES
> ('PLATFORM_001_BUCKET_01', 100000),
> ('PLATFORM_001_BUCKET_02', 100000),
> ...
> ('PLATFORM_001_BUCKET_10', 100000);
> 
> -- 请求随机路由到不同桶
> int bucket = ThreadLocalRandom.current().nextInt(10) + 1;
> String accountNo = String.format("PLATFORM_001_BUCKET_%02d", bucket);
> ```
> 
> **方案二：异步汇总**
> ```
> 1. 扣减请求先写入内存队列
> 2. 定时任务批量汇总，一次性更新数据库
> 3. 减少数据库写入频率
> ```
> 
> **方案三：Redis 预扣 + 异步入账**
> ```
> 1. Redis Lua 原子扣减（高并发）
> 2. 扣减成功后发 MQ
> 3. 消费端异步更新 MySQL
> ```
> 
> **面试追问**：分桶后怎么查询总余额？
> 
> ```sql
> SELECT SUM(available_balance) AS total_available,
>        SUM(frozen_balance) AS total_frozen
> FROM account
> WHERE account_no LIKE 'PLATFORM_001_BUCKET_%';
> ```
> 
> 或者维护一个汇总账户，定时同步。

### Q15：流水表数据量大（几亿行），查询慢怎么办？

> **深度回答**：
> 
> **分表策略**：
> 
> | 维度 | 方式 | 适用场景 |
> |------|------|----------|
> | 按时间 | 月表/季表 | 流水有明显时间特征 |
> | 按账户 | 账户号哈希 | 查询大多按账户维度 |
> | 按金额 | 大额/小额分开 | 大额流水查询频率低 |
> 
> **推荐**：按时间分表 + 按账户号索引
> ```sql
> -- 月表
> account_transaction_202601
> account_transaction_202602
> ...
> 
> -- 查询时指定表
> SELECT * FROM account_transaction_202607 
> WHERE account_no = 'A' ORDER BY create_time DESC LIMIT 20;
> ```
> 
> **归档策略**：
> - 热数据（最近 3 个月）：主库
> - 温数据（3 个月 - 1 年）：从库
> - 冷数据（1 年以上）：归档库/对象存储
> 
> **面试追问**：分表后跨月查询怎么办？
> 
> 应用层合并：查询两个月的流水，应用层 merge 排序。或者用 ShardingSphere 等中间件自动路由。

### Q17：财务公司的客户模型怎么设计？成员单位和外部机构有什么区别？

> **深度回答**：
>
> **客户分层**：
>
> | 客户类型 | 说明 | 示例 | 核心属性 |
> |----------|------|------|----------|
> | **成员单位** | 集团下属法人机构，在财务公司开立账户、办理业务 | 中国电信股份有限公司、天翼终端、号百控股、31省电信分公司 | 客户号、统一社会信用代码、法人信息、评级、授信额度 |
> | **集团总部** | 特殊成员单位，享有资金归集和预算管控权限 | 中国电信集团有限公司 | 预算审批权限、资金归集授权 |
> | **外部金融机构** | 同业对手方，不办理存贷业务，仅参与同业拆借/投资 | 工商银行、建设银行、国泰君安 | 机构代码、同业授信额度、拆借限额 |
> | **外部合作机构** | 非金融对手方，如供应商（代付场景） | 设备供应商、物业公司 | 收款账户信息、白名单状态 |
>
> **成员单位表设计**：
> ```sql
> CREATE TABLE member_unit (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     member_no VARCHAR(32) NOT NULL UNIQUE COMMENT '成员单位编号',
>     member_name VARCHAR(128) NOT NULL COMMENT '单位名称',
>     unified_credit_code VARCHAR(18) NOT NULL COMMENT '统一社会信用代码',
>     member_type TINYINT NOT NULL COMMENT '类型：1-法人子公司 2-分公司 3-特殊目的实体',
>     parent_member_no VARCHAR(32) COMMENT '上级成员单位编号（树形结构）',
>     region_code VARCHAR(10) COMMENT '所属区域编码（省级）',
>     rating_level VARCHAR(10) COMMENT '内部评级：AAA/AA/A/BBB/BB/B',
>     credit_limit DECIMAL(18,2) DEFAULT 0 COMMENT '授信总额度（元）',
>     status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1-正常 2-冻结 3-注销',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_parent_member (parent_member_no),
>     INDEX idx_region (region_code)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='成员单位表';
> ```
>
> **树形结构设计**：成员单位有层级关系（集团→省公司→地市公司），用 `parent_member_no` 表达父子关系。查询某成员单位及其下属单位时用递归 CTE（MySQL 8.0）或应用层递归。
>
> **为什么成员单位要单独建表，不直接复用通用客户表？**
>
> 1. **属性差异大**：成员单位有评级、授信额度、集团层级等金融特有属性，通用客户表无法承载
> 2. **关系复杂**：成员单位之间有资金归集关系、委托贷款关系，需要专门的关系表
> 3. **监管要求**：银保监会要求按成员单位维度报送关联交易、授信集中度等报表
> 4. **生命周期不同**：成员单位注销需要先结清所有合约和账户，通用客户没有这个约束

### Q18：财务公司的产品体系怎么分层？产品和合约是什么关系？

> **深度回答**：
>
> **产品分层架构**：
>
> ```
> 产品大类（Product Category）
>   └── 产品类型（Product Type）
>         └── 产品模板（Product Template）
>               └── 产品实例 = 合约（Contract）
> ```
>
> **六大产品线**：
>
> | 产品线 | 产品类型 | 典型产品 | 计息规则 |
> |--------|----------|----------|----------|
> | **存款** | 活期/定期/通知/协定 | 协定存款（年化1.15%）、3个月定期（1.35%） | 按日计息、按季/到期结息 |
> | **贷款** | 流动资金/固定资产/委托/银团 | 流动资金贷款（LPR+50BP） | 按日计息、按月/季结息 |
> | **结算** | 内部转账/资金归集/资金下拨 | 自动归集（日终扫款） | 手续费按笔/按金额阶梯 |
> | **票据** | 承兑/贴现 | 电子银行承兑汇票贴现 | 贴现利率按期限定价 |
> | **投资** | 债券/同业存单/理财 | 国债逆回购、同业存单 | 到期一次性还本付息 |
> | **同业** | 拆借/存放/回购 | 7天同业拆借（Shibor+20BP） | 到期还本付息 |
>
> **产品模板表**：
> ```sql
> CREATE TABLE product_template (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     product_code VARCHAR(32) NOT NULL UNIQUE COMMENT '产品编码',
>     product_name VARCHAR(128) NOT NULL COMMENT '产品名称',
>     product_line TINYINT NOT NULL COMMENT '产品线：1-存款 2-贷款 3-结算 4-票据 5-投资 6-同业',
>     product_type VARCHAR(32) NOT NULL COMMENT '产品类型：活期/定期/流动资金贷款等',
>     interest_rate_type TINYINT COMMENT '利率类型：1-固定 2-浮动(LPR加点)',
>     base_interest_rate DECIMAL(8,6) COMMENT '基准利率',
>     spread_bp INT COMMENT '加减基点（1BP=0.01%）',
>     min_amount DECIMAL(18,2) COMMENT '最低金额',
>     max_amount DECIMAL(18,2) COMMENT '最高金额',
>     min_term_days INT COMMENT '最短期限（天）',
>     max_term_days INT COMMENT '最长期限（天）',
>     settlement_cycle TINYINT COMMENT '结息周期：1-按日 2-按月 3-按季 4-到期',
>     status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1-上架 2-下架',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_product_line (product_line)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='产品模板表';
> ```
>
> **产品与合约的关系**：
>
> | 维度 | 产品（模板） | 合约（实例） |
> |------|-------------|-------------|
> | 本质 | 业务规则的定义 | 业务规则的执行 |
> | 数量 | 1个产品模板 | N个合约实例 |
> | 属性 | 利率、期限、金额范围 | 具体利率、具体金额、具体期限 |
> | 状态 | 上架/下架 | 签订→生效→执行→结清/终止 |
> | 示例 | "流动资金贷款产品" | "给江苏电信的5000万贷款合同" |
>
> **面试追问**：为什么不直接在合约里存利率，要单独建产品模板表？
>
> 1. **规则变更**：利率政策调整时改一处模板，不影响历史合约
> 2. **一致性**：同类产品利率、期限规则统一，避免人工填写出错
> 3. **定价引擎**：产品模板是定价引擎的输入，支持利率审批流程
> 4. **监管合规**：银保监会要求产品定价有据可查，模板是定价依据

### Q19：财务公司的账户类型有哪些？内部账户和外部账户怎么区分？

> **深度回答**：
>
> **账户分类体系**：
>
> ```
> 账户体系
> ├── 内部账户（成员单位在财务公司开立）
> │   ├── 存款账户
> │   │   ├── 活期存款账户（每个成员单位至少1个）
> │   │   ├── 定期存款账户（每笔定期存款1个）
> │   │   ├── 通知存款账户
> │   │   └── 协定存款账户
> │   ├── 贷款账户
> │   │   ├── 流动资金贷款账户
> │   │   ├── 固定资产贷款账户
> │   │   └── 委托贷款账户
> │   ├── 结算账户
> │   │   ├── 内部结算账户（成员单位间转账）
> │   │   └── 资金池子账户（归集/下拨）
> │   └── 票据账户
> │       └── 贴现账户
> ├── 外部账户（财务公司在银行开立）
> │   ├── 备付金账户（在工/农/中/建等银行开立）
> │   ├── 同业账户（在其他金融机构开立）
> │   └── 清算账户（跨行资金清算）
> └── 内部管理账户
>     ├── 损益账户（利息收入、手续费收入）
>     ├── 待清算账户（在途资金）
>     └── 拨备账户（贷款损失准备）
> ```
>
> **内部账户表设计**：
> ```sql
> CREATE TABLE internal_account (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     account_no VARCHAR(64) NOT NULL UNIQUE COMMENT '账户号',
>     member_no VARCHAR(32) NOT NULL COMMENT '成员单位编号',
>     account_category TINYINT NOT NULL COMMENT '账户大类：1-存款 2-贷款 3-结算 4-票据',
>     account_type VARCHAR(32) NOT NULL COMMENT '账户类型：活期存款/流动资金贷款等',
>     product_code VARCHAR(32) COMMENT '关联产品编码',
>     currency VARCHAR(3) NOT NULL DEFAULT 'CNY' COMMENT '币种',
>     available_balance DECIMAL(18,2) NOT NULL DEFAULT 0 COMMENT '可用余额',
>     frozen_balance DECIMAL(18,2) NOT NULL DEFAULT 0 COMMENT '冻结余额',
>     total_balance DECIMAL(18,2) GENERATED ALWAYS AS (available_balance + frozen_balance) STORED COMMENT '总余额',
>     credit_limit DECIMAL(18,2) DEFAULT 0 COMMENT '授信额度（贷款账户用）',
>     used_credit DECIMAL(18,2) DEFAULT 0 COMMENT '已用授信',
>     interest_rate DECIMAL(8,6) COMMENT '执行利率',
>     open_date DATE NOT NULL COMMENT '开户日期',
>     close_date DATE COMMENT '销户日期',
>     status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1-正常 2-冻结 3-睡眠 4-销户',
>     version INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_member_no (member_no),
>     INDEX idx_account_category (account_category),
>     INDEX idx_product_code (product_code)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='内部账户表';
> ```
>
> **资金池账户结构**：
>
> ```
> 集团结算主账户（集团总部）
>   ├── 江苏电信子账户（归集余额：5.2亿）
>   ├── 广东电信子账户（归集余额：8.1亿）
>   ├── 浙江电信子账户（归集余额：4.8亿）
>   └── ...（200+成员单位子账户）
>
> 日终归集：各成员单位子账户 → 集团结算主账户
> 日终下拨：集团结算主账户 → 各成员单位子账户（根据预算计划）
> ```
>
> **为什么贷款账户也要建 account 表，不直接在合约表里存余额？**
>
> 1. **统一记账**：所有资金变动都通过账户体系，便于核算和审计
> 2. **余额查询**：统一接口查余额，不用区分存款还是贷款
> 3. **交易流水**：所有账户共用流水表，统一管理
> 4. **冻结/解冻**：司法冻结、风控冻结统一走账户层，不侵入业务层

### Q20：合约的生命周期怎么管理？状态机怎么设计？

> **深度回答**：
>
> **合约生命周期**：
>
> ```
> ┌─────────┐    审批通过    ┌─────────┐    到期/结清    ┌─────────┐
> │  草稿    │ ──────────→  │  生效    │ ──────────→   │  结清    │
> │ DRAFT   │              │ ACTIVE  │              │ SETTLED │
> └─────────┘              └─────────┘              └─────────┘
>      │                        │                        ↑
>      │ 撤回                   │ 提前终止                │
>      ↓                        ↓                        │
> ┌─────────┐              ┌─────────┐                   │
> │  撤回    │              │  终止    │ ──────────────────┘
> │WITHDRAWN│              │TERMINATED│
> └─────────┘              └─────────┘
> ```
>
> **合约表设计**：
> ```sql
> CREATE TABLE contract (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     contract_no VARCHAR(64) NOT NULL UNIQUE COMMENT '合约编号',
>     member_no VARCHAR(32) NOT NULL COMMENT '成员单位编号',
>     product_code VARCHAR(32) NOT NULL COMMENT '产品编码',
>     contract_type TINYINT NOT NULL COMMENT '合约类型：1-存款 2-贷款 3-结算 4-票据 5-投资 6-同业',
>     principal_amount DECIMAL(18,2) NOT NULL COMMENT '本金/面额',
>     interest_rate DECIMAL(8,6) NOT NULL COMMENT '执行利率',
>     start_date DATE NOT NULL COMMENT '起始日期',
>     end_date DATE NOT NULL COMMENT '到期日期',
>     term_days INT NOT NULL COMMENT '期限（天）',
>     settlement_cycle TINYINT COMMENT '结息周期：1-按日 2-按月 3-按季 4-到期',
>     status TINYINT NOT NULL DEFAULT 0 COMMENT '状态：0-草稿 1-生效 2-执行中 3-结清 4-终止 5-撤回',
>     approved_by VARCHAR(64) COMMENT '审批人',
>     approved_time DATETIME COMMENT '审批时间',
>     settled_time DATETIME COMMENT '结清时间',
>     remark VARCHAR(512) COMMENT '备注',
>     version INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_member_no (member_no),
>     INDEX idx_product_code (product_code),
>     INDEX idx_status (status),
>     INDEX idx_end_date (end_date)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='合约表';
> ```
>
> **状态流转规则**：
>
> | 当前状态 | 允许的目标状态 | 触发条件 |
> |----------|---------------|----------|
> | 草稿 | 生效、撤回 | 审批通过→生效；提交人撤回→撤回 |
> | 生效 | 执行中、终止 | 首笔交易发生→执行中；提前终止申请→终止 |
> | 执行中 | 结清、终止 | 本金利息全部结清→结清；提前还款→终止 |
> | 结清 | （终态） | 不可变更 |
> | 终止 | （终态） | 不可变更 |
> | 撤回 | （终态） | 不可变更 |
>
> **面试追问**：合约状态变更怎么保证并发安全？
>
> ```java
> // 状态变更必须校验当前状态
> UPDATE contract 
> SET status = #{targetStatus}, 
>     version = version + 1,
>     update_time = NOW()
> WHERE contract_no = #{contractNo} 
>   AND status = #{currentStatus}  -- 乐观锁：只在当前状态符合时才更新
>   AND version = #{version};
> -- 影响行数=0说明状态已变更，抛出异常
> ```
>
> 这比先 SELECT 再 UPDATE 更安全，避免了并发状态变更的竞态条件。

### Q21：财务公司的资产模型怎么设计？贷款资产和投资资产有什么区别？

> **深度回答**：
>
> **资产分类**：
>
> | 资产类型 | 来源 | 计量方式 | 风险权重 |
> |----------|------|----------|----------|
> | **贷款资产** | 成员单位贷款发放 | 摊余成本法 | 100%（一般企业） |
> | **债券资产** | 国债、政策性金融债 | 摊余成本法/公允价值 | 0%（国债）/20%（政策性金融债） |
> | **同业资产** | 同业拆出、同业存放 | 摊余成本法 | 20%-100%（视对手方） |
> | **票据资产** | 持有的承兑汇票 | 摊余成本法 | 20%-100%（视承兑人） |
> | **固定资产** | 办公设备、系统软件 | 原值-累计折旧 | 不计入风险资产 |
>
> **贷款资产表设计**：
> ```sql
> CREATE TABLE loan_asset (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     contract_no VARCHAR(64) NOT NULL COMMENT '关联合约编号',
>     account_no VARCHAR(64) NOT NULL COMMENT '贷款账户号',
>     member_no VARCHAR(32) NOT NULL COMMENT '借款成员单位',
>     principal DECIMAL(18,2) NOT NULL COMMENT '贷款本金',
>     outstanding_principal DECIMAL(18,2) NOT NULL COMMENT '剩余本金',
>     accrued_interest DECIMAL(18,2) NOT NULL DEFAULT 0 COMMENT '应收未收利息',
>     interest_rate DECIMAL(8,6) NOT NULL COMMENT '执行利率',
>     disbursement_date DATE NOT NULL COMMENT '放款日',
>     maturity_date DATE NOT NULL COMMENT '到期日',
>     repayment_method TINYINT NOT NULL COMMENT '还款方式：1-到期一次还本付息 2-等额本息 3-等额本金 4-按月付息到期还本',
>     five_level_class TINYINT NOT NULL DEFAULT 1 COMMENT '五级分类：1-正常 2-关注 3-次级 4-可疑 5-损失',
>     provision_amount DECIMAL(18,2) NOT NULL DEFAULT 0 COMMENT '拨备金额',
>     overdue_days INT NOT NULL DEFAULT 0 COMMENT '逾期天数',
>     status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1-正常 2-逾期 3-核销',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_member_no (member_no),
>     INDEX idx_contract_no (contract_no),
>     INDEX idx_five_level (five_level_class),
>     INDEX idx_maturity_date (maturity_date)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='贷款资产表';
> ```
>
> **投资资产表设计**：
> ```sql
> CREATE TABLE investment_asset (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     contract_no VARCHAR(64) NOT NULL COMMENT '关联合约编号',
>     asset_code VARCHAR(64) NOT NULL COMMENT '证券代码/存单编号',
>     asset_name VARCHAR(128) NOT NULL COMMENT '资产名称',
>     asset_type TINYINT NOT NULL COMMENT '类型：1-国债 2-政策性金融债 3-同业存单 4-企业债 5-理财产品',
>     face_value DECIMAL(18,2) NOT NULL COMMENT '面值',
>     purchase_price DECIMAL(18,2) NOT NULL COMMENT '买入价格',
>     current_price DECIMAL(18,2) COMMENT '当前市价（公允价值）',
>     coupon_rate DECIMAL(8,6) COMMENT '票面利率',
>     purchase_date DATE NOT NULL COMMENT '买入日',
>     maturity_date DATE NOT NULL COMMENT '到期日',
>     counterparty VARCHAR(128) COMMENT '对手方（发行机构）',
>     risk_weight DECIMAL(5,2) NOT NULL COMMENT '风险权重（%）',
>     status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1-持有 2-已卖出 3-已到期',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_asset_type (asset_type),
>     INDEX idx_maturity_date (maturity_date)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='投资资产表';
> ```
>
> **贷款资产 vs 投资资产的核心区别**：
>
> | 维度 | 贷款资产 | 投资资产 |
> |------|----------|----------|
> | 对手方 | 成员单位（集团内部） | 金融机构/政府（外部） |
> | 定价方式 | LPR + 风险溢价 | 市场竞价/招投标 |
> | 风险评估 | 内部评级 + 五级分类 | 外部评级 + 风险权重 |
> | 拨备要求 | 按五级分类计提拨备 | 按公允价值计量（一般不计提） |
> | 减值测试 | 每月 | 每季度 |
> | 监管报送 | 贷款明细报送 | 投资组合报送 |
>
> **面试追问**：五级分类怎么自动判断？
>
> ```java
> /**
>  * 根据逾期天数自动调整五级分类。
>  */
> public int classifyLoan(int overdueDays) {
>     if (overdueDays <= 0) return 1;      // 正常
>     if (overdueDays <= 90) return 2;     // 关注
>     if (overdueDays <= 180) return 3;    // 次级
>     if (overdueDays <= 360) return 4;    // 可疑
>     return 5;                            // 损失
> }
> ```
> 拨备覆盖率要求：正常1%、关注2%、次级25%、可疑50%、损失100%。

### Q22：客户、产品、账户、合约、资产之间的关系是什么？

> **深度回答**：
>
> **实体关系图**：
>
> ```
> ┌──────────┐    1:N    ┌──────────┐    1:N    ┌──────────┐
> │  客户     │ ────────→ │  合约     │ ────────→ │  资产     │
> │(成员单位) │          │(产品实例) │          │(贷款/投资)│
> └──────────┘          └──────────┘          └──────────┘
>       │                     ↑                     │
>       │ 1:N                 │ N:1                 │ 1:1
>       ↓                     │                     ↓
> ┌──────────┐          ┌──────────┐          ┌──────────┐
> │  账户     │ ←────────│  产品     │          │  流水     │
> │(内部/外部)│    N:1   │(产品模板) │          │(交易记录)│
> └──────────┘          └──────────┘          └──────────┘
>       │
>       │ 1:N
>       ↓
> ┌──────────┐
> │  交易流水  │
> └──────────┘
> ```
>
> **关系详解**：
>
> | 关系 | 说明 | 示例 |
> |------|------|------|
> | 客户 → 合约（1:N） | 一个成员单位可以签多份合约 | 江苏电信同时有1笔存款合约、2笔贷款合约 |
> | 产品 → 合约（1:N） | 一个产品模板生成多个合约实例 | "流动资金贷款产品"生成200+份贷款合约 |
> | 合约 → 账户（1:1 或 1:N） | 合约生效后开立对应账户 | 1份贷款合约对应1个贷款账户 |
> | 合约 → 资产（1:1） | 贷款合约对应贷款资产，投资合约对应投资资产 | 贷款合约→贷款资产（记录剩余本金、拨备等） |
> | 客户 → 账户（1:N） | 一个成员单位有多个账户 | 江苏电信有活期存款账户、定期存款账户、贷款账户 |
> | 账户 → 流水（1:N） | 每个账户有多笔交易流水 | 活期存款账户每天有多笔入账/出账 |
>
> **一笔贷款业务的完整链路**：
>
> ```
> 1. 客户：江苏电信（member_no: JS_TELECOM）
> 2. 产品：流动资金贷款产品（product_code: LOAN_WORKING_CAPITAL）
> 3. 合约：合约编号 LOAN202607001，金额5000万，期限1年，利率LPR+50BP
> 4. 账户：贷款账户 ACC_LOAN_202607001，授信额度5000万
> 5. 资产：贷款资产 LA_202607001，剩余本金5000万，五级分类=正常
> 6. 流水：放款流水 TXN_DISBURSE_001，金额+5000万，账户余额变为5000万
> ```
>
> **面试追问**：为什么不把合约和账户合并成一张表？
>
> 1. **生命周期不同**：合约可能提前终止，但账户需要保留历史流水
> 2. **一对多场景**：委托贷款合约涉及委托方账户和借款方账户，一个合约对应多个账户
> 3. **关注点不同**：合约关注业务条款（利率、期限），账户关注资金余额
> 4. **复用性**：账户模块独立后，存款、贷款、结算共用账户基础设施

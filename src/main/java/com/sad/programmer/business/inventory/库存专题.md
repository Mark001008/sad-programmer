# 库存专题

> 面试高频度：⭐⭐⭐⭐⭐  
> 适用场景：电商系统、秒杀系统、订单系统、仓储系统  
> 核心考点：高并发扣减、超卖防护、跨层一致性、状态机设计

---

## 一、架构设计篇

### Q1：你们的库存系统为什么分三层？每层解决什么问题？

> **深度回答**：
> 
> 三层不是为了分层而分层，是**关注点分离**：
> 
> | 层 | 解决的问题 | 如果没有这层会怎样 |
> |----|-----------|-------------------|
> | **销售层** | 高并发读写（秒杀 QPS 10000+） | 所有请求直接打到 MySQL，数据库扛不住 |
> | **调度层** | 订单与库存的生命周期管理 | 库存扣了但订单没创建，或者订单取消了库存没释放 |
> | **仓库层** | 物理仓库的真实库存映射 | 线上卖了 100 件，仓库实际只有 80 件 |
> 
> **关键理解**：三层之间不是简单调用，而是**职责边界**：
> - 销售层不关心"这个库存是哪个仓库的"，只关心"能不能卖"
> - 调度层不关心"库存存在 Redis 还是 MySQL"，只关心"预占→锁定→确认"的状态流转
> - 仓库层不关心"谁在卖"，只关心"仓库里实际有多少货"
> 
> **面试追问**：三层之间数据怎么流转？
> ```
> 下单：销售层扣可销售库存 → 调度层创建预占记录 → 仓库层锁定物理库存
> 取消：调度层状态→UNLOCKED → 销售层回滚可销售库存
> 入库：仓库层增加物理库存 → 销售层同步可销售库存
> ```

### Q2：为什么调度层要用状态机？状态流转怎么保证并发安全？

> **深度回答**：
> 
> 调度层的核心是**预占记录的生命周期管理**，状态机定义了合法的状态转换：
> 
> ```
> RESERVED(0) ──→ LOCKED(1) ──→ CONFIRMED(3)  [终态，不可逆]
>      │              │
>      └──→ UNLOCKED(2) ←──┘
> ```
> 
> **为什么需要状态机？** 因为同一个预占记录可能被多个并发操作：
> - 用户同时点了"支付"和"取消"
> - 延迟队列超时释放 vs 用户刚好支付成功
> - 重复回调（支付网关多次通知）
> 
> **并发安全怎么保证？** 用 CAS（Compare And Swap）：
> 
> ```java
> // 只有当前状态等于期望值时才更新
> String sql = "UPDATE reservation_record "
>            + "SET status = ?, update_time = NOW() "
>            + "WHERE reservation_id = ? AND status = ?";
> // 如果返回 0，说明状态已被其他事务修改，操作失败
> ```
> 
> **面试追问**：CAS 返回 0 怎么处理？
> 
> 看业务语义：
> - `lockStock` 返回 0 → 说明已经被解锁了，返回 false
> - `confirmDeduction` 返回 0 → 说明不是 LOCKED 状态，返回 false
> - 不重试，因为状态不匹配意味着业务上不允许这个操作
> 
> **面试再追问**：为什么不用分布式锁？
> 
> CAS 是**无锁方案**，性能更好。分布式锁引入了额外的复杂度（锁超时、续期、网络分区），对于单条记录的状态更新，数据库行锁 + CAS 已经足够。

### Q3：幂等检查怎么实现的？为什么不用 Redis Set 做？

> **深度回答**：
> 
> **场景**：同一订单对同一商品重复调用 `reserveStock`，应返回失败而非创建多条预占。
> 
> **实现**：直接查数据库，走复合索引：
> 
> ```java
> // ReservationDaoImpl
> String sql = "SELECT reservation_id FROM reservation_record "
>            + "WHERE order_id = ? AND product_id = ? AND status != 2";
> ```
> 
> 索引：`(order_id, product_id)` 复合索引，查询走索引，O(1)。
> 
> **为什么不用 Redis Set？**
> 
> | 方案 | 优点 | 致命缺陷 |
> |------|------|----------|
> | Redis Set | 快 | Redis 宕机丢数据，幂等检查失效，重复预占 |
> | 数据库查询 | 可靠 | 稍慢（但有索引，延迟 < 1ms） |
> 
> 幂等检查是**资金安全相关**的操作，必须以数据库为准。Redis 只适合做缓存，不适合做幂等的唯一依据。
> 
> **面试追问**：为什么不用布隆过滤器做幂等预判？
> 
> 布隆过滤器可以快速判断"一定不存在"，但无法判断"一定存在"（有误判率）。幂等检查要求**精确匹配**（同一个 orderId + productId），布隆过滤器不适用。数据库复合索引查询延迟 < 1ms，已经是最佳方案。

## 二、并发控制篇

### Q4：Redis Lua 扣减库存，为什么不能用 GET + DECRBY 两步？

> **深度回答**：
> 
> **反例**：
> ```java
> // 错误！非原子操作
> int stock = jedis.get(key);  // 线程A读到1，线程B也读到1
> if (stock >= quantity) {
>     jedis.decrBy(key, quantity);  // 线程A扣1剩0，线程B扣1剩-1 → 超卖！
> }
> ```
> 
> **正确做法**：Lua 脚本保证原子性：
> 
> ```lua
> local stock = tonumber(redis.call('GET', KEYS[1]))
> if stock == nil then return -1 end    -- Key不存在，需加载
> if stock < tonumber(ARGV[1]) then return 0 end  -- 库存不足
> redis.call('DECRBY', KEYS[1], ARGV[1])
> return 1                              -- 扣减成功
> ```
> 
> **为什么 Lua 是原子的？** Redis 是单线程模型，执行 Lua 脚本时不会处理其他命令。整个脚本是一个不可分割的执行单元。
> 
> **面试追问**：Lua 返回 -1（Key 不存在）怎么处理？
> 
> ```java
> if (evalResult == -1) {
>     // Key 不存在，从 MySQL 加载库存到 Redis
>     loadStockFromDbToRedis(jedis, productId, redisKey);
>     retryCount++;
>     // 重试一次
> }
> ```
> 
> 这是 **Cache-Aside + 自动加载** 模式。首次请求或 Redis 重启后，自动从 DB 回源。

### Q5：Redis 扣减成功但 MySQL 更新失败怎么办？

> **深度回答**：
> 
> 这是 **Redis + MySQL 双写一致性**的核心问题。我们的方案是**先扣 Redis，再更新 MySQL，失败则补偿回滚**：
> 
> ```java
> // 1. Redis Lua 扣减成功
> boolean deducted = deductFromRedis(productId, quantity);
> 
> // 2. MySQL 乐观锁扣减
> int affected = dao.updateAvailableStockWithCheck(conn, productId, quantity);
> if (affected == 0) {
>     // MySQL 扣减失败，补偿回滚 Redis
>     jedis.incrBy(redisKey, quantity);  // 回滚
>     return false;
> }
> ```
> 
> **为什么这个顺序？**
> 
> | 顺序 | 场景 | 后果 |
> |------|------|------|
> | 先 Redis 后 MySQL | MySQL 失败 | Redis 回滚，用户看到"库存不足"，**可接受** |
> | 先 MySQL 后 Redis | Redis 失败 | MySQL 已扣但 Redis 没扣，**缓存多扣**，用户看到"有库存"但实际没有 |
> 
> 先扣 Redis 的好处是：**失败时数据偏保守**（用户看到库存不足而非超卖）。
> 
> **面试追问**：INCRBY 回滚也失败了怎么办？
> 
> 这是极端情况（Redis 也挂了）。此时：
> 1. MySQL 事务已回滚，数据是正确的
> 2. Redis 库存比 MySQL 少（偏保守），用户看到"库存不足"
> 3. 下次请求触发 `loadStockFromDbToRedis`，从 MySQL 重新加载，自动修复
> 
> **核心原则**：Redis 是缓存，MySQL 是最终真相源。缓存数据偏少 = 少卖，可以接受；缓存数据偏多 = 超卖，不可接受。

### Q6：仓库层的 SELECT FOR UPDATE 和乐观锁有什么区别？什么时候用哪个？

> **深度回答**：
> 
> **SELECT FOR UPDATE（悲观锁）**：
> ```sql
> SELECT * FROM warehouse_inventory 
> WHERE warehouse_id = ? AND product_id = ? FOR UPDATE
> ```
> - 事务内锁定该行，其他事务阻塞等待
> - 适合**读-改-写**场景：先查再算再写
> - 我们用在 `inbound`（入库）：先查是否存在，存在则累加，不存在则插入
> 
> **乐观锁（WHERE 条件）**：
> ```sql
> UPDATE warehouse_inventory 
> SET available_stock = available_stock - ?
> WHERE warehouse_id = ? AND product_id = ? AND available_stock >= ?
> ```
> - 不加锁，通过 WHERE 条件判断是否成功
> - 适合**纯写**场景：不需要先读，直接更新
> - 我们用在 `outbound`（出库）：直接扣减，库存不足返回 0
> 
> **选择依据**：
> 
> | 场景 | 选择 | 原因 |
> |------|------|------|
> | 入库（先查是否存在再决定插入/更新） | SELECT FOR UPDATE | 需要读取结果来决定后续逻辑 |
> | 出库（直接扣减，WHERE 兜底） | 乐观锁 | 不需要先读，一条 SQL 搞定 |
> | 库存转移（A仓→B仓） | SELECT FOR UPDATE | 需要同时锁定两行 |
> 
> **面试追问**：SELECT FOR UPDATE 会死锁吗？
> 
> 会。如果多个事务以不同顺序锁定多行就会死锁。解决方案：
> 1. 按固定顺序锁定（如 warehouse_id 升序）
> 2. 设置锁等待超时 `innodb_lock_wait_timeout`
> 3. 尽量用乐观锁替代

### Q7：延迟队列怎么实现预占超时自动释放？

> **深度回答**：
> 
> **数据结构**：Redis ZSET，score 为过期时间戳，member 为 reservationId。
> 
> **投递**：预占成功后，把 reservationId 放入 ZSET：
> ```java
> delayQueue.offer(reservationId, expireMillis);
> // 内部：ZADD key {currentTimeMillis + expireMillis} reservationId
> ```
> 
> **消费**：定时任务调用 `handleExpiredReservations()`：
> ```java
> public void handleExpiredReservations() {
>     String reservationId;
>     while ((reservationId = delayQueue.poll()) != null) {
>         unlockStock(reservationId, "auto-expired by delay queue");
>     }
> }
> ```
> 
> **poll() 内部实现**（Lua 原子操作）：
> ```lua
> -- ZRANGEBYSCORE key 0 {currentTime} LIMIT 0 1
> -- ZREM key member
> -- 两步必须原子，否则多个消费者会重复消费
> ```
> 
> **面试追问**：为什么不用 RocketMQ 延迟消息？
> 
> | 方案 | 优点 | 缺点 |
> |------|------|------|
> | Redis ZSET | 轻量，无额外依赖，原子性好 | Redis 宕机丢消息 |
> | RocketMQ | 可靠，支持持久化 | 重，需要额外部署 |
> 
> 生产环境如果已有 MQ，用 MQ 更可靠。
> 
> **面试再追问**：Redis 宕机导致延迟消息丢失怎么办？
> 
> 兜底方案：定期扫描数据库中 `status=RESERVED 且 expire_time < NOW()` 的记录，批量解锁。

## 三、数据一致性篇

### Q8：Redis 和 MySQL 的数据一致性怎么保证？

> **深度回答**：
> 
> 我们用的是 **Cache-Aside + 写时双删** 模式：
> 
> **读路径**：
> ```
> 1. 读 Redis → 命中直接返回
> 2. 未命中 → 读 MySQL → 写入 Redis（设置 TTL）→ 返回
> ```
> 
> **写路径（扣减）**：
> ```
> 1. Redis Lua 原子扣减
> 2. MySQL 乐观锁扣减
> 3. MySQL 失败 → Redis INCRBY 回滚
> ```
> 
> **写路径（回收/同步）**：
> ```
> 1. MySQL 先更新
> 2. Redis INCRBY / SET 同步
> ```
> 
> **为什么不先写 MySQL 再写 Redis？**
> 
> | 顺序 | 失败场景 | 后果 |
> |------|----------|------|
> | 先 MySQL 后 Redis | Redis 写失败 | 缓存脏数据，用户看到旧库存 |
> | 先 Redis 后 MySQL | MySQL 写失败 | Redis 回滚，用户看到库存不足（可接受） |
> 
> **面试追问**：TTL 过期后缓存和数据库不一致怎么办？
> 
> TTL 3600 秒过期后，下次请求触发 Cache-Aside 回源，从 MySQL 重新加载。最坏情况是 1 小时内的数据不一致，但因为写操作会同步更新 Redis，实际不一致窗口很小。
> 
> **面试再追问**：如果要强一致呢？
> 
> 用 **分布式事务**（如 Seata AT 模式）或 **消息最终一致性**（如 RocketMQ 事务消息）。但库存场景通常接受最终一致性，强一致代价太大。

### Q9：预占记录和可销售库存之间怎么保持一致？

> **深度回答**：
> 
> 这是调度层和销售层之间的**跨层一致性**问题。
> 
> **正常流程**：
> ```
> 1. 销售层：Redis DECRBY 扣减可销售库存（原子）
> 2. 调度层：MySQL INSERT 预占记录（事务）
> 3. 如果步骤 2 失败 → 销售层回滚 Redis
> ```
> 
> **取消/超时流程**：
> ```
> 1. 调度层：MySQL UPDATE status → UNLOCKED
> 2. 上层调用销售层：MySQL INCR + Redis INCRBY
> ```
> 
> **关键设计**：销售层的扣减和调度层的预占**不在同一个事务**中（Redis 和 MySQL 无法分布式事务）。所以：
> - 先扣销售层，再创建调度层预占
> - 调度层失败，回滚销售层
> - 调度层成功，两者一致
> 
> **面试追问**：如果回滚销售层也失败了呢？
> 
> 极端情况：销售层少扣了（Redis 比 MySQL 少），用户看到"库存不足"。下次 `syncActualStock` 会从 MySQL 重新同步到 Redis，自动修复。
> 
> **核心原则**：跨层一致性靠**补偿机制 + 定期同步**，不靠分布式事务。

## 四、深度追问篇

### Q10：如果让你重新设计，你会改什么？

> **参考答案**（展示思考深度）：
> 
> **1. 加入本地缓存（Caffeine）**：
> - 销售层查询可以先走本地缓存，减少 Redis 网络开销
> - 本地缓存 TTL 设短（几秒），容忍短暂不一致
> 
> **2. 异步化 MySQL 更新**：
> - Redis 扣减成功后，通过消息队列异步更新 MySQL
> - 提高写入吞吐量，但增加一致性复杂度
> 
> **3. 库存分桶**：
> - 将 1000 件库存拆成 10 个桶，每桶 100 件
> - 不同请求路由到不同桶，减少热点竞争
> 
> **4. 加入对账系统**：
> - 定时对比 Redis、MySQL、预占记录三者数据
> - 自动修复不一致
> 
> **5. 读写分离**：
> - 查询走从库，写入走主库
> - 减轻主库压力

### Q11：本地缓存和分布式缓存怎么选？

> **深度回答**：
> 
> | 维度 | 本地缓存（Caffeine/Guava） | 分布式缓存（Redis） |
> |------|---------------------------|-------------------|
> | 延迟 | 纳秒级 | 毫秒级（网络开销） |
> | 容量 | 受 JVM 堆限制 | 独立内存，可扩展 |
> | 一致性 | 单机一致，多实例不一致 | 多实例一致 |
> | 淘汰策略 | LRU/LFU/TTL | LRU/LFU/TTL/LFU |
> | 适用场景 | 读多写少、容忍短暂不一致 | 高并发读写、需要强一致 |
> 
> **库存系统怎么选？**
> 
> 库存是**写多**场景（秒杀扣减），且需要**多实例一致**，所以选 Redis。
> 
> 但可以在 Redis 前加一层本地缓存做**库存标记**：
> ```java
> // 库存为 0 的标记，本地缓存 10 秒
> // 避免库存为 0 时每次请求都穿透到 Redis
> if (localCache.getIfPresent("stock:zero:" + productId) != null) {
>     return false;  // 快速失败
> }
> ```
> 
> **面试追问**：本地缓存多实例不一致怎么办？
> 
> 库存标记场景可以容忍：最坏情况是多卖几件（本地缓存说有库存但实际没有），MySQL 乐观锁兜底。或者用 Redis Pub/Sub 广播缓存失效事件。

### Q12：为什么用 JDBC 而不是 MyBatis/JPA？

> **深度回答**：
> 
> **项目背景**：这是面试练习项目，目的是展示**底层原理理解**。
> 
> **用 JDBC 的好处**：
> 1. **完全控制 SQL**：面试时能手写 SQL，展示基本功
> 2. **理解连接/事务管理**：手动 `setAutoCommit(false)`、`commit()`、`rollback()`
> 3. **理解资源关闭**：手动关闭 Connection、Statement、ResultSet
> 4. **无框架黑盒**：每一步都是可见的
> 
> **生产环境当然用 MyBatis**：
> - 模板代码少
> - 动态 SQL 方便
> - 插件生态丰富
> 
> **面试追问**：JDBC 的 Connection 管理有什么坑？
> 
> 1. **连接泄漏**：忘记在 finally 中关闭
> 2. **事务未回滚**：catch 中忘记 rollback
> 3. **autoCommit 未恢复**：关闭前应恢复 autoCommit=true
> 4. **隔离级别**：不同方法需要不同隔离级别，容易搞混
> 
> 我们的代码都处理了这些：
> ```java
> private void closeQuietly(Connection conn) {
>     if (conn != null) {
>         try {
>             if (!conn.isClosed()) {
>                 conn.setAutoCommit(true);  // 恢复 autoCommit
>             }
>         } catch (SQLException ignored) {}
>         JdbcUtil.close(conn);  // 关闭连接
>     }
> }
> ```

## 五、场景设计篇

### Q13：设计一个秒杀库存系统

> **深度回答**（结合实际实现）：
> 
> **架构**：
> ```
> 用户 → Nginx（限流）→ 应用层 → Redis Lua（原子扣减）
>                                      ↓ 成功
>                               MySQL（乐观锁补偿）
>                                      ↓
>                               调度层（预占记录 + 延迟队列）
> ```
> 
> **关键设计点**：
> 
> | 环节 | 方案 | 原因 |
> |------|------|------|
> | 前端 | 按钮置灰 + 倒计时 | 减少无效请求 |
> | Nginx | limit_req 限流 | 保护后端 |
> | 应用层 | 本地缓存库存标记 | 库存为 0 直接返回，不穿透到 Redis |
> | Redis | Lua 原子扣减 | 单线程无锁竞争 |
> | MySQL | 乐观锁补偿 | 兜底防超卖 |
> | 调度层 | 预占 + 延迟队列 | 支持未支付超时释放 |
> 
> **面试追问**：10 万件商品，100 万人抢，Redis 能扛住吗？
> 
> Redis 单机 QPS 约 10 万。Lua 脚本执行时间约 0.1ms，理论 QPS 可达 100 万。100 万人同时请求，Redis 能扛住。
> 
> 瓶颈在网络 IO 和应用层。解决方案：
> 1. 应用层本地缓存库存标记，库存为 0 直接返回
> 2. Redis Cluster 分片
> 3. 多级限流（Nginx + 应用层 + Redis）

### Q14：订单取消后库存没释放，怎么排查？

> **深度回答**：
> 
> **排查步骤**：
> 
> 1. **查预占记录状态**：
> ```sql
> SELECT * FROM reservation_record WHERE order_id = 'xxx';
> -- status=0 还在预占中，说明没执行解锁
> ```
> 
> 2. **查延迟队列**：
> ```
> ZRANGEBYSCORE scheduling:delay:reservations 0 {now}
> -- 看 reservationId 是否还在队列中
> ```
> 
> 3. **查 Redis 库存**：
> ```
> GET inventory:sales:{productId}
> -- 对比 MySQL 中的 available_stock
> ```
> 
> **可能原因**：
> 
> | 原因 | 现象 | 修复 |
> |------|------|------|
> | unlockStock 代码异常 | status 仍为 0 | 手动执行 unlockStock |
> | 延迟队列 poll 失败 | reservationId 还在 ZSET | 手动触发 handleExpiredReservations |
> | Redis 宕机 | ZSET 数据丢失 | 扫描 DB 中过期的 RESERVED 记录 |
> | 调用链断裂 | 调度层解锁了但销售层没回滚 | 对账修复 Redis 库存 |
> 
> **面试追问**：怎么预防？
> 
> 1. **对账系统**：定时对比三层数据
> 2. **兜底扫描**：定期扫描 `status=RESERVED AND expire_time < NOW()`
> 3. **监控告警**：预占记录超过阈值告警

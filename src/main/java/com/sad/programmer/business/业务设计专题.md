## 1. 秒杀系统的全链路设计是怎样的？如何保证高并发下的库存一致性？

**深度答案：**

秒杀系统的本质是**高并发写 + 强一致性**，需要从全链路进行流量治理：

**前端限流层：**
- 按钮防抖：点击后置灰，防止重复提交
- 验证码/答题：增加请求时间成本，过滤机器刷单
- URL 动态化：秒杀开始前才暴露真实 URL，防止提前刷接口
- 前端缓存：静态资源走 CDN，减少服务器压力

**网关限流层：**
- 令牌桶算法控制 QPS（如 1000 QPS）
- 限流维度：用户ID、商品ID、IP地址
- 超限直接返回友好提示，不穿透到下游

**库存预扣层（Redis）：**
```lua
-- Lua 脚本保证原子性
local stock = redis.call('get', KEYS[1])
if stock and tonumber(stock) > 0 then
    redis.call('decr', KEYS[1])
    return 1  -- 扣减成功
end
return 0  -- 库存不足
```
- 库存预热：秒杀开始前将库存加载到 Redis
- Redis 集群分片：避免单点瓶颈

**异步下单层：**
- 扣减成功后发送 MQ 消息（订单服务消费）
- 削峰填谷：MQ 缓冲写压力
- 消费端幂等：唯一订单号防重复创建

**数据库兜底：**
- 乐观锁：`UPDATE t_stock SET quantity = quantity - 1 WHERE quantity > 0`
- 最终一致性：Redis 和 DB 双写，以 DB 为准

**架构设计亮点：**
```
前端防抖 → 网关限流 → Redis预扣 → MQ异步 → DB兜底
   ↓           ↓           ↓           ↓           ↓
 减少请求    流量控制    高速扣减    削峰填谷    强一致
```

**面试亮点：**
- 能否说清各层的作用和降级策略
- 是否理解 Redis 和 DB 双写的一致性问题
- 是否考虑过超卖的兜底方案（如订单支付时二次校验库存）

**实战场景：**
- 电商平台大促秒杀
- 限量商品抢购（如茅台、iPhone）
- 优惠券秒杀发放

## 2. 分布式事务有哪 4 种主流方案？如何选型？

**深度答案：**

### 方案对比

| 方案 | 一致性 | 性能 | 业务侵入 | 适用场景 |
|------|--------|------|----------|----------|
| **2PC** | 强一致 | 差（阻塞） | 低 | 传统数据库事务、金融核心 |
| **TCC** | 最终一致 | 中 | 高 | 资金转账、库存扣减 |
| **SAGA** | 最终一致 | 好 | 中 | 长流程、跨多服务（如订单履约） |
| **本地消息表** | 最终一致 | 好 | 低 | 异步场景、解耦服务 |

### 2PC（两阶段提交）
- **阶段一**：协调者询问所有参与者是否可以提交，参与者返回 Yes/No
- **阶段二**：全部 Yes 则提交，否则回滚
- **问题**：协调者单点故障、参与者阻塞、脑裂风险
- **适用**：MySQL XA 事务、金融强一致场景

### TCC（Try-Confirm-Cancel）
- **Try**：预留资源（如冻结库存、冻结余额）
- **Confirm**：确认提交（幂等）
- **Cancel**：回滚释放（幂等）
- **难点**：空回滚、悬挂、幂等性
- **适用**：资金交易、库存扣减

### SAGA
- 长事务拆分为多个本地事务，每个事务有对应的补偿操作
- 正向执行失败时，逆向执行补偿
- **编排式**：中心协调器控制流程
- **协同式**：事件驱动，各服务自行监听
- **适用**：订单履约（下单→扣库存→支付→发货）

### 本地消息表
- 业务操作和消息插入在同一个本地事务
- 定时任务扫描未确认消息，发送到 MQ
- 下游消费成功后回调确认
- **适用**：异步解耦、最终一致场景

**选型决策树：**
```
强一致？ → 2PC/XA
需要资源预留？ → TCC
长流程多步骤？ → SAGA
异步解耦？ → 本地消息表/事务消息
```

**面试亮点：**
- 能否说出各方案的适用边界和踩坑点
- 是否理解 TCC 的空回滚和悬挂问题
- 是否知道 RocketMQ 的事务消息机制

**实战场景：**
- 跨行转账（2PC 或 TCC）
- 电商下单（SAGA：扣库存→扣款→发货）
- 支付结果通知（本地消息表）

## 3. 限流算法有哪些？各自优缺点是什么？

**深度答案：**

### 令牌桶算法（Token Bucket）
```
         ┌─────────────────┐
         │   Token Bucket   │
         │  (固定速率填充)  │
         └────────┬────────┘
                  │
    ┌─────────────┴─────────────┐
    │                           │
 消费请求                    丢弃请求
 (有令牌)                   (无令牌)
```
- **原理**：以固定速率向桶中放入令牌，请求需获取令牌才能通过
- **优点**：允许突发流量（桶满时），平滑限流
- **缺点**：实现相对复杂，需维护定时器
- **适用**：API 网关、用户维度限流

### 漏桶算法（Leaky Bucket）
- **原理**：请求进入桶中，以固定速率流出处理
- **优点**：严格平滑流量，输出速率恒定
- **缺点**：无法应对突发流量，即使系统空闲也限制
- **适用**：流量整形、日志收集

### 滑动窗口算法（Sliding Window）
- **原理**：将时间划分为多个小窗口，统计当前时间窗口内的请求数
- **优点**：比固定窗口更平滑，避免临界突发
- **缺点**：内存开销较大（需记录每个请求时间戳）
- **适用**：精确限流（如每用户每秒 N 次）

### 滑动日志算法（Sliding Log）
- **原理**：记录每个请求的时间戳，统计时间窗口内的请求数
- **优点**：最精确
- **缺点**：内存开销最大
- **适用**：低并发精确限流

**对比总结：**

| 算法 | 平滑性 | 突发处理 | 内存开销 | 实现复杂度 |
|------|--------|----------|----------|------------|
| 令牌桶 | 好 | 支持 | 低 | 中 |
| 漏桶 | 最好 | 不支持 | 低 | 低 |
| 滑动窗口 | 中 | 部分支持 | 中 | 中 |
| 滑动日志 | 最好 | 不支持 | 高 | 高 |

**面试亮点：**
- 能否说清各算法的实现原理和适用场景
- 是否了解分布式限流（Redis + Lua）的实现
- 是否知道 Sentinel 的滑动窗口统计原理

**实战场景：**
- 网关限流：令牌桶
- 用户接口防刷：滑动窗口
- 消息队列消费限速：漏桶

## 4. 服务降级和熔断有什么区别？Hystrix 和 Sentinel 的实现原理？

**深度答案：**

### 降级 vs 熔断

**降级（Degradation）：**
- **主动降级**：提前识别非核心功能，高峰期关闭（如关闭推荐、评论）
- **被动降级**：依赖服务异常时，返回默认值或缓存数据
- **目的**：保障核心链路，牺牲非核心体验

**熔断（Circuit Breaking）：**
- **触发条件**：错误率超过阈值（如 50%）
- **状态机**：CLOSED → OPEN → HALF_OPEN
  - CLOSED：正常状态，统计错误率
  - OPEN：熔断状态，直接快速失败
  - HALF_OPEN：半开状态，试探性放行部分请求
- **目的**：防止级联故障，保护下游服务

### Hystrix 实现原理
- **线程池隔离**：每个依赖服务分配独立线程池，避免相互影响
- **信号量隔离**：限制并发请求数，无线程切换开销
- **滑动窗口统计**：10 秒内分为 10 个桶，统计成功/失败/超时
- **熔断策略**：基于错误百分比或请求量阈值

### Sentinel 实现原理
- **滑动窗口（LeapArray）**：将时间窗口划分为多个小格子，统计 QPS、RT、异常数
- **熔断策略**：
  - 慢调用比例：RT 超过阈值的比例
  - 异常比例：异常请求的比例
  - 异常数：异常请求的绝对数量
- **热点参数限流**：针对特定参数值限流（如商品 ID）
- **集群限流**：Token Server 统一分配令牌

**架构对比：**

| 特性 | Hystrix | Sentinel |
|------|---------|----------|
| 隔离策略 | 线程池/信号量 | 信号量 |
| 熔断策略 | 错误率 | 慢调用/异常比例/异常数 |
| 流控 | 无 | QPS/并发数 |
| 热点限流 | 无 | 支持 |
| 集群限流 | 无 | 支持 |
| 规则配置 | 本地 | 本地/Dashboard/Nacos |

**面试亮点：**
- 能否说清降级和熔断的区别和联系
- 是否理解滑动窗口统计的实现
- 是否知道 Sentinel 的热点参数限流原理

**实战场景：**
- 电商商品详情页（降级推荐、评论）
- 支付链路（熔断第三方支付通道）
- 秒杀系统（限流 + 熔断兜底）

## 5. 分布式 ID 生成方案有哪些？雪花算法的时钟回拨问题如何解决？

**深度答案：**

### 方案对比

| 方案 | 唯一性 | 有序性 | 可用性 | 适用场景 |
|------|--------|--------|--------|----------|
| UUID | 是 | 否 | 高 | 日志追踪、非有序场景 |
| 数据库自增 | 是 | 是 | 低 | 低并发、简单场景 |
| Redis INCR | 是 | 是 | 中 | 中等并发 |
| 雪花算法 | 是 | 是 | 高 | 通用场景 |
| Leaf | 是 | 是 | 高 | 大厂生产环境 |

### 雪花算法（Snowflake）
```
┌─────────────────────────────────────────────────────────────────┐
│ 0 │ 41位时间戳 │ 5位数据中心 │ 5位机器ID │ 12位序列号 │
└─────────────────────────────────────────────────────────────────┘
```
- **时间戳**：毫秒级，69年不重复
- **数据中心 + 机器ID**：支持 1024 个节点
- **序列号**：同一毫秒内支持 4096 个 ID

**时钟回拨问题：**
- **问题**：NTP 同步或闰秒导致时钟回拨，可能生成重复 ID
- **解决方案**：
  1. **拒绝服务**：检测到回拨直接抛异常
  2. **等待追回**：小幅回拨（< 5ms）等待追回
  3. **扩展位**：预留 2-3 位作为回拨标记，支持小范围回拨
  4. **百度 UidGenerator**：预分配一批 ID 到 RingBuffer，不依赖实时时钟

### Leaf（美团）
**号段模式：**
- 数据库存储当前最大 ID 和步长
- 服务启动时预加载一段 ID（如 10001-20000）
- 用完后再加载下一段
- **双 Buffer**：一个 buffer 用到 10% 时，异步加载下一个 buffer，避免阻塞

**雪花模式：**
- 对标准雪花算法的改进
- 引入 ZooKeeper 分配 workerID
- 解决时钟回拨：启动时检查、运行时监控

**架构设计：**
```
┌─────────────────────────────────────────────────────────────┐
│                      Leaf Server                             │
│  ┌─────────────────┐      ┌─────────────────┐              │
│  │  号段模式        │      │  雪花模式        │              │
│  │  ┌───────────┐  │      │  ┌───────────┐  │              │
│  │  │ Buffer 1  │  │      │  │ ZK分配ID  │  │              │
│  │  └───────────┘  │      │  └───────────┘  │              │
│  │  ┌───────────┐  │      │  ┌───────────┐  │              │
│  │  │ Buffer 2  │  │      │  │ 时钟检查  │  │              │
│  │  └───────────┘  │      │  └───────────┘  │              │
│  └─────────────────┘      └─────────────────┘              │
└─────────────────────────────────────────────────────────────┘
```

**面试亮点：**
- 能否说清雪花算法的位分配和生成过程
- 是否理解时钟回拨的原因和解决方案
- 是否知道 Leaf 双 Buffer 的设计思想

**实战场景：**
- 订单号生成（雪花算法）
- 流水号生成（Leaf 号段模式）
- 分布式日志追踪（UUID）

## 6. 缓存与数据库一致性如何保证？Cache Aside / Read Through / Write Behind 有什么区别？

**深度答案：**

### Cache Aside（旁路缓存）
```
读：先读缓存 → 命中返回 → 未命中读 DB → 写入缓存 → 返回
写：更新 DB → 删除缓存（而非更新）
```
- **为什么删除而不是更新？**
  - 避免并发写导致缓存脏数据
  - 更新缓存可能触发不必要的计算
- **延迟双删**：更新 DB 后，延迟一段时间再删缓存，覆盖主从延迟

### Read Through（读穿透）
```
读：先读缓存 → 缓存自动回源 DB → 加载到缓存 → 返回
写：更新 DB → 删除缓存
```
- 缓存层封装了回源逻辑，应用层只和缓存交互
- 适用于缓存框架支持的场景（如 Guava Cache、Caffeine）

### Write Behind（异步写回）
```
写：更新缓存 → 异步批量写入 DB
```
- **优点**：写性能极高，可合并写操作
- **缺点**：数据可能丢失，一致性最弱
- **适用**：对一致性要求不高的场景（如计数器、浏览量）

### 一致性问题场景分析

**先更新 DB，再删除缓存：**
- 并发场景：读请求读到旧缓存 → 写请求更新 DB → 写请求删缓存 → 读请求写入旧缓存
- **解决方案**：延迟双删、消息队列异步删除

**先删除缓存，再更新 DB：**
- 并发场景：删缓存 → 读请求读 DB 旧值写入缓存 → 写请求更新 DB
- **问题更严重**，不推荐

**最终方案：**
```
更新 DB → 删除缓存 → 消息队列兜底删除 → 订阅 Binlog 异步更新
```

**面试亮点：**
- 能否说清各模式的优缺点和适用场景
- 是否理解为什么"先更新 DB，再删缓存"
- 是否知道 Canal 订阅 Binlog 的方案

**实战场景：**
- 电商商品信息（Cache Aside + 延迟双删）
- 用户会话信息（Read Through）
- 文章浏览量（Write Behind）

## 7. 大表 DDL 如何在线执行？pt-osc / gh-ost / MySQL 8.0 Instant DDL 有什么区别？

**深度答案：**

### 问题背景
- MySQL 5.6 之前，ALTER TABLE 会锁表，阻塞读写
- 大表（千万级）DDL 可能耗时数小时，严重影响业务

### pt-osc（Percona Toolkit）
```
1. 创建新表（结构相同）
2. 在新表上执行 DDL
3. 创建触发器：旧表的 INSERT/UPDATE/DELETE 同步到新表
4. 分批拷贝旧数据到新表
5. 数据同步完成后，原子 RENAME 切换
```
- **优点**：成熟稳定，社区广泛使用
- **缺点**：触发器开销大，写入量大时影响性能
- **限制**：不能用于已有触发器的表

### gh-ost（GitHub）
```
1. 创建新表（结构相同）
2. 创建 Binlog 流监听（伪装从库）
3. 分批拷贝旧数据到新表
4. 通过 Binlog 应用增量变更
5. 数据同步完成后，原子 RENAME 切换
```
- **优点**：无触发器，对主库影响小；可动态调整限流
- **缺点**：依赖 Binlog，需开启 row 格式
- **适用**：写入量大、对主库性能敏感的场景

### MySQL 8.0 Instant DDL
- **原理**：某些 DDL 操作只修改元数据，不重建表
- **支持的操作**：
  - 添加列（在最后）
  - 删除列
  - 修改列顺序
  - 修改列默认值
- **限制**：不支持修改列类型、添加索引
- **性能**：毫秒级完成

### 方案对比

| 方案 | 锁表 | 触发器 | Binlog | 性能影响 | 适用场景 |
|------|------|--------|--------|----------|----------|
| pt-osc | 否 | 是 | 否 | 中 | 通用场景 |
| gh-ost | 否 | 否 | 是 | 低 | 写入量大 |
| Instant | 否 | 否 | 否 | 无 | MySQL 8.0 特定操作 |

**面试亮点：**
- 能否说清 pt-osc 和 gh-ost 的实现原理差异
- 是否理解为什么 gh-ost 对主库影响更小
- 是否知道 Instant DDL 的限制

**实战场景：**
- 电商订单表新增字段（gh-ost）
- 用户表添加索引（pt-osc）
- 日志表修改列类型（gh-ost）

## 8. 接口幂等性如何实现？Token 机制、唯一索引、状态机各有什么优缺点？

**深度答案：**

### Token 机制
```
1. 客户端申请 Token（服务端生成唯一 Token，存入 Redis）
2. 客户端携带 Token 请求接口
3. 服务端检查 Token 存在性 → 存在则删除并处理 → 不存在则拒绝
```
- **优点**：简单可靠，适用于所有场景
- **缺点**：多一次请求获取 Token，增加 RT
- **优化**：页面加载时预获取 Token

### 唯一索引
```
1. 请求携带唯一业务ID（如订单号）
2. 插入时利用数据库唯一约束去重
3. 重复请求捕获 DuplicateKeyException，返回成功
```
- **优点**：实现简单，无需额外存储
- **缺点**：仅适用于插入场景，更新场景不适用
- **适用**：创建订单、创建支付流水

### 状态机
```
1. 定义状态流转规则（如：CREATED → PAID → SHIPPED）
2. 更新时检查当前状态是否符合预期
3. 符合则更新，不符合则返回成功（幂等）
```
- **优点**：天然幂等，支持更新场景
- **缺点**：需设计状态机，业务侵入
- **适用**：订单状态、退款状态

### 乐观锁
```
UPDATE table SET ..., version = version + 1 WHERE id = ? AND version = ?
```
- **优点**：适用于更新场景，无需额外存储
- **缺点**：需维护版本号，冲突时重试

## 9. 读写分离架构的主从延迟如何处理？

**深度答案：**

### 主从延迟原因
- **网络延迟**：主从之间的网络往返
- **从库单线程回放**：MySQL 5.6 之前 Binlog 回放是单线程
- **大事务**：大表 DDL、批量更新阻塞回放
- **从库负载**：从库承担读压力，影响回放速度

### 解决方案

**1. 强制走主库**
- 关键业务（如支付、下单）强制读主库
- 实现：注解标记、路由规则
- 缺点：主库压力增大

**2. 延迟判断**
- 检查从库 GTID/位点，判断是否追上主库
- 未追上则等待或走主库
- 实现：`SHOW SLAVE STATUS` 检查 `Seconds_Behind_Master`

**3. 半同步复制**
- 主库等待至少一个从库确认收到 Binlog 后才返回
- 保证主从数据强一致
- 缺点：写入延迟增加

**4. 并行复制**
- MySQL 5.7+ 支持基于组提交的并行复制
- 从库多线程回放，减少延迟

**5. 中间件路由**
- ShardingSphere、MyCat 等中间件自动路由
- 根据 SQL 类型、事务状态自动选择主从

**6. 缓存路由**
- 写入后将记录标识存入 Redis（TTL = 预估延迟时间）
- 读取时检查标识，存在则走主库

**架构设计：**
```

│                      Application                             │
│  ┌─────────────────┐      ┌─────────────────┐              │
│  │   写请求         │      │   读请求         │              │
│  └────────┬────────┘      └────────┬────────┘              │
│           │                        │                        │
│           ▼                        ▼                        │
```

## 10. 微服务拆分的判断标准是什么？如何避免过度拆分？

**深度答案：**

### 拆分判断标准

**1. 业务边界**
- 按领域驱动设计（DDD）划分限界上下文
- 每个服务对应一个业务领域
- 示例：订单服务、库存服务、支付服务

**2. 团队结构**
- 康威定律：系统架构反映组织沟通结构
- 每个服务由一个团队负责（2-pizza team）
- 避免跨团队依赖

**3. 变更频率**
- 变更频繁的功能独立为服务
- 稳定的功能可以合并
- 示例：商品详情（稳定） vs 促销活动（频繁变更）

**4. 性能要求**
- 高并发功能独立部署、独立扩缩容
- 示例：秒杀服务独立于普通订单服务

**5. 数据独立性**
- 每个服务拥有独立的数据存储
- 避免跨服务 join 查询
- 示例：订单库、用户库、商品库分离

### 过度拆分的信号

- 服务间调用链路过长（> 5 层）
- 分布式事务频繁出现
- 单个功能需要修改多个服务
- 服务数量超过团队维护能力
- 大量跨服务 join 或数据同步

### 拆分策略

**1. 绞杀者模式**
- 新功能用新服务实现
- 逐步将旧功能迁移到新服务
- 适合遗留系统改造

**2. 分支 by abstraction**
- 在旧代码中引入抽象层
- 新服务实现相同接口
- 切换流量到新服务

**3. 数据库拆分**
- 先拆分数据库（垂直分库）
- 再拆分应用服务
- 避免分布式 join

- 是否知道过度拆分的信号和应对策略

**实战场景：**

- 电商系统按业务域拆分
- 金融系统按合规要求拆分

**深度答案：**

### 核心概念

**Trace（链路）**：一次完整的请求调用链
**Span（跨度）**：一次方法调用或 RPC 请求
**TraceId**：全局唯一标识，贯穿整个链路
**SpanId**：当前 Span 的唯一标识
**ParentSpanId**：父 Span 的标识，形成树形结构

### 实现原理

**1. 上下文传播**

```
│                      Context Propagation                     │

│       ▼               ▼               ▼                     │

└─────────────────────────────────────────────────────────────┘
```

- **HTTP Header**：`traceparent: 00-abc123-span1-01`

## 12. 灰度发布有哪些实现方案？如何保证新老版本兼容？

**深度答案：**

### 灰度策略

**1. 基于流量比例**
- 随机分流：1% → 5% → 20% → 100%
- 实现：负载均衡器权重配置
- 适用：新功能逐步放量

- 白名单：内部用户、VIP 用户优先
- 用户 ID 范围：尾号 0-9 逐步放量
- 地域：先灰度部分地区

**3. 基于请求特征**
- Header 标记：`X-Gray-Version: v2`
- 参数标记：`?gray=true`
- Cookie 标记：`gray_user=1`

**4. 基于业务属性**
- 商品类型：先灰度虚拟商品
- 订单金额：先灰度小额订单
- 支付方式：先灰度某种支付方式

### 实现方案

**1. Nginx 分流**
```nginx
upstream backend {
    server 10.0.0.1:8080 weight=90;  # 旧版本
    server 10.0.0.2:8080 weight=10;  # 新版本
}
```

**2. 网关路由**
```java
// Spring Cloud Gateway
@Bean
public RouteLocator routes(RouteLocatorBuilder builder) {
    return builder.routes()
        .route("gray", r -> r.header("X-Gray-Version", "v2")
            .filters(f -> f.setPath("/api/v2"))
            .uri("lb://service-v2"))
        .build();
}
```

**3. 服务网格（Istio）**
```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
spec:
  http:
  - match:
    - headers:
        x-gray-version:
          exact: v2
    route:
    - destination:
        host: service-v2
  - route:
    - destination:
        host: service-v1
```

### 版本兼容策略

**1. 数据库兼容**
- 新版本先兼容旧字段
- 灰度完成后再清理旧字段
- 使用默认值处理 null

**2. 接口兼容**
- 新字段可选，旧字段保留
- 版本号区分：`/api/v1/` vs `/api/v2/`
- 返回值增加版本字段

**3. 缓存兼容**
- 缓存 key 增加版本标记
- 灰度期间新老版本缓存隔离
- 全量后清理旧缓存

## 14. 如何设计一个分布式锁？Redis、ZooKeeper、Etcd 各有什么优缺点？

**深度答案：**

### Redis 分布式锁

**实现方式：**
```lua
-- 加锁
SET resource_name my_random_value NX PX 30000

-- 释放锁（Lua 脚本保证原子性）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**优点：**
- 性能高（毫秒级）
- 实现简单
- 社区成熟（Redisson）

**缺点：**
- 主从切换可能丢失锁
- 锁续期需要额外机制（Watch Dog）
- 单点故障风险

### ZooKeeper 分布式锁

**实现方式：**
```
1. 创建临时顺序节点 /lock/resource-0001
2. 获取 /lock 下所有子节点
3. 判断是否是最小节点
4. 是则获取锁，否则监听前一个节点
5. 释放锁时删除节点
```

**优点：**
- 强一致性（ZAB 协议）
- 自动清理（临时节点）
- 公平锁（顺序节点）

**缺点：**
- 性能较低（毫秒级）
- 依赖 ZooKeeper 集群
- 惊群效应（需优化）

### Etcd 分布式锁

**实现方式：**
```
1. 创建 Lease（带 TTL）
2. PUT key with Lease（CAS 操作）
3. 成功则获取锁
4. 定期续租 Lease
5. 释放锁时删除 key + revoke Lease
```

**优点：**
- 强一致性（Raft 协议）
- 性能优于 ZooKeeper
- 原生支持 Lease

**缺点：**
- 社区相对较小
- 运维成本

### 方案对比

| 特性 | Redis | ZooKeeper | Etcd |
|------|-------|-----------|------|
| 一致性 | 弱 | 强 | 强 |
| 性能 | 最高 | 中 | 高 |
| 可用性 | 高 | 中 | 高 |
| 实现复杂度 | 低 | 中 | 中 |
| 适用场景 | 高并发 | 强一致 | 通用 |

**面试亮点：**
- 能否说清各方案的实现原理和权衡
- 是否理解 Redis 锁的续期机制
- 是否知道 ZooKeeper 的惊群效应

**实战场景：**
- 秒杀库存扣减（Redis）
- 分布式任务调度（ZooKeeper）
- 配置中心锁（Etcd）

```
│  │  │  MySQL   │  │  MongoDB │  │  HBase   │              ││

│  └─────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────┘
```

### 缓存穿透

**问题：** 查询不存在的数据，每次都穿透到数据库

**解决方案：**
1. **布隆过滤器**：预加载所有有效 key，不存在的 key 直接返回
2. **空值缓存**：查询结果为空时缓存空值（设置较短 TTL）
3. **参数校验**：非法参数直接返回

### 缓存击穿

**问题：** 热点 key 过期，大量请求同时穿透到数据库

**解决方案：**
1. **互斥锁**：只允许一个请求回源，其他等待
2. **热点数据永不过期**：异步更新缓存
3. **逻辑过期**：缓存记录过期时间，由后台线程更新

### 缓存雪崩

**问题：** 大量 key 同时过期，请求全部打到数据库

**解决方案：**
1. **随机过期时间**：避免同时过期
2. **多级缓存**：L1 本地缓存 + L2 分布式缓存
3. **限流降级**：数据库压力大时返回默认值
4. **缓存预热**：系统启动时加载热点数据

### 缓存一致性

**方案选择：**
- **Cache Aside**：先更新 DB，再删除缓存
- **Read Through**：缓存层封装回源逻辑
- **Write Behind**：异步写入 DB

**面试亮点：**
- 能否说清穿透、击穿、雪崩的区别和解决方案
- 是否理解布隆过滤器的原理和误判率
- 是否知道多级缓存的设计

- 用户会话缓存
- 热门搜索缓存

# 订单专题

> 适用场景：电商平台、O2O、SaaS 订单中台、交易中心
> 核心考点：状态机设计、幂等创建、超时取消、拆单合单、分布式事务、退款逆向

---

## 一、订单模型设计篇

### Q1：订单表怎么设计？为什么要有主订单和子订单？

> **深度回答**：
>
> **两层订单模型**：
>
> ```sql
> CREATE TABLE order_main (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     order_no VARCHAR(64) NOT NULL UNIQUE COMMENT '主订单号（幂等键）',
>     user_id BIGINT NOT NULL COMMENT '下单用户ID',
>     order_status TINYINT NOT NULL DEFAULT 0 COMMENT '订单状态',
>     total_amount DECIMAL(12,2) NOT NULL COMMENT '商品总金额',
>     discount_amount DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '优惠金额',
>     freight_amount DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '运费',
>     payable_amount DECIMAL(12,2) NOT NULL COMMENT '应付金额 = total - discount + freight',
>     payment_no VARCHAR(64) COMMENT '支付单号',
>     pay_time DATETIME COMMENT '支付时间',
>     receiver_name VARCHAR(64) COMMENT '收货人',
>     receiver_phone VARCHAR(20) COMMENT '收货电话',
>     receiver_address VARCHAR(512) COMMENT '收货地址',
>     remark VARCHAR(256) COMMENT '订单备注',
>     expire_time DATETIME NOT NULL COMMENT '支付截止时间',
>     version INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_user_id (user_id),
>     INDEX idx_order_status (order_status),
>     INDEX idx_create_time (create_time),
>     INDEX idx_expire_time (expire_time)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='主订单表';
>
> CREATE TABLE order_sub (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     sub_order_no VARCHAR(64) NOT NULL UNIQUE COMMENT '子订单号',
>     order_no VARCHAR(64) NOT NULL COMMENT '所属主订单号',
>     shop_id BIGINT NOT NULL COMMENT '店铺/商户ID',
>     sub_status TINYINT NOT NULL DEFAULT 0 COMMENT '子订单状态',
>     sub_amount DECIMAL(12,2) NOT NULL COMMENT '子订单金额',
>     freight_amount DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '运费',
>     logistics_no VARCHAR(64) COMMENT '物流单号',
>     ship_time DATETIME COMMENT '发货时间',
>     receive_time DATETIME COMMENT '收货时间',
>     version INT NOT NULL DEFAULT 0,
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_order_no (order_no),
>     INDEX idx_shop_id (shop_id)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='子订单表';
>
> CREATE TABLE order_item (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     sub_order_no VARCHAR(64) NOT NULL COMMENT '所属子订单号',
>     sku_id BIGINT NOT NULL COMMENT '商品SKU ID',
>     sku_name VARCHAR(256) NOT NULL COMMENT '商品名称（快照）',
>     sku_attrs VARCHAR(256) COMMENT '规格属性（快照）',
>     unit_price DECIMAL(10,2) NOT NULL COMMENT '成交单价（快照）',
>     quantity INT NOT NULL COMMENT '购买数量',
>     line_amount DECIMAL(12,2) NOT NULL COMMENT '行金额 = unit_price * quantity',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     INDEX idx_sub_order_no (sub_order_no),
>     INDEX idx_sku_id (sku_id)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单商品明细表';
> ```
>
> **为什么需要主订单 + 子订单？**
>
> | 场景 | 主订单职责 | 子订单职责 |
> |------|-----------|-----------|
> | 用户下单买了3个店铺的商品 | 承载用户维度信息（收货地址、支付、优惠） | 每个店铺一个子订单，独立发货、独立确认收货 |
> | 退款只退其中一个店铺 | 主订单状态不变 | 对应子订单进入退款流程 |
> | 对账结算 | 主订单对用户（支付维度） | 子订单对商户（结算维度） |
>
> **设计亮点**：
> 1. **商品快照**：`sku_name`、`sku_attrs`、`unit_price` 都是下单时的快照，商品改价不影响历史订单
> 2. **金额拆分**：`payable_amount = total_amount - discount_amount + freight_amount`，入参金额由服务端计算，不信任前端
> 3. **过期时间**：`expire_time` 用于未支付订单超时自动取消
>
> **面试追问**：为什么不把收货地址放在子订单？
>
> 同一次下单的所有子订单共享收货地址，放在主订单避免冗余。如果用户需要拆分地址，那就是两次独立下单。

### Q2：订单状态机怎么设计？主订单和子订单的状态怎么联动？

> **深度回答**：
>
> **主订单状态机**：
>
> ```
> ┌────────┐   支付成功   ┌────────┐   全部发货   ┌────────┐   全部收货   ┌────────┐
> │ 待支付  │ ─────────→ │ 已支付  │ ─────────→ │ 已发货  │ ─────────→ │ 已完成  │
> │PENDING │            │ PAID   │            │SHIPPED │            │COMPLETED│
> └────────┘            └────────┘            └────────┘            └────────┘
>     │                     │                     │                     │
>     │ 超时/取消           │ 申请退款             │ 申请退款             │ 申请售后
>     ↓                     ↓                     ↓                     ↓
> ┌────────┐            ┌────────┐            ┌────────┐            ┌────────┐
> │ 已取消  │            │ 退款中  │            │ 退款中  │            │ 售后中  │
> │CANCELLED│           │REFUNDING│           │REFUNDING│           │AFTER_SALE│
> └────────┘            └────────┘            └────────┘            └────────┘
>                              │                     │
>                              │ 退款成功             │ 退款成功
>                              ↓                     ↓
>                         ┌────────┐            ┌────────┐
>                         │ 已退款  │            │ 已退款  │
>                         │REFUNDED│            │REFUNDED│
>                         └────────┘            └────────┘
> ```
>
> **子订单状态机**（独立于主订单）：
>
> ```
> 待支付 → 已支付 → 待发货 → 已发货 → 已收货 → 已完成
>    ↓        ↓        ↓        ↓        ↓
> 已取消   已退款   已退款   已退款   售后中 → 已退款
> ```
>
> **主子订单状态联动规则**：
>
> | 子订单事件 | 主订单状态变更规则 |
> |-----------|-------------------|
> | 某子订单支付 | 主订单：待支付→已支付（只要有1个子订单支付） |
> | 某子订单取消 | 主订单：若所有子订单都取消，主订单也取消 |
> | 某子订单发货 | 主订单：已支付→部分发货/已发货（看其他子订单） |
> | 某子订单退款 | 主订单：根据其他子订单状态判断 |
>
> **状态变更的原子性**：
> ```java
> @Transactional
> public void updateSubOrderStatus(String subOrderNo, int targetStatus) {
>     // 1. 更新子订单状态（乐观锁）
>     int rows = orderSubMapper.updateStatus(subOrderNo, targetStatus, currentStatus, version);
>     if (rows == 0) throw new ConcurrentModificationException("状态已变更");
>
>     // 2. 检查所有子订单状态，计算主订单应有状态
>     int newMainStatus = calculateMainStatus(orderNo);
>
>     // 3. 更新主订单状态（乐观锁）
>     orderMainMapper.updateStatus(orderNo, newMainStatus, currentMainVersion);
> }
> ```
>
> **面试追问**：为什么不用事件驱动更新主订单状态？
>
> 事件驱动有延迟，且消息可能丢失。直接在同一事务内更新主子订单状态，保证强一致。事件驱动适合跨服务通知（如通知物流系统），不适合同一服务内的状态联动。

### Q3：订单创建怎么保证幂等？重复提交怎么处理？

> **深度回答**：
>
> **三层幂等保障**：
>
> ```
> 前端防抖（按钮置灰）
>    ↓
> 网关层幂等（请求唯一ID去重）
>    ↓
> 服务层幂等（订单号唯一约束）
> ```
>
> **服务层幂等实现**：
> ```java
> public String createOrder(CreateOrderRequest request) {
>     // 1. 幂等检查：同一请求ID是否已创建订单
>     String idempotentKey = "order:create:" + request.getRequestId();
>     String existingOrderNo = redis.get(idempotentKey);
>     if (existingOrderNo != null) {
>         return existingOrderNo; // 直接返回已有订单号
>     }
>
>     // 2. 分布式锁防并发
>     String lockKey = "lock:order:create:" + request.getUserId();
>     boolean locked = redisLock.tryLock(lockKey, 10, TimeUnit.SECONDS);
>     if (!locked) throw new BizException("请勿重复提交");
>
>     try {
>         // 3. 再次检查（双重检查）
>         existingOrderNo = redis.get(idempotentKey);
>         if (existingOrderNo != null) return existingOrderNo;
>
>         // 4. 计算金额（服务端计算，不信任前端）
>         OrderPriceResult price = priceService.calculate(request.getItems());
>
>         // 5. 扣减库存（预扣）
>         stockService.deduct(request.getItems());
>
>         // 6. 创建订单
>         String orderNo = generateOrderNo();
>         OrderMain order = buildOrder(request, price, orderNo);
>         orderMainMapper.insert(order);
>
>         // 7. 设置幂等标记（TTL = 订单过期时间 + 缓冲）
>         redis.setex(idempotentKey, 35 * 60, orderNo);
>
>         // 8. 发送延迟消息，30分钟未支付自动取消
>         mqProducer.sendDelayMessage("order.expire", orderNo, 30, TimeUnit.MINUTES);
>
>         return orderNo;
>     } finally {
>         redisLock.unlock(lockKey);
>     }
> }
> ```
>
> **关键设计点**：
>
> | 设计点 | 方案 | 原因 |
> |--------|------|------|
> | 请求ID幂等 | Redis + 唯一约束 | 防止网络重试导致重复创建 |
> | 分布式锁 | Redis SETNX | 防止同一用户并发下单 |
> | 金额服务端计算 | 下单前重新查询价格 | 防止前端篡改价格 |
> | 库存预扣 | 先扣库存再创建订单 | 防止超卖 |
> | 延迟取消 | RocketMQ 延迟消息 | 未支付订单自动释放库存 |
>
> **面试追问**：为什么库存先扣再创建订单？如果订单创建失败，库存怎么回滚？
>
> 这是 TCC 模式：
> - Try：扣减库存（预留）
> - Confirm：订单创建成功，库存确认扣减
> - Cancel：订单创建失败，库存回滚
>
> 如果用最终一致性，可以先创建订单（状态=待确认），再异步扣库存，扣失败则取消订单。

### Q4：超时未支付订单怎么自动取消？

> **深度回答**：
>
> **三种方案对比**：
>
> | 方案 | 实现 | 优点 | 缺点 |
> |------|------|------|------|
> | **定时任务扫表** | 每分钟扫描 `expire_time < NOW() AND status = PENDING` | 简单 | 有延迟，高并发下扫描压力大 |
> | **RocketMQ 延迟消息** | 下单时发送延迟30分钟的消息，消费时取消 | 实时性好 | 消息可能丢失（需兜底） |
> | **Redis 过期回调** | SET key TTL=30min，过期时触发回调 | 实时 | Redis 不保证可靠回调，key 可能被驱逐 |
>
> **推荐方案：延迟消息 + 定时任务兜底**
>
> ```java
> // 1. 下单时发送延迟消息
> public void sendExpireMessage(String orderNo, int delayMinutes) {
>     Message message = new Message("ORDER_EXPIRE_TOPIC", orderNo.getBytes());
>     // RocketMQ 延迟级别：1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
>     message.setDelayTimeLevel(16); // 30分钟
>     producer.send(message);
> }
>
> // 2. 消费延迟消息
> @RocketMQMessageListener(topic = "ORDER_EXPIRE_TOPIC")
> public void handleExpire(OrderExpireMessage msg) {
>     String orderNo = msg.getOrderNo();
>     OrderMain order = orderMainMapper.selectByOrderNo(orderNo);
>
>     // 只有待支付状态才取消
>     if (order != null && order.getOrderStatus() == OrderStatus.PENDING) {
>         cancelOrder(orderNo, "超时未支付自动取消");
>     }
> }
>
> // 3. 兜底定时任务（每5分钟执行）
> @Scheduled(cron = "0 */5 * * * ?")
> public void scanExpiredOrders() {
>     List<String> expiredOrders = orderMainMapper.selectExpiredOrders(
>         OrderStatus.PENDING, LocalDateTime.now(), 100
>     );
>     for (String orderNo : expiredOrders) {
>         cancelOrder(orderNo, "定时任务兜底取消");
>     }
> }
> ```
>
> **取消订单的逆向流程**：
> ```java
> @Transactional
> public void cancelOrder(String orderNo, String reason) {
>     // 1. 更新订单状态（乐观锁，只取消待支付订单）
>     int rows = orderMainMapper.updateStatus(orderNo, OrderStatus.CANCELLED,
>                                              OrderStatus.PENDING, version);
>     if (rows == 0) return; // 状态已变更，跳过
>
>     // 2. 回滚库存
>     stockService.rollback(orderNo);
>
>     // 3. 释放优惠券（如果用了优惠券）
>     couponService.release(orderNo);
>
>     // 4. 记录取消原因
>     orderLogService.log(orderNo, "CANCEL", reason);
> }
> ```
>
> **面试追问**：延迟消息丢了怎么办？
>
> 定时任务兜底。延迟消息负责实时取消（用户体验好），定时任务负责兜底扫描（保证最终一致）。两者不冲突，取消操作本身是幂等的（乐观锁保证）。

### Q5：价格计算怎么做？优惠券、满减、折扣怎么叠加？

> **深度回答**：
>
> **价格计算链**：
>
> ```
> 原价（商品单价 × 数量）
>   ↓ 满减优惠
>   ↓ 折扣优惠
>   ↓ 优惠券抵扣
>   ↓ 积分抵扣
>   ↓ 运费计算
> = 最终应付金额
> ```
>
> **计算顺序很重要**（不同顺序结果不同）：
>
> | 顺序 | 原价 | 满减(满200减20) | 折扣(8折) | 优惠券(50元) | 最终 |
> |------|------|----------------|-----------|-------------|------|
> | 满减→折扣→券 | 300 | 280 | 224 | 174 | 174 |
> | 折扣→满减→券 | 300 | 240 | 220 | 170 | 170 |
>
> **设计原则**：计算顺序由运营后台配置，代码不硬编码。
>
> ```java
> /**
>  * 价格计算引擎，按优先级链式执行优惠规则。
>  */
> public class PriceCalculationEngine {
>
>     private final List<DiscountRule> rules; // 按优先级排序
>
>     public PriceResult calculate(CartContext context) {
>         BigDecimal originalPrice = context.getTotalPrice();
>         BigDecimal currentPrice = originalPrice;
>         List<DiscountDetail> details = new ArrayList<>();
>
>         // 按优先级依次执行优惠规则
>         for (DiscountRule rule : rules) {
>             if (rule.isApplicable(context, currentPrice)) {
>                 DiscountDetail detail = rule.apply(context, currentPrice);
>                 currentPrice = currentPrice.subtract(detail.getDiscountAmount());
>                 details.add(detail);
>             }
>         }
>
>         // 最终金额不能为负
>         currentPrice = currentPrice.max(BigDecimal.ZERO);
>
>         return new PriceResult(originalPrice, currentPrice, details);
>     }
> }
> ```
>
> **防篡改设计**：价格计算结果存储在服务端，前端只展示，支付时重新校验。
>
> ```java
> // 下单时：计算价格，存储快照
> PriceResult price = priceEngine.calculate(cartContext);
> order.setPayableAmount(price.getFinalPrice());
> // 存储价格明细到 Redis，key = orderNo
> redis.setex("order:price:" + orderNo, 35 * 60, JSON.toJSONString(price));
>
> // 支付回调时：校验金额一致性
> PriceResult cachedPrice = redis.get("order:price:" + orderNo);
> if (!cachedPrice.getFinalPrice().equals(paymentAmount)) {
>     throw new BizException("金额不一致，疑似篡改");
> }
> ```
>
> **面试追问**：优惠券并发扣减怎么防超发？
>
> Redis 原子扣减 + 数据库兜底（乐观锁）。
> ```lua
> -- Lua 脚本原子扣减优惠券
> local stock = redis.call('hget', KEYS[1], 'stock')
> if stock and tonumber(stock) > 0 then
>     redis.call('hincrby', KEYS[1], 'stock', -1)
>     return 1
> end
> return 0
> ```

### Q6：拆单规则是什么？什么时候拆、怎么拆？

> **深度回答**：
>
> **拆单时机**：订单创建后、支付前，根据业务规则拆分为多个子订单。
>
> **拆单规则**：
>
> | 规则 | 说明 | 示例 |
> |------|------|------|
> | **商户维度** | 不同店铺的商品拆成不同子订单 | 淘宝跨店购物 |
> | **仓库维度** | 不同仓库发货的商品拆开 | 京东自营多仓发货 |
> | **物流维度** | 大件和小件分开（大件走物流，小件走快递） | 家具 + 配件 |
> | **业务类型** | 实物商品和虚拟商品分开 | 手机 + 话费充值 |
> | **支付方式** | 需要分期的商品单独拆出 | 苹果官网分期 |
>
> **拆单流程**：
>
> ```
> 购物车商品列表
>      ↓
> ┌──────────────────────────────────────┐
> │ 拆单引擎                              │
> │  rule1: 按商户分组                    │
> │  rule2: 按仓库分组                    │
> │  rule3: 按物流方式分组                 │
> │  ...（规则可配置）                    │
> └──────────────────────────────────────┘
>      ↓
> 子订单1（店铺A）  子订单2（店铺B）  子订单3（虚拟商品）
> ```
>
> **拆单后的金额分摊**：
>
> 优惠金额需要按比例分摊到子订单，避免精度丢失。
>
> ```java
> /**
>  * 按比例分摊优惠金额，最后一单吸收尾差。
>  */
> public List<BigDecimal> allocateDiscount(BigDecimal totalDiscount, List<BigDecimal> subAmounts) {
>     BigDecimal total = subAmounts.stream().reduce(BigDecimal.ZERO, BigDecimal::add);
>     List<BigDecimal> result = new ArrayList<>();
>     BigDecimal allocated = BigDecimal.ZERO;
>
>     for (int i = 0; i < subAmounts.size(); i++) {
>         if (i == subAmounts.size() - 1) {
>             // 最后一单：总优惠 - 已分摊 = 剩余（吸收尾差）
>             result.add(totalDiscount.subtract(allocated));
>         } else {
>             // 按比例分摊
>             BigDecimal ratio = subAmounts.get(i).divide(total, 10, RoundingMode.HALF_UP);
>             BigDecimal discount = totalDiscount.multiply(ratio).setScale(2, RoundingMode.HALF_UP);
>             result.add(discount);
>             allocated = allocated.add(discount);
>         }
>     }
>     return result;
> }
> ```
>
> **面试追问**：拆单后退款怎么处理？
>
> 子订单独立退款。退款金额 = 该子订单实付金额（已分摊的优惠不退）。主订单维度看，只有所有子订单都退款成功，主订单才变为"已退款"。

### Q7：下单和扣库存的顺序是什么？怎么防止超卖？

> **深度回答**：
>
> **三种模式对比**：
>
> | 模式 | 流程 | 优点 | 缺点 | 适用场景 |
> |------|------|------|------|----------|
> | **下单减库存** | 创建订单 → 扣库存 | 不会超卖 | 恶意下单锁库存 | 普通商品 |
> | **支付减库存** | 创建订单 → 支付 → 扣库存 | 库存精准 | 可能超卖 | 虚拟商品 |
> | **预扣库存** | Redis预扣 → 创建订单 → 支付确认/回滚 | 兼顾安全和体验 | 复杂 | 秒杀/高并发 |
>
> **推荐：预扣库存（TCC 模式）**
>
> ```java
> /**
>  * 库存扣减服务，实现 TCC 三阶段。
>  */
> public class StockTccService {
>
>     // Try：预扣库存（冻结）
>     public boolean tryDeduct(String orderNo, List<StockItem> items) {
>         for (StockItem item : items) {
>             // 可用库存 >= 数量，且冻结库存 + 数量 <= 总库存
>             int rows = stockMapper.freeze(
>                 item.getSkuId(), item.getQuantity()
>             );
>             if (rows == 0) return false; // 库存不足
>         }
>         return true;
>     }
>
>     // Confirm：确认扣减（冻结转实扣）
>     public void confirmDeduct(String orderNo) {
>         stockMapper.confirmFreeze(orderNo);
>     }
>
>     // Cancel：回滚（释放冻结）
>     public void cancelDeduct(String orderNo) {
>         stockMapper.releaseFreeze(orderNo);
>     }
> }
> ```
>
> **库存表设计**：
> ```sql
> CREATE TABLE stock (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     sku_id BIGINT NOT NULL UNIQUE COMMENT '商品SKU ID',
>     total_stock INT NOT NULL COMMENT '总库存',
>     available_stock INT NOT NULL COMMENT '可用库存 = total - frozen',
>     frozen_stock INT NOT NULL DEFAULT 0 COMMENT '冻结库存（已预扣未确认）',
>     version INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_sku_id (sku_id)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='库存表';
>
> -- 预扣：可用库存扣减，冻结库存增加
> UPDATE stock SET available_stock = available_stock - #{quantity},
>                 frozen_stock = frozen_stock + #{quantity},
>                 version = version + 1
> WHERE sku_id = #{skuId} AND available_stock >= #{quantity} AND version = #{version};
>
> -- 确认：冻结库存扣减
> UPDATE stock SET frozen_stock = frozen_stock - #{quantity},
>                 version = version + 1
> WHERE sku_id = #{skuId} AND frozen_stock >= #{quantity};
>
> -- 回滚：冻结库存扣减，可用库存增加
> UPDATE stock SET frozen_stock = frozen_stock - #{quantity},
>                 available_stock = available_stock + #{quantity},
>                 version = version + 1
> WHERE sku_id = #{skuId} AND frozen_stock >= #{quantity};
> ```
>
> **面试追问**：为什么需要冻结库存？直接扣可用库存不行吗？
>
> 直接扣可用库存，订单取消时需要"加回去"。但"加回去"和"新增库存"在数据库层面无法区分，可能导致库存溢出。冻结库存是预留语义，确认时扣冻结（净减），回滚时扣冻结加可用（净零），语义清晰。

### Q8：订单搜索怎么做？EsSearch 还是数据库？

> **深度回答**：
>
> **方案对比**：
>
> | 方案 | 查询性能 | 数据一致性 | 适用场景 |
> |------|----------|-----------|----------|
> | MySQL + 索引 | 单表千万级 OK | 强一致 | 订单量 < 1000万 |
> | MySQL 分表 + ShardingSphere | 百亿级 OK | 强一致 | 订单量大，查询维度单一 |
> | ES 搜索 | 亿级毫秒 | 最终一致 | 多维度模糊搜索、后台管理 |
> | TiDB | 百亿级 OK | 强一致 | 不想分表，强一致需求 |
>
> **推荐方案：MySQL 分表 + ES 搜索**
>
> ```
> 用户端查询（按订单号、按时间）→ MySQL 分表（主键/索引查询）
> 运营端查询（按状态、金额区间、模糊搜索）→ Elasticsearch
> ```
>
> **ES 同步方案**：
> ```
> 订单变更 → Binlog → Canal → Kafka → ES 同步服务 → Elasticsearch
> ```
>
> **面试追问**：Canal 同步延迟怎么办？
>
> 1. 用户端查 MySQL（强一致），运营端查 ES（最终一致），延迟可接受
> 2. 关键操作（如支付成功后立即查询）走 MySQL
> 3. ES 同步服务失败时有重试机制，保证最终一致

### Q9：退款流程怎么设计？全链路是什么？

> **深度回答**：
>
> **退款状态机**：
>
> ```
> 申请退款 → 商户审核 → 退款处理中 → 退款成功
>    ↓           ↓            ↓
> 审核拒绝    用户撤销      退款失败 → 人工处理
> ```
>
> **退款表设计**：
> ```sql
> CREATE TABLE refund_order (
>     id BIGINT PRIMARY KEY AUTO_INCREMENT,
>     refund_no VARCHAR(64) NOT NULL UNIQUE COMMENT '退款单号',
>     order_no VARCHAR(64) NOT NULL COMMENT '原订单号',
>     sub_order_no VARCHAR(64) COMMENT '子订单号（子订单退款时）',
>     refund_amount DECIMAL(12,2) NOT NULL COMMENT '退款金额',
>     refund_reason VARCHAR(512) NOT NULL COMMENT '退款原因',
>     refund_type TINYINT NOT NULL COMMENT '退款类型：1-仅退款 2-退货退款',
>     refund_status TINYINT NOT NULL DEFAULT 0 COMMENT '状态：0-申请中 1-审核通过 2-退款中 3-成功 4-拒绝',
>     payment_channel VARCHAR(32) COMMENT '原支付渠道',
>     refund_channel VARCHAR(32) COMMENT '退款渠道（原路退回）',
>     create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
>     update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>     INDEX idx_order_no (order_no),
>     INDEX idx_refund_status (refund_status)
> ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='退款单表';
> ```
>
> **退款全链路**：
>
> ```
> 用户申请退款
>     ↓
> 商户审核（可配置自动审核规则：金额<50元自动通过）
>     ↓
> 退款服务：创建退款单
>     ↓
> 调用支付渠道退款接口（支付宝/微信/银联）
>     ↓
> 等待退款回调
>     ↓
> 退款成功 → 更新退款单状态 → 更新订单状态 → 通知用户
> 退款失败 → 重试（最多3次）→ 人工处理
> ```
>
> **面试追问**：退款金额能不能大于原订单金额？
>
> 不能。退款前校验：`退款金额 ≤ 原订单实付金额 - 已退款金额`。部分退款时，优惠券一般不退（或按比例退），运费看业务规则。
>
> **幂等设计**：退款接口幂等键 = 退款单号 + 原支付单号。支付渠道退款接口本身也要求幂等（重复调用返回同一结果）。

### Q10：订单中台怎么设计？和业务系统怎么解耦？

> **深度回答**：
>
> **订单中台定位**：沉淀通用订单能力，支撑多业务线（电商、充值、票务、服务）。
>
> **中台能力分层**：
>
> ```
> 业务系统（电商/充值/票务/服务）
>      ↓ API
> ┌──────────────────────────────────────────────────┐
> │                   订单中台                         │
> ├──────────────────────────────────────────────────┤
> │ 订单创建  │ 状态管理  │ 价格引擎  │ 退款引擎      │
> ├──────────────────────────────────────────────────┤
> │ 拆单引擎  │ 搜索服务  │ 超时管理  │ 数据统计      │
> ├──────────────────────────────────────────────────┤
> │ 订单号生成 │ 幂等框架  │ 扩展字段  │ 事件通知      │
> └──────────────────────────────────────────────────┘
>      ↓
> 下游服务（库存/支付/物流/营销/通知）
> ```
>
> **扩展性设计**：不同业务线的订单有差异化字段，用 JSON 扩展字段解决。
>
> ```sql
> -- 通用订单表 + JSON 扩展字段
> CREATE TABLE order_main (
>     -- 通用字段（所有业务线共享）
>     order_no VARCHAR(64),
>     user_id BIGINT,
>     order_status TINYINT,
>     payable_amount DECIMAL(12,2),
>     -- 业务扩展字段（JSON）
>     biz_extend JSON COMMENT '业务扩展',
>     -- 电商场景：{"receiver_name":"张三","receiver_phone":"138xxx","address":"..."}
>     -- 充值场景：{"phone_number":"138xxx","package_id":"10086"}
>     -- 票务场景：{"event_id":"123","seat_no":"A12","show_time":"2026-08-01 19:30"}
> );
> ```
>
> **面试追问**：订单中台的边界在哪？什么该下沉到中台，什么留在业务系统？
>
> | 下沉到中台 | 留在业务系统 |
> |-----------|-------------|
> | 订单创建、状态管理 | 业务特有的校验规则 |
> | 价格计算框架 | 具体的优惠策略 |
> | 超时取消、退款框架 | 业务特有的退款规则 |
> | 订单号生成、幂等 | 业务特有的扩展逻辑 |
>
> 原则：**流程下沉，策略上浮**。中台提供流程骨架，业务系统注入策略实现。

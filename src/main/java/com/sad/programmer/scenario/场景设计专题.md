## 01. 短链接系统

### 场景描述

设计一个类似 bit.ly 的短链接服务：用户提交长 URL，返回一个短链（如 `https://s.cn/aB3xK9`）；用户访问短链时，重定向到原始 URL。需要支持自定义短码、过期时间、访问统计。日活短链创建量 1000 万，读写比 100:1。

### 核心挑战

1. **短码唯一性**：如何在分布式环境下生成不冲突的短码
2. **高并发读**：99% 的请求是读重定向，如何做到毫秒级响应
3. **过期清理**：海量过期短链如何高效清理而不影响在线服务
4. **302 vs 301**：不同重定向方式对 SEO、统计、缓存的影响

### 设计方案

```
┌──────────────┐
│   Client     │
└──────┬───────┘
       │
       ▼
┌──────────────┐    ┌───────────────┐
│  Nginx/SLB   │───>│  业务服务集群  │
└──────┬───────┘    └───────┬───────┘
       │                    │
       ▼                    ▼
┌──────────────┐    ┌───────────────┐
│  Redis 集群   │    │  MySQL 集群    │
│  (热点缓存)   │    │  (持久存储)    │
└──────────────┘    └───────────────┘
       │                    │
       ▼                    ▼
┌──────────────┐    ┌───────────────┐
│  本地缓存     │    │  异步清理队列  │
│  (LRU Caffeine)│   │  (Kafka+定时) │
└──────────────┘    └───────────────┘
```

**写流程**：客户端提交长 URL → 服务端用分布式 ID 生成器（Snowflake / 号段模式）获取全局唯一 ID → Base62 编码为 6-8 位短码 → 存入 MySQL + 写入 Redis 缓存 → 返回短链。

**读流程**：客户端访问短链 → Nginx 层先查本地缓存 → miss 查 Redis → miss 查 MySQL → 回填缓存 → 302 重定向。

**过期清理**：短链带 TTL 写入 Redis，MySQL 中标记过期时间。后台定时任务扫描过期记录，批量删除 Redis key + 归档 MySQL 记录。清理任务分片执行，避免单点压力。

**架构图描述**：分三层——接入层（Nginx + 本地缓存）、服务层（无状态 Spring Boot 集群）、存储层（Redis 热数据 + MySQL 全量数据 + Kafka 异步清理管道）。

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 短码生成 | Snowflake ID + Base62 | 趋势递增、无需查重、单机 4096/ms |
| 重定向方式 | 302（临时） | 方便统计点击；301 浏览器永久缓存，丢失统计 |
| 热点缓存 | Redis Cluster + Caffeine L1 | 读多写少，双层缓存降低 Redis 压力 |
| 持久存储 | MySQL 分库分表 | 按短码 hash 分 64 库，单库可控 |
| 过期清理 | Kafka + 定时任务分片 | 异步解耦，不影响在线请求 |

### 面试追问

**Q1：为什么用 Base62 而不是 Base64？**
> Base64 包含 `+` 和 `/`，在 URL 中需要转义，增加复杂度。Base62 用 `0-9a-zA-Z` 共 62 个字符，生成的短码天然 URL-safe。

**Q2：如果短码冲突了怎么办？**
> Snowflake ID 在同一毫秒内通过序列号保证不冲突。如果用随机生成方式，需要查重冲突后重试，但会在高并发下产生热点。推荐号段模式或 Snowflake 避免冲突。

**Q3：6 位 Base62 能支撑多少短链？不够怎么办？**
> 62^6 ≈ 568 亿，足够绝大多数场景。如果不够，升级到 7-8 位，或者对不同 ID 段使用不同长度编码（可变长度方案）。

**Q4：302 重定向下如何防止被薅羊毛/恶意刷量？**
> 在 Nginx 层做限流（令牌桶），同一 IP 短时间内访问同一短码有频率上限。对高频异常 IP 加入黑名单。访问统计用 Redis INCR 异步批量落盘。

**Q5：如何实现自定义短码？**
> 用户自定义短码需要全局唯一校验。写入前先查 Redis SET NX 判断是否已占用，再写入 MySQL（唯一索引兜底）。自定义短码与系统生成短码共用同一张表。

### 踩坑点

- **Base62 编码前导零问题**：ID=0 和 ID 很小时，Base62 结果很短甚至为 0，需要补零到固定最小长度
- **301 缓存陷阱**：使用 301 后浏览器永久缓存，即使删除短链用户仍能重定向，统计完全丢失
- **Redis 和 MySQL 数据不一致**：先写 MySQL 再写 Redis，如果 Redis 写失败需要补偿机制（延迟双删或消息队列重试）
- **短码安全**：连续 ID 生成的短码可被遍历，建议 ID 生成后做混淆（如 XOR 随机种子）或直接用 Snowflake

## 02. 朋友圈 / Feed 流

### 场景描述

设计一个类似微信朋友圈/Twitter 的 Feed 流系统。用户发布动态，关注的人可以在自己的时间线上看到。假设 DAU 5 亿，日均发布 1 亿条动态，每人平均关注 200 人。

### 核心挑战

1. **推拉模式选择**：如何在写扩散和读扩散之间取平衡
2. **大 V 问题**：千万粉丝的用户发一条动态，如何不压垮系统
3. **Timeline 分页**：深度分页性能问题、新增动态插入后数据漂移
4. **多维度 Feed**：关注的人的动态、热门推荐、同城动态如何融合

### 设计方案

```
发布流程（推拉结合）:
┌────────┐  发布   ┌──────────┐  推 Fan-out  ┌──────────────┐
│ User A │------->│ 发布服务  │------------->│ Feed 收件箱   │
└────────┘        └──────────┘   (仅推给     │ (每个用户一个) │
                    │             普通用户)    └──────────────┘
                    ▼
              ┌──────────┐
              │ 动态存储  │ (所有动态原始数据)
              └──────────┘

读取流程:
┌────────┐  拉取  ┌──────────┐  合并   ┌──────────────┐  补充  ┌──────────┐
│ User B │------>│ Feed 服务 │------->│ 收件箱 + 大V  │------>│ 用户/内容 │
└────────┘       └──────────┘  拉取    │ 拉取合并排序   │  详情  │ 服务      │
                                        └──────────────┘       └──────────┘
```

**推模式（写扩散）**：用户 A 发布动态时，系统遍历 A 的粉丝列表，将动态 ID 写入每个粉丝的收件箱（Redis List / MySQL feed_inbox 表）。优点：读取快，直接从收件箱拉取。缺点：大 V 发一次动态需要写入千万条记录。

**拉模式（读扩散）**：不预写收件箱。用户 B 刷朋友圈时，实时拉取 B 关注的所有人的最新动态并排序合并。优点：写入简单。缺点：关注 200 人就需要查 200 次，读延迟高。

**推拉结合（最终方案）**：粉丝数 < 5000 的用户走推模式（写扩散）；粉丝数 >= 5000 的大 V 走拉模式（读扩散）。读取时，先从收件箱拉取推模式数据，再实时拉取关注的大 V 最新动态，两路合并排序。

**Timeline 分页**：使用游标分页（`max_id` + `limit`），不做 OFFSET 深度分页。每条动态带全局递增时间戳作为排序依据，分页游标为上一页最后一条的 `(timestamp, id)`。

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 收件箱存储 | Redis ZSET (score=时间戳) | 自动排序、支持范围查询、TTL 过期 |
| 动态原始数据 | MySQL 分库分表 + HBase | 元数据走 MySQL，富媒体内容走 HBase |
| Fan-out 推送 | Kafka + 异步 Worker | 削峰填谷，失败重试，可控消费速率 |
| 大 V 拉取 | Redis + 本地缓存 | 热点大 V 数据常驻缓存 |
| 详情补充 | 批量 RPC (MultiGet) | 避免 N+1 查询 |

### 面试追问

**Q1：推拉结合的阈值怎么定？5000 粉丝是拍脑袋的吗？**
> 不完全是拍脑袋。假设系统每秒有 1000 条新动态发布，大 V 阈值为 T。推模式 Fan-out 总写入量 = 每条动态的粉丝数 × 动态数。需要根据集群写能力反推 T。通常 T 在 1000-10000 之间，具体取决于硬件和 SLA。

**Q2：收件箱用 Redis ZSET 存储，容量怎么控制？**
> 每个用户的收件箱只保留最近 500-1000 条。定期 ZREMRANGEBYRANK 淘汰旧数据。历史数据从 MySQL 全量表拉取（冷启动/深度翻页场景）。

**Q3：用户取消关注后，已推送到收件箱的动态要不要删？**
> 不删。取消关注后新动态不再推送，但历史已推送的动态保留。如果要删，需要回溯该用户所有粉丝的收件箱逐一删除，成本太高。产品上通常可以接受"取关后仍能看到之前的动态"。

**Q4：如何保证 Fan-out 推送的可靠性？**
> Kafka 消费端做幂等处理（Redis SISMEMBER 判断是否已推送）。消费失败自动重试，超过阈值进死信队列人工介入。推送完成后更新推送状态位图（Bitmap），定期对账补推。

**Q5：朋友圈的点赞/评论如何与 Feed 流结合？**
> 点赞/评论走独立的互动服务，Feed 流只存储动态 ID。客户端拉取到动态列表后，批量查询互动服务获取点赞数、评论摘要。避免每次刷 Feed 都写 Feed 表。

### 踩坑点

- **大 V 发布瞬间的毛刺**：即使走拉模式，热门大 V 发布瞬间会触发大量缓存 miss，需要缓存预热 + 热点探测自动升级缓存
- **Feed 排序漂移**：新动态插入后，上一次分页的 max_id 可能跳过数据。解决方案：分页游标加 `(timestamp, id)` 双字段排序
- **推模式的消息丢失**：Kafka 消费端处理不及时导致堆积，收件箱写入延迟高。需要监控消费 lag，自动扩容消费者
- **冷启动问题**：新用户没有关注任何人，Feed 为空。需要推荐系统兜底，提供热门/同城/兴趣推荐 Feed

## 03. 即时通讯系统

### 场景描述

设计一个支持单聊、群聊的 IM 系统。要求消息可靠投递（不丢、不重复），支持已读/未读状态，支持多端（手机、PC、Web）同时在线同步。日活 1 亿，日消息量 500 亿。

### 核心挑战

1. **长连接管理**：亿级在线连接的心跳维护和连接迁移
2. **消息可靠投递**：如何保证消息不丢、不重复、有序
3. **已读/未读状态**：群聊场景下已读状态的存储爆炸问题
4. **多端同步**：用户在手机和 PC 同时在线，消息如何同步

### 设计方案

```
┌─────────┐    WebSocket     ┌──────────────┐
│ Client A │<───────────────>│  Gateway 集群  │
└─────────┘                  └──────┬───────┘
                                    │
         ┌──────────────────────────┼──────────────────────────┐
         ▼                          ▼                          ▼
┌──────────────┐           ┌──────────────┐           ┌──────────────┐
│  连接管理      │           │  消息路由     │           │  状态服务     │
│ (ConnSession) │           │ (Router)     │           │ (Online/已读) │
└──────┬───────┘           └──────┬───────┘           └──────────────┘
       │                          │
       ▼                          ▼
┌──────────────┐           ┌──────────────┐
│  Redis       │           │  消息存储     │
│ (在线状态+路由)│           │ (MySQL+HBase) │
└──────────────┘           └──────────────┘
```

**消息投递流程（单聊）**：
1. A 发消息到 Gateway → Gateway 存储消息到消息表（msg_id 递增）→ 查找 B 的在线状态
2. B 在线：通过 Gateway 直接推送给 B → B 回 ACK → 更新消息状态为已送达
3. B 不在线：消息暂存离线队列 → B 上线后拉取未读消息
4. **可靠投递**：客户端发送后启动超时计时器，未收到 ACK 则重发；服务端用 `msg_id` 做幂等去重

**消息投递流程（群聊）**：
1. A 发群消息 → 写入群消息表 → 查询群成员列表 → 写入每个成员的收件箱（读扩散 or 写扩散）
2. 群聊通常用**写扩散**：每个成员有独立的消息序列号（`user_seq`），保证每个用户看到的消息顺序一致
3. 大群（>500 人）用**读扩散**：不预写收件箱，成员拉取时实时查群消息表

**已读/未读**：单聊用一个 `last_read_seq` 字段即可。群聊用 Bitmap：每人维护一个已读位图（offset = msg_seq），群维度聚合已读人数。超过 1000 人的大群不做逐人已读，只显示"已读 N 人"。

**多端同步**：每端维护自己的同步序列号（`device_seq`）。消息写入用户信箱时分配全局递增 `user_seq`，各端拉取时用各自的 `device_seq` 作为游标。一端已读不会影响另一端的未读状态，通过独立的 `read_seq_per_device` 管理。

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 长连接协议 | WebSocket + 心跳 30s | 浏览器兼容、双向通信、比 HTTP 轮询省资源 |
| 连接网关 | Netty | 高并发、低延迟、成熟的长连接框架 |
| 在线状态 | Redis Bitmap / SET | 亿级用户在线状态，Bitmap 只需 125MB/亿人 |
| 消息存储 | MySQL（元数据）+ HBase（消息体） | 元数据查询走 MySQL，海量消息体走 HBase |
| 消息队列 | Kafka | 消息持久化、有序、高吞吐 |
| 已读状态 | RoaringBitmap | 压缩率高，群聊已读查询 O(1) |

### 面试追问

**Q1：如何保证消息不丢？**
> 三层保障：① 客户端发送后启动重试，直到收到 ACK；② 服务端收到消息后先写入持久化存储，再推送；③ 推送后等待客户端 ACK，未 ACK 的消息在重连后重新推送。本质是**至少一次投递 + 客户端幂等去重**。

**Q2：消息重复怎么解决？**
> 每条消息带唯一的 `client_msg_id`（客户端生成的 UUID）。服务端收到后先查是否已处理过（Redis SETNX），已存在则直接返回 ACK 不重复处理。存储层也做唯一索引兜底。

**Q3：群聊消息的时序性如何保证？**
> 群维度分配递增的 `group_seq`，每个用户拉取时按 `group_seq` 排序。但不同用户看到同一条消息的时间可能不同（网络延迟），这是可接受的——IM 系统保证的是**逻辑有序**而非物理实时。

**Q4：用户离线一个月后上线，如何快速拉取未读消息？**
> 用户信箱中只保留最近 N 条（如 1000 条）未读消息的 ID。更早的消息从全量消息存储中拉取。上线拉取接口支持分页 + 批量，首次拉取只拉未读数和最新 20 条，用户向上滚动时再按需加载。

**Q5：如何处理群聊的已读回执风暴？**
> 群消息已读不逐条回执。用户打开群聊时，上报当前已读到的 `seq`，服务端更新 `last_read_seq`。聚合"已读 N 人"通过离线任务定时从各成员的 `last_read_seq` 聚合计算，不实时更新。

### 踩坑点

- **长连接的心跳风暴**：亿级连接同时发心跳造成瞬时流量毛刺。心跳间隔加随机抖动（30s ± 5s）
- **消息乱序**：网络抖动导致先发的消息后到达。客户端做排序缓冲区，按 `seq` 顺序展示
- **群消息写放大**：500 人群一条消息写 500 次，10000 人群写 10000 次。大群必须用读扩散
- **多端冲突**：两端同时修改同一个对话的置顶/免打扰状态，需要最后写入胜出（LWW）或向量时钟

## 04. 搜索自动补全

### 场景描述

设计一个搜索框自动补全系统（Typeahead / Autocomplete）。用户每输入一个字符，下拉展示 Top 10 热门补全建议。支撑 DAU 1 亿，QPS 峰值 50 万，延迟要求 < 50ms。

### 核心挑战

1. **低延迟**：每次击键触发请求，必须在 50ms 内返回
2. **热度排序**：不仅要匹配前缀，还要按搜索热度排序
3. **拼音纠错**：用户输入拼音或错别字时如何智能纠错
4. **数据更新**：热搜词实时变化，如何及时反映到补全结果

### 设计方案

```
┌──────────┐  每次击键  ┌──────────────┐
│ 搜索框    │──────────>│  CDN/边缘缓存 │
└──────────┘           └──────┬───────┘
                              │ miss
                              ▼
                     ┌──────────────┐
                     │  补全服务集群  │
                     │ (Trie + Cache)│
                     └──────┬───────┘
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
        ┌──────────┐ ┌──────────┐ ┌──────────────┐
        │ Redis     │ │ 本地缓存  │ │ 离线计算管道  │
        │ (前缀->Top)│ │ (Caffeine)│ │ (Spark+Flink)│
        └──────────┘ └──────────┘ └──────────────┘
```

**核心数据结构**：Trie（前缀树），每个节点存储该前缀下的 Top K 热门补全词。`TrieNode = {children: Map<char, TrieNode>, topK: List<(keyword, score)>}`。

**查询流程**：用户输入 "jav" → 查本地缓存 → miss 查 Redis → miss 查内存 Trie → 返回 `["java", "javascript", "java 教程", ...]`。

**数据更新（离线+近实时）**：
1. **离线批处理**：每天凌晨用 Spark 统计前一天全量搜索日志，计算每个关键词的搜索频次，重建 Trie 序列化到文件
2. **近实时更新**：Flink 实时统计最近 1 小时搜索量，与离线分数加权合并（实时权重 0.3，离线权重 0.7）
3. **服务热加载**：新 Trie 文件生成后，通知服务节点增量加载（Diff Trie），不需要重启

**拼音纠错**：维护一份拼音词典（拼音→汉字列表）。用户输入拼音时，先查拼音词典转为候选汉字，再查 Trie 补全。编辑距离为 1 的错别字，通过 Trie 的模糊匹配能力处理。

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 核心数据结构 | 前缀压缩 Trie (Double-array) | 内存紧凑、前缀查询 O(L) |
| 热度缓存 | 三级缓存（Caffeine -> Redis -> Trie） | 逐级回源，最大限度降低延迟 |
| 热度计算 | Spark 离线 + Flink 实时 | 离线保证准确性，实时保证时效性 |
| 拼音纠错 | 拼音词典 + 编辑距离 | 简单有效，不引入复杂 NLP |
| 数据分发 | 一致性哈希分片 | 按前缀首字母分片到不同节点 |

### 面试追问

**Q1：为什么不在每次击键时实时计算 Top K？**
> 实时计算需要遍历所有匹配前缀的关键词并排序，数据量大时延迟远超 50ms。预计算好 Top K 存在 Trie 节点中，查询只是内存读取，延迟可控。

**Q2：Trie 的内存占用怎么优化？**
> 用 Double-array Trie 压缩存储，只分配实际使用的位置。或者用 Radix Tree（基数树）合并单链路径。Top K 列表只存储 ID 不存完整关键词，查询时再补全。

**Q3：如何处理敏感词/违禁词？**
> 在 Trie 构建时标记敏感词节点，查询结果返回前做过滤。敏感词列表由审核系统维护，支持实时下发更新。

**Q4：冷门前缀的补全怎么处理？**
> 冷门前缀在 Trie 中没有足够数据时，退回用更短的前缀的 Top K 过滤结果，或者展示通用热搜词兜底。

**Q5：分布式部署下如何保证各节点数据一致？**
> Trie 文件版本化管理，通过 ZooKeeper/etcd 通知各节点加载新版本。版本号单调递增，节点加载时校验版本一致性。灰度发布：先更新 10% 节点验证，再全量推送。

### 踩坑点

- **CDN 缓存粒度**：每个前缀是一个独立的缓存 key，组合爆炸（26^N）。实际只缓存高频前缀，冷门前缀回源
- **Trie 加载卡顿**：全量 Trie 构建耗时长，加载到内存需要几秒。用 Double Buffer 机制：新 Trie 构建完成后指针切换，零停机
- **拼音歧义**：同一个拼音对应大量汉字（如 "yi" 有上百个字），需要结合搜索频次和上下文筛选
- **热更新延迟**：Flink 实时计算有窗口延迟（1-5 分钟），紧急事件（如明星塌房）需要人工干预置顶

## 05. 排行榜系统

### 场景描述

设计一个实时排行榜系统，支持：全服积分排行榜、好友排行榜、活动期间限时排行榜。用户量 10 亿，日活 1 亿，积分变更频繁（每秒百万次写入），支持 Top N 查询和用户排名查询。

### 核心挑战

1. **高并发写入**：每秒百万次积分更新，如何保证排序正确性
2. **排名查询**：任意用户的实时排名，不能遍历
3. **多维度排行**：全服/分服/好友/限时，维度爆炸
4. **防刷**：如何防止刷积分/刷榜

### 设计方案

```
┌──────────┐    ┌──────────────┐    ┌──────────────────┐
│ 积分变更   │───>│ 排行榜服务    │───>│  Redis ZSET      │
│ (业务事件) │    │ (ZADD + ZRANK)│    │  key=board:{id}  │
└──────────┘    └──────┬───────┘    │  score=积分        │
                       │            │  member=userId     │
                       ▼            └──────────────────┘
              ┌──────────────┐              │
              │  异步归档管道  │              ▼
              │ (Kafka+Spark) │    ┌──────────────────┐
              └──────┬───────┘    │  MySQL 全量归档    │
                     ▼            │  (T+1 离线排行)    │
              ┌──────────────┐    └──────────────────┘
              │  离线排行快照  │
              │ (历史排行/大促) │
              └──────────────┘
```

**核心操作**：
- **更新积分**：`ZADD board:{id} {new_score} {userId}` — O(log N)
- **查 Top N**：`ZREVRANGE board:{id} 0 N-1 WITHSCORES` — O(log N + M)
- **查用户排名**：`ZREVRANK board:{id} {userId}` — O(log N)
- **查用户分数**：`ZSCORE board:{id} {userId}` — O(1)

**分段排行**：当 ZSET 成员超过千万级时，按分数段拆分为多个 ZSET（如 0-1000, 1001-5000, ...）。查询 Top N 时从最高分段开始取；查用户排名时，先定位到分数段，再段内计算排名 + 累加前面所有段的总人数。

**好友排行榜**：好友关系走独立的好友服务。查询时拉取好友 ID 列表 → 批量查 ZSCORE → 内存排序返回。好友列表缓存在 Redis，设置合理 TTL。

**限时排行榜**：活动期间创建临时 ZSET（key 含活动 ID + 时间段），活动结束后归档到 MySQL 并删除 Redis key。

**防刷策略**：
1. 积分变更频率限制（令牌桶，每用户每秒最多 N 次变更）
2. 积分来源校验（服务端计算，不信任客户端上报的分数）
3. 异常积分突增检测（Flink 实时监控，超阈值告警 + 冻结）

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 实时排行 | Redis ZSET | 天然有序集合，ZADD/ZRANK 都是 O(log N) |
| 超大规模排行 | Redis Cluster + 分段 ZSET | 单 ZSET 不超过 500 万成员 |
| 离线快照 | Spark 批处理 + MySQL | T+1 历史排行、跨天排行对比 |
| 防刷 | Flink CEP + 令牌桶 | 实时检测异常模式 |

### 面试追问

**Q1：Redis ZSET 在千万级数据下性能如何？**
> ZSET 底层是跳表 + 哈希表。千万级时 ZADD 和 ZRANK 都是 O(log N) ≈ O(24)，单次操作几微秒。但内存占用大（每条记录约 100 字节，1000 万条 ≈ 1GB），且大量写入时主从复制压力大。建议分片。

**Q2：如何实现"打败了 99% 的用户"？**
> 用 `ZREVRANK` 得到用户排名 R，用 `ZCARD` 得到总人数 N，百分比 = `(N - R) / N`。ZCARD 是 O(1)。缓存 N 值（每分钟更新一次避免频繁调用）。

**Q3：多人同时加分导致排名抖动怎么办？**
> 排行榜本身是实时的，排名变化是正常的。如果需要平滑展示（避免排名频繁跳动），可以做积分聚合窗口（如每 10 秒更新一次排名），前端拿到的排名是最近一个窗口的快照。

**Q4：如何处理积分相同时的排名？**
> Redis ZSET 中分数相同时按 member 字典序排序。如果需要按先达到者排名靠前，可以在分数中编码时间信息：`score = 原始积分 * 10^13 + (MAX_TS - timestamp)`，使得先达到的人排名更靠前。

**Q5：好友排行榜如何优化好友数很多的用户？**
> 好友数超过 1000 的用户，不全量查询。只拉取最近活跃的 Top 200 好友（按最后登录时间排序），缓存在 Redis List 中。用户查看时从缓存中取，异步刷新。

### 踩坑点

- **ZSET 内存爆炸**：10 亿用户的排行榜不可全量放 Redis。只放活跃用户（1 亿），冷数据从 MySQL 加载
- **积分精度问题**：浮点数比较有精度问题，积分用整数（如乘以 100 转为分）
- **主从延迟**：写入主节点后立刻从从节点查排名，可能读到旧数据。排行榜查询走主节点
- **排行榜清零**：赛季重置时不要 DEL key（会阻塞），用 RENAME 切换到新 key，旧 key 异步删除

## 06. 优惠券 / 秒杀系统

### 场景描述

设计一个支持优惠券发放和限时秒杀的系统。10 万张优惠券在 0 点开抢，预计 500 万人参与，峰值 QPS 100 万。要求：不超卖、不重复领取、下单成功后 15 分钟内未支付自动释放库存。

### 核心挑战

1. **超高并发扣减**：百万 QPS 下保证库存扣减原子性
2. **超卖防护**：绝对不能多卖，否则是资损
3. **异步下单**：秒杀结果与下单流程解耦
4. **限流降级**：保护后端数据库不被打垮

### 设计方案

```
请求流:  Client -> CDN -> Nginx(限流) -> Gateway(鉴权) -> 秒杀服务 -> Redis(扣减) -> Kafka(下单) -> 订单服务 -> MySQL

┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ 前端静态化 │->│ Nginx    │->│ 网关层    │->│ 秒杀服务  │->│ 订单服务  │
│ CDN 加速  │  │ 限流+削峰│  │ 登录校验  │  │ Redis 扣减│  │ 异步下单  │
└──────────┘  └──────────┘  └──────────┘  └──────────┘  └──────────┘
```

**四层过滤**：
1. **前端**：按钮置灰 + 验证码 + 本地随机丢弃（拦截 50% 无效请求）
2. **Nginx**：限流（漏桶/令牌桶），超出直接返回"活动太火爆"
3. **网关**：登录校验 + 用户级去重（Redis SETNX 防同一用户重复请求）
4. **秒杀服务**：Redis 原子扣减库存

**库存扣减（Redis + Lua 原子脚本）**：
```lua
-- KEYS[1] = stock_key, KEYS[2] = bought_key
-- ARGV[1] = userId
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock <= 0 then return -1 end  -- 已售罄
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -2 end  -- 已购买
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1  -- 扣减成功
```

**异步下单**：扣减成功后发送 Kafka 消息 → 订单服务消费消息创建订单 → 用户 15 分钟内支付 → 超时未支付触发库存回滚（延迟队列）。

**库存回滚**：RocketMQ 延迟消息 / Redis 过期键 + Keyspace Notification / 自研延迟队列（ZSET score = 过期时间戳，定时轮询）。

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 库存扣减 | Redis + Lua | 单线程原子执行，10 万 QPS 无压力 |
| 前端限流 | Nginx + OpenResty | 接近用户侧，最快拦截 |
| 异步下单 | Kafka | 高吞吐、持久化、顺序消费 |
| 超时关单 | RocketMQ 延迟消息 | 原生支持延迟级别，简单可靠 |
| 数据兜底 | MySQL 乐观锁 | 最终一致性校验 `WHERE stock >= count` |

### 面试追问

**Q1：Redis 扣减成功但 Kafka 发送失败怎么办？**
> 两种方案：① 本地事务表：先写 MySQL 事务表记录"用户已扣减"，后台定时扫描发送 Kafka；② Redis 事务 + 消息确认：Kafka 发送失败则回滚 Redis 库存（INCR + SREM）。

**Q2：如果 Redis 宕机了怎么办？**
> Redis Cluster 主从切换，秒杀暂停（直接返回"系统繁忙"）。切换完成后从 MySQL 校准库存（以 MySQL 为准）。Redis 只是缓存加速层，MySQL 是最终库存数据源。

**Q3：如何防止脚本/机器人刷单？**
> ① 请求带设备指纹 + 行为验证（滑块验证码）；② 同一设备/IP 限流；③ 下单时校验收货地址、手机号的合理性；④ 事后风控模型分析异常订单。

**Q4：秒杀结束后库存还有剩余怎么办？**
> 秒杀倒计时结束后，如果 Redis 中还有库存，同步回写 MySQL。如果是因为支付超时释放的库存，可以开放第二轮抢购或转入常规库存。

**Q5：如何做秒杀系统的压测？**
> 分层压测：① Nginx 层用 wrk 模拟 100 万 QPS；② 秒杀服务用 JMeter 模拟完整链路；③ 关注指标：P99 延迟、Redis CPU、Kafka 消费 lag、MySQL 连接数。压测时用影子库避免脏数据。

### 踩坑点

- **超卖是红线**：Redis 扣减和下单必须在同一事务中保证一致性，否则"扣了没下"或"下了没扣"
- **热点 key 问题**：所有请求打到同一个库存 key 上。解决：库存分桶（key_1 ~ key_N，每个 1/N 库存），随机选择桶扣减
- **15 分钟关单的时间精度**：不要用 `Thread.sleep(15min)`，服务器重启会丢失。用延迟队列持久化
- **缓存与 DB 不一致**：最终以 MySQL 为准，定期用 Redis 库存和 MySQL 库存做对账

## 07. 评论系统

### 场景描述

设计一个支持楼中楼（嵌套评论）、@提及、敏感词过滤的评论系统。支持文章评论和视频评论，日均新增评论 5 亿条，支持多种排序（时间序/热度序/点赞序）。

### 核心挑战

1. **楼中楼嵌套**：无限层级嵌套如何存储和查询
2. **@提醒**：@提及后如何高效通知被 @ 的用户
3. **敏感词过滤**：海量评论实时过滤，误杀率要低
4. **排序策略**：时间序 vs 热度序如何平衡

### 设计方案

```
评论存储模型（邻接表 + 闭包表混合）:
┌──────────────────────────────────────────┐
│ comment 表                                │
│ id | content | user_id | target_id       │
│ parent_id | root_id | path | depth       │
│ like_count | reply_count | status        │
│ created_at | updated_at                  │
└──────────────────────────────────────────┘

查询结构:
根评论1 (path: /001)
├── 回复1-1 (path: /001/002)
│   └── 回复1-1-1 (path: /001/002/003)
└── 回复1-2 (path: /001/004)
根评论2 (path: /005)
```

**楼中楼方案**：
- **存储**：每条评论记录 `root_id`（所属根评论）、`parent_id`（直接父评论）、`path`（路径编码，如 `/001/002/003`）
- **一级评论列表**：`WHERE root_id IS NULL AND target_id = ? ORDER BY created_at DESC LIMIT 20`
- **展开楼中楼**：`WHERE root_id = ? ORDER BY path ASC LIMIT 50`（path 排序保证嵌套顺序）
- **层级限制**：最多展示 3 层，超过 3 层的回复扁平化显示

**@提醒流程**：
1. 评论发布时正则提取 `@username` → 查用户 ID → 写入 `mention` 表
2. 异步发送通知到消息服务（Kafka → 推送服务）
3. 用户打开"提到我的"页面时，从 `mention` 表分页查询

**敏感词过滤**：
- **DFA（确定有限自动机）**：预编译敏感词库为 DFA，单次扫描 O(N) 匹配所有敏感词
- **多级策略**：① 实时过滤（发布时）→ 替换为 `***`；② 异步审核 → AI 模型判断语义；③ 人工复审 → 审核队列
- **热更新**：敏感词库变更后通过配置中心推送到服务节点，热加载 DFA

**排序策略**：
- **时间序**：`ORDER BY created_at DESC`，适合最新评论
- **热度序**：`score = like_count * 2 + reply_count * 5 - hours_since_created * 0.1`，定期重新计算
- **点赞序**：纯按 `like_count DESC`，适合高赞评论优先

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 评论存储 | MySQL（path 编码） | 支持范围查询、事务一致 |
| 评论缓存 | Redis Sorted Set | 热度排序、分页查询 |
| 敏感词过滤 | DFA 自动机 | 单次扫描、内存友好 |
| @提醒 | Kafka + 消息表 | 异步解耦、可靠投递 |
| 排序计算 | 定时任务 + 增量更新 | 热度分数每小时重算 |

### 面试追问

**Q1：path 编码方式有什么缺点？**
> path 依赖固定位数编码，位数不够时需要迁移数据。替代方案：闭包表（closure table），存储所有祖先-后代关系对，查询更灵活但写入成本更高。实际中 path 编码已足够覆盖 3 层嵌套。

**Q2：敏感词如何应对谐音、拼音、火星文？**
> ① 拼音转换后再匹配；② 谐音词典（如"草泥马"->敏感词）；③ Unicode 归一化处理火星文（如 `@` -> `a`）；④ 最终靠 AI 模型做语义审核兜底。

**Q3：评论的 @ 提醒如何做到实时？**
> @ 提醒走独立的消息通道（WebSocket 推送），与评论写入解耦。评论写入成功后发送 Kafka 事件，推送服务消费后通过 WebSocket 推送通知。离线用户走离线消息队列。

**Q4：如何处理评论的举报和删除？**
> 举报写入 `report` 表，达到阈值自动进入审核队列。删除采用软删除（`status = DELETED`），保留数据用于审计。根评论删除时级联隐藏所有子评论（不物理删除）。

**Q5：视频评论和文章评论如何统一？**
> 评论表用 `target_type`（ARTICLE/VIDEO）+ `target_id` 做多态关联。业务逻辑差异通过策略模式封装（如视频评论支持时间点关联：评论出现在视频 01:23 处）。

### 踩坑点

- **N+1 查询**：展示一级评论时不要循环查每条评论的回复数和用户信息，用批量查询 + 缓存
- **热评马太效应**：高赞评论一直霸榜，新评论没有曝光机会。解决方案：热度分数加时间衰减因子
- **path 编码溢出**：`/001/002/003` 如果超过 3 层，path 需要预留足够位数
- **评论一致性**：用户删除评论后缓存未更新，其他用户还能看到。删除操作需要同步清缓存

## 08. 权限系统

### 场景描述

设计一个通用的权限管理系统，支持 RBAC（基于角色的访问控制）和 ABAC（基于属性的访问控制）。要求支持菜单权限、按钮权限、数据权限（如只看自己部门的数据），权限变更实时生效。支撑 10 万用户、1000 个角色、5000 个权限点。

### 核心挑战

1. **RBAC vs ABAC 选型**：不同场景需要不同的权限模型
2. **数据权限**：行级数据过滤如何通用化
3. **权限缓存**：频繁鉴权下的缓存一致性
4. **动态鉴权**：基于上下文的实时权限判断

### 设计方案

```
RBAC 模型:
┌────────┐   M:N    ┌────────┐   M:N    ┌──────────┐
│  User  │─────────>│  Role  │─────────>│ Permission│
└────────┘          └────────┘          └──────────┘
     │                    │                    │
     ▼                    ▼                    ▼
┌────────┐          ┌──────────┐        ┌──────────────┐
│UserRole│          │ RolePerm │        │Menu/Button/Data│
└────────┘          └──────────┘        └──────────────┘

ABAC 扩展:
┌──────────────────────────────────────────────┐
│ Policy = Effect + Subject + Resource + Action │
│ + Condition (environment, time, IP, dept...) │
└──────────────────────────────────────────────┘
```

**RBAC 基础**：用户-角色-权限三张关联表。角色继承（Role Hierarchy）通过角色树实现。权限类型分三种：菜单权限（控制页面可见性）、按钮权限（控制操作可执行性）、数据权限（控制数据可见范围）。

**数据权限实现**：
```java
@DataSourceScope(tableAlias = "o", deptColumn = "dept_id")
public List<Order> listOrders() { ... }

// AOP 拦截，自动追加 SQL 条件：
// 普通用户：WHERE o.user_id = #{currentUserId}
// 部门经理：WHERE o.dept_id IN (#{deptIds})
// 管理员：不追加条件
```

用 AOP 拦截 Mapper 方法，根据当前用户的数据权限范围自动追加 `WHERE` 条件。数据权限范围分级：全部 > 本部门及下级 > 本部门 > 仅本人。

**ABAC 扩展**：对于复杂权限场景（如"工作日 9-18 点，IP 在公司网段内，才能审批金额超过 10 万的订单"），用 ABAC 策略引擎：
```
Policy:
  Effect: ALLOW
  Subject: role = "manager"
  Resource: type = "order", amount > 100000
  Condition: time in workday_9_18 AND ip in company_network
```

**权限缓存策略**：
- 用户权限列表缓存在 Redis（key = `user_perm:{userId}`，TTL = 5 分钟）
- 权限变更时主动删除缓存（延迟双删）
- 鉴权请求先查本地缓存（Caffeine，TTL = 30s），miss 再查 Redis

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| RBAC 基础 | MySQL 关联表 | 灵活、可审计、关系清晰 |
| ABAC 策略引擎 | Drools / 自研 DSL | 规则引擎支持复杂条件组合 |
| 数据权限 | MyBatis 拦截器 / AOP | 透明追加 SQL，业务无感知 |
| 权限缓存 | Caffeine L1 + Redis L2 | 双层缓存，变更时失效 |
| 权限变更通知 | Redis Pub/Sub | 实时通知所有节点清除缓存 |

### 面试追问

**Q1：RBAC 和 ABAC 什么时候用哪个？**
> RBAC 适合权限点明确、角色相对固定的场景（后台管理系统）。ABAC 适合权限规则复杂、需要基于上下文动态判断的场景（如审批流、多租户）。实践中常以 RBAC 为基础，对特殊需求叠加 ABAC。

**Q2：数据权限如何避免 N+1 查询？**
> 数据权限追加的 WHERE 条件在 SQL 层面完成，不额外发查询。关键是把数据权限参数（如部门 ID 列表）在进入 Service 层时就设置到 ThreadLocal，AOP 拦截时直接取用。

**Q3：权限变更如何实时生效？**
> 权限变更后：① 删除 Redis 中该用户的权限缓存；② 通过 Redis Pub/Sub 通知所有应用节点清除本地 Caffeine 缓存；③ 用户下一次请求时重新加载。延迟双删保证极端情况下的最终一致性。

**Q4：超管和租户管理员的权限如何隔离？**
> 在权限查询 SQL 中始终带 `tenant_id` 条件。超管的"全部数据"权限也是在租户范围内，不能跨租户。权限表加 `tenant_id` 字段做行级隔离。

**Q5：如何审计权限变更？**
> 所有权限变更操作记录到 `audit_log` 表：who、when、what（操作类型）、before（变更前）、after（变更后）。不可删除、不可修改。定期导出审计报告。

### 踩坑点

- **权限缓存不一致**：用户权限变更后缓存未及时清除，导致用户仍有旧权限。延迟双删 + TTL 兜底
- **数据权限循环依赖**：部门权限查询需要先查用户所属部门，部门信息也在缓存中，需要避免循环依赖
- **角色爆炸**：每新增一种权限组合就创建一个新角色，角色数爆炸。解决方案：角色继承 + 权限组合模板
- **ABAC 性能**：复杂策略引擎每次鉴权都需要解析规则。解决方案：规则缓存（编译后的规则对象缓存）+ 高频策略结果缓存

## 09. 文件上传系统

### 场景描述

设计一个支持大文件上传的文件系统。要求支持分片上传、断点续传、秒传、多格式文件预览，文件存储在对象存储（S3/OSS），通过 CDN 加速下载。单文件最大支持 10GB，日均上传量 1TB。

### 核心挑战

1. **大文件上传**：网络不稳定时大文件上传容易失败
2. **断点续传**：上传中断后如何从中断处继续
3. **秒传**：文件已存在时如何跳过上传
4. **CDN 加速**：如何让下载速度最快

### 设计方案

```
上传流程:
┌────────┐  1. 查询文件    ┌──────────┐  2. 查 MD5    ┌──────────┐
│ Client │───────────────>│ 上传服务  │──────────────>│ 文件索引  │
└───┬────┘                └──────────┘    已存在?      │ (MySQL)  │
    │                     返回秒传/继续     │           └──────────┘
    │ 3. 分片上传          ┌──────────┐    │
    │ ──────────────────> │ 分片存储  │    │
    │ (并行上传 N 片)      │ (OSS临时) │    │
    │                     └──────────┘    │
    │ 4. 合并请求          ┌──────────┐    │
    │ ──────────────────> │ 合并服务  │───>│ OSS 永久存储 │
    │                     └──────────┘    │ CDN 分发    │
```

**分片上传**：
1. 客户端计算文件 MD5（边读边算，不占内存）→ 发送到服务端查询是否已存在
2. 已存在：直接返回文件 URL（**秒传**）
3. 未存在：服务端生成 `upload_id`，返回需要上传的分片列表（支持**断点续传**：已上传的分片标记为完成）
4. 客户端并行上传分片（每片 5MB，默认 3 并发）→ 所有分片上传完成后调用合并接口
5. 服务端调用 OSS 的 Multipart Upload Complete API 合并分片 → 更新文件索引

**断点续传**：
- 客户端记录 `upload_id` + 已上传分片序号到本地（localStorage / IndexedDB）
- 重新上传时先调用 `/upload/check` 接口，传入 `upload_id`，服务端返回已完成的分片列表
- 客户端只上传缺失的分片

**CDN 加速**：
- 文件上传到 OSS 后，配置 CDN 域名 CNAME 到 OSS 域名
- 静态资源设置长缓存（Cache-Control: max-age=31536000）+ 文件 hash 作为 URL 后缀
- 海外用户通过 CDN 边缘节点就近下载

**文件预览**：
- 图片：直接返回 URL，前端缩放
- 文档（PDF/Word/PPT）：异步转换服务（LibreOffice / 阿里云文档转换）→ 生成 PDF 或图片序列 → 前端逐页渲染
- 视频：OSS 转码服务 → HLS 切片 → 前端 `<video>` 播放

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 对象存储 | 阿里云 OSS / AWS S3 | 海量存储、按量付费、内置 CDN |
| 分片上传 | OSS Multipart Upload | 官方支持、断点续传原生能力 |
| 文件索引 | MySQL + 文件 MD5 | 秒传查重、文件元数据管理 |
| 文档预览 | LibreOffice + PDF.js | 开源方案、格式覆盖广 |
| CDN | 云 CDN + 回源 OSS | 全球加速、自动缓存 |

### 面试追问

**Q1：MD5 冲突怎么办？**
> 理论上 MD5 有冲突可能，实际中概率极低。如果要求绝对可靠，可以 MD5 + SHA256 双重校验。或者秒传时额外校验文件大小（MD5 + 文件大小组合判断）。

**Q2：分片大小怎么定？**
> 通常 5-10MB。太小则分片数多、合并开销大；太大则单片失败重传成本高。动态策略：根据网络带宽自适应调整（弱网环境减小分片到 2MB）。

**Q3：秒传如何防止伪造？**
> 客户端上传前先计算 MD5，但服务端合并完成后会重新计算校验。如果客户端谎报 MD5（声称文件已存在），服务端验证实际内容不匹配则拒绝。秒传只是跳过传输，不跳过验证。

**Q4：文件删除后 CDN 缓存怎么处理？**
> 调用 CDN 的 Purge API 清除对应 URL 的缓存。或者文件 URL 包含版本号（如 `/v2/file.pdf`），删除后更新版本号，新 URL 自然未命中旧缓存。

**Q5：如何处理上传过程中的恶意文件（病毒/木马）？**
> 上传完成后异步扫描：调用 ClamAV 或云安全服务扫描文件。扫描结果为恶意则标记文件不可用，通知用户。上传期间不阻塞（异步扫描），但下载时校验文件状态。

### 踩坑点

- **OSS 合并失败**：分片上传后合并失败（某个分片校验不通过），需要清理临时分片，否则产生存储浪费
- **大文件 MD5 计算慢**：10GB 文件计算 MD5 需要几十秒。前端用 Web Worker + File.slice 逐片计算，边上传边计算
- **CDN 回源风暴**：大量新文件同时上线，CDN cache miss 导致回源请求打到 OSS。预热 CDN（提前推送热门文件到边缘节点）
- **并发上传的浏览器限制**：浏览器对同一域名的并发连接数限制为 6。上传域名和业务域名分开，避免上传阻塞正常 API 请求

## 10. 数据大屏 / 实时统计

### 场景描述

设计一个实时数据大屏系统，展示 GMV、订单量、UV、转化率等核心指标，要求延迟 < 3 秒。同时支持多维分析（按地区、品类、渠道切分），历史数据可回溯查询。

### 核心挑战

1. **低延迟**：3 秒内从数据产生到大屏展示
2. **高吞吐**：百万 TPS 的数据流实时聚合
3. **多维分析**：任意维度组合的上卷/下钻
4. **精度与性能**：实时计算如何在精度和性能间取舍

### 设计方案

```
数据流:
┌──────────┐   ┌──────────┐   ┌──────────────┐   ┌──────────┐   ┌──────────┐
│ 业务系统  │──>│  Kafka   │──>│  Flink 实时   │──>│  Redis   │──>│  大屏前端 │
│ (订单/日志)│   └──────────┘   │  聚合计算     │   │  (结果)   │   │  WebSocket│
└──────────┘                   └──────┬───────┘   └──────────┘   └──────────┘
                                      │
                                      ▼
                               ┌──────────────┐
                               │ ClickHouse   │
                               │ (多维分析+回溯)│
                               └──────────────┘

预聚合模型:
┌──────────────────────────────────────────┐
│ Cube 预聚合表                             │
│ time_bucket | dimension_1 | dimension_2  │
│ | metric_sum | metric_count | ...        │
│                                          │
│ 支持任意维度组合查询，空间换时间           │
└──────────────────────────────────────────┘
```

**实时聚合（Flink）**：
1. Kafka 消费业务事件流（订单、支付、浏览等）
2. Flink 滚动窗口（10 秒窗口）聚合核心指标：GMV、订单数、UV（HyperLogLog 去重）
3. 聚合结果写入 Redis（按时间窗口 key，如 `gmv:20240101102340`）
4. 大屏前端通过 WebSocket 订阅最新数据，每 3 秒刷新

**多维分析**：
- **预计算 Cube**：提前定义维度组合（地区×品类、渠道×时间 等），Flink 多路输出预聚合到不同 Cube
- **降精度换查询速度**：实时指标只保留最近 1 小时的 10 秒粒度数据，1 小时前降为分钟粒度，1 天前降为小时粒度
- **历史回溯**：ClickHouse 存储全量明细数据，支持任意维度的即席查询（OLAP）

**UV 去重**：实时 UV 用 HyperLogLog（误差 0.81%，内存仅 12KB/百万级 UV）。精确 UV 在 ClickHouse 中用 `uniqExact` 离线计算。

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 实时计算 | Flink | 窗口语义完善、Exactly-once 保证 |
| 实时存储 | Redis | 毫秒级读写、大屏实时查询 |
| OLAP 引擎 | ClickHouse | 列式存储、多维分析极速 |
| UV 去重 | HyperLogLog (Redis) | 内存极小、误差可接受 |
| 数据推送 | WebSocket | 实时双向通信、无轮询开销 |

### 面试追问

**Q1：HyperLogLog 的误差率 0.81% 可以接受吗？**
> 大屏场景下完全可接受。GMV 100 亿，UV 误差 0.81% 就是 810 万的偏差，但 UV 本身不直接产生收入。如果需要精确 UV，离线用 ClickHouse 精确计算，实时大屏用 HLL 展示趋势即可。

**Q2：Flink 任务挂了，数据会丢吗？**
> Flink 开启 Checkpoint（每分钟一次），状态持久化到 HDFS/S3。任务恢复后从最近的 Checkpoint 重新消费 Kafka（Kafka 消费位点也回滚）。保证 Exactly-once 语义。

**Q3：如何支持临时新增维度的查询？**
> 如果是预计算 Cube 覆盖的维度，直接查 Redis。如果是新维度，降级到 ClickHouse 实时查询（P99 延迟 1-5 秒），同时异步补充该维度的预计算 Cube。

**Q4：大屏数据如何处理跨天/跨月的聚合？**
> Flink 窗口只做短期聚合。跨天/跨月数据在 ClickHouse 中按分区键（天/月分区）预聚合。查询时 Merge 多个分区的聚合结果。

**Q5：如何保证大屏展示的"好看"和"流畅"？**
> 前端用 WebSocket 推送 + 数据平滑动画（数字跳动用 Tween 动画而非瞬间切换）。数据延迟通过服务端时间戳标注，前端显示"数据更新于 X 秒前"增强信任感。

### 踩坑点

- **Redis Key 膨胀**：每个维度组合 × 每个时间窗口是一个 key，维度爆炸导致 Redis key 数百万。控制维度组合数量，冷数据定期归档删除
- **Flink 反压**：上游 Kafka 数据量突增（如大促开始），Flink 算子处理不过来产生反压。设置合理的并行度 + 开启背压监控
- **时区问题**：分布式系统时区不一致导致数据错位。统一使用 UTC 存储，前端展示时转换时区
- **大促流量预估不足**：平时 QPS 1 万，大促突然 100 万。提前压测 + 弹性扩容 Flink 作业

## 11. 分布式定时任务

### 场景描述

设计一个分布式定时任务调度系统，支持：Cron 表达式调度、任务分片（大任务拆分到多台机器并行执行）、幂等执行、失败重试、任务依赖编排（DAG）。日均任务量 100 万，关键任务延迟 < 1 秒。

### 核心挑战

1. **任务分片**：大任务如何拆分到多节点并行执行
2. **幂等执行**：任务重试时如何避免重复执行副作用
3. **失败重试**：任务失败后如何智能重试
4. **任务编排**：多个任务之间的依赖关系如何管理

### 设计方案

```
┌──────────────┐
│  调度中心      │ (主节点选举，Cron 触发)
│  (Scheduler)  │
└──────┬───────┘
       │ 触发任务
       ▼
┌──────────────┐     ┌──────────────┐
│  任务分发      │────>│  执行节点集群  │
│  (Dispatcher) │     │  (Executor)   │
└──────┬───────┘     └──────┬───────┘
       │                    │
       ▼                    ▼
┌──────────────┐     ┌──────────────┐
│  任务状态存储  │     │  任务日志存储  │
│  (MySQL)      │     │  (ES/日志平台) │
└──────────────┘     └──────────────┘

任务分片:
Job(total=1000, shard=4)
├── Shard 0: items 0-249   -> Executor A
├── Shard 1: items 250-499 -> Executor B
├── Shard 2: items 500-749 -> Executor C
└── Shard 3: items 750-999 -> Executor D
```

**调度实现**：
- **主节点选举**：基于 ZooKeeper/etcd 的临时节点实现高可用。主节点负责 Cron 触发，主节点故障后从节点自动接管
- **任务分发**：触发时向任务队列（Redis List / DB 行锁）写入执行记录，Executor 竞争获取任务
- **分片策略**：总数据量 N，分片数 M。每个分片处理 `[shardId * N/M, (shardId+1) * N/M)` 的数据范围

**幂等保证**：
1. 任务执行前生成唯一 `execution_id`（`job_id + trigger_time`），写入执行记录表（唯一索引）
2. 执行过程中标记执行状态：`PENDING -> RUNNING -> SUCCESS/FAILED`
3. 重试时先检查执行记录，已成功则跳过

**DAG 任务编排**：
```
A (数据清洗)
├── B (指标计算)
│   └── D (报表生成)
└── C (数据导出)
    └── D (报表生成)

// 节点状态流转
PENDING -> READY (所有前置完成) -> RUNNING -> SUCCESS/FAILED
```

每个 DAG 节点记录状态，当所有前置节点完成后（入度为 0 且前置全部 SUCCESS），当前节点变 READY 并触发执行。DAG 调度器监听任务完成事件，级联检查下游节点。

**失败重试策略**：
- 固定间隔重试：失败后等 N 秒重试，最多 3 次
- 指数退避：1s -> 2s -> 4s -> 8s...
- 重试超限后告警 + 人工介入

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 调度框架 | XXL-JOB / 自研 | 轻量级、开箱即用、支持分片 |
| 主节点选举 | ZooKeeper / etcd | 成熟的分布式协调组件 |
| 任务队列 | Redis List / MySQL 行锁 | 简单竞争获取、分布式安全 |
| DAG 编排 | 有向图 + 状态机 | 状态流转清晰、可视化友好 |
| 监控告警 | Prometheus + Grafana | 任务成功率、延迟、堆积监控 |

### 面试追问

**Q1：任务分片怎么保证不重不漏？**
> 分片策略基于数据范围，每个分片处理 `[start, end)` 区间。任务元数据记录分片总数和各分片状态。如果某个分片执行失败，只重试该分片，不影响其他分片。所有分片完成后标记任务整体成功。

**Q2：如何处理慢任务拖垮整个 DAG？**
> 为每个任务设置超时时间，超时自动标记为失败并触发重试或告警。DAG 级别设置整体超时，超时后跳过等待中的节点，执行降级路径。

**Q3：调度中心主节点挂了，正在执行的任务怎么办？**
> 已在执行中的任务不受影响（Executor 本地继续执行）。主节点恢复后，通过心跳检测识别未完成的任务，补充调度。关键是在任务表中记录触发时间和预期完成时间，新主节点扫描超时未完成的任务进行恢复。

**Q4：如何实现 cron 秒级精度？**
> 传统 Quartz 的 CronTrigger 最小精度是秒。如果需要毫秒级精度，使用时间轮算法（HashedWheelTimer）管理触发时间。或者用 DB 轮询 + 悲观锁保证不重复触发。

**Q5：任务执行日志如何高效收集？**
> Executor 执行时将日志写入本地文件 -> Filebeat 采集到 ES -> Kibana 查询。实时日志通过 gRPC Stream 推送到调度中心。关键指标（执行时间、影响行数）写入任务执行记录表。

### 踩坑点

- **任务重复触发**：网络抖动导致调度中心误判任务未触发，重复下发。执行记录唯一索引 + 状态机保证幂等
- **分片数据不均匀**：有些分片数据量远大于其他分片，导致长尾延迟。解决方案：动态分片（根据数据量自适应调整分片边界）
- **时钟不同步**：分布式节点时钟偏差导致 Cron 触发时间不一致。NTP 同步 + 以调度中心时钟为准
- **数据库连接池耗尽**：大量任务同时执行时并发查 DB。任务执行结果异步批量落库，减少 DB 连接占用

## 12. 海量数据去重

### 场景描述

设计一个海量数据去重系统。场景包括：爬虫 URL 去重（100 亿条）、日志分析中 UV 统计（百亿级）、用户行为事件去重（秒级幂等判断）。要求：内存占用可控、误判率可接受、支持实时查询。

### 核心挑战

1. **内存爆炸**：100 亿条数据全量存储需要 TB 级内存
2. **精确 vs 概率**：精确去重的存储成本 vs 概率去重的误判率
3. **实时性**：需要在毫秒级判断是否重复
4. **数据结构选择**：不同场景需要不同的去重方案

### 设计方案

```
场景分类:
┌──────────────────────────────────────────────────────┐
│  精确去重（容忍较大内存）                              │
│  -> HashSet / Redis SET / Bitmap                      │
│                                                       │
│  概率去重（容忍少量误判）                              │
│  -> 布隆过滤器 (Bloom Filter)                          │
│                                                       │
│  计数去重（只需要去重后的计数）                        │
│  -> HyperLogLog                                       │
│                                                       │
│  状态标记去重（只需知道"是否已存在"）                  │
│  -> Bitmap / RoaringBitmap                            │
└──────────────────────────────────────────────────────┘
```

**布隆过滤器（Bloom Filter）**：
- 位数组 + K 个独立哈希函数
- 插入：对元素计算 K 个哈希，将对应位设为 1
- 查询：检查 K 个位是否全为 1 → 全为 1 则"可能存在"，有 0 则"一定不存在"
- **不存在误判（False Negative）**，只存在**假阳性误判（False Positive）**
- 100 亿 URL，误判率 1%，需要约 11.5GB 内存（相比 HashSet 的 TB 级别节省 100 倍）

**HyperLogLog**：
- 基数估计算法，12KB 内存可估计 2^64 个不同元素
- 误差率 0.81%
- 适合 UV 统计等只需要去重计数的场景

**Bitmap / RoaringBitmap**：
- 每个 bit 代表一个元素是否存在，1 亿个元素只需 12MB
- 适合 ID 去重（用户 ID、订单 ID 等连续整数型数据）
- RoaringBitmap 用压缩位图，稀疏数据时内存更省

**组合方案（实际生产）**：
```
查询流程:
请求 -> Bloom Filter 判重 -> 可能重复? 
                              │
                    ┌─────────┴─────────┐
                    │                   │
               一定不存在            可能存在
                    │                   │
                    ▼                   ▼
              直接处理              查 DB/Redis 确认
                                    │
                              ┌─────┴─────┐
                              │           │
                           确实重复     实际不存在（误判）
                              │           │
                              ▼           ▼
                           拒绝/跳过    处理 + 更新 BF
```

**分布式布隆过滤器**：
- Redis 原生支持 BF（RedisBloom 模块）：`BF.ADD`、`BF.EXISTS`
- 自研方案：位数组分片存储在多台 Redis 上，哈希后取模定位到具体 Redis 节点
- 扩容：Counting Bloom Filter（支持删除）或 Scalable Bloom Filter（自动扩容）

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| URL 去重 | 布隆过滤器 (RedisBloom) | 内存极小、QPS 百万级 |
| UV 统计 | HyperLogLog (Redis) | 12KB/百万级基数、误差可接受 |
| 用户 ID 去重 | RoaringBitmap | 压缩率高、支持集合运算 |
| 精确去重 | Redis SET + 过期策略 | 需要 100% 准确的场景 |
| 分布式布隆 | Redis Cluster + RedisBloom | 原生支持、运维简单 |

### 面试追问

**Q1：布隆过滤器支持删除吗？**
> 标准布隆过滤器不支持删除（置 0 会影响其他元素）。解决方案：① Counting Bloom Filter，每个位用计数器替代，删除时减计数；② Cuckoo Filter，天然支持删除且空间效率更高。

**Q2：布隆过滤器的误判率怎么控制？**
> 误判率公式：`p ≈ (1 - e^(-kn/m))^k`，其中 m 是位数组大小，k 是哈希函数数量，n 是元素数量。增加位数组大小或哈希函数数量可降低误判率。100 亿 URL、1% 误判率需要 m ≈ 11.5GB、k ≈ 7。

**Q3：HyperLogLog 为什么能用 12KB 估计 2^64 个元素？**
> HLL 将元素哈希后观察前导零的个数，用统计学方法（调和平均数）估计基数。12KB 分成 16384 个桶（register），每个桶 6 bit，能存储最大前导零值。桶越多精度越高。

**Q4：如何处理布隆过滤器的容量预估错误？**
> Scalable Bloom Filter：当误判率超过阈值时，自动创建一个新的 BF 层。查询时检查所有层。多层 BF 会增加查询延迟（查多层），但避免了重建的开销。

**Q5：实时场景中布隆过滤器初始化慢怎么办？**
> 预热策略：启动时从持久化的 BF 文件加载（内存映射 mmap 加速）。增量预热：启动后先放行请求（允许少量误判），后台异步加载历史数据到 BF。

### 踩坑点

- **布隆过滤器误判率随数据量增长**：容量预估不足时误判率急剧上升。需要预留 30% 容量缓冲
- **HyperLogLog 合并问题**：多个 HLL 合并需要相同精度配置（桶数一致），否则结果不准
- **Bitmap 内存浪费**：用户 ID 稀疏时（如 ID 跨度 10 亿但只有 100 万用户），Bitmap 浪费内存。改用 RoaringBitmap
- **分布式 BF 一致性**：多个节点的 BF 状态不完全一致，查询可能返回不同结果。最终一致性可接受，定期从数据源重建 BF

## 13. 多租户系统

### 场景描述

设计一个 SaaS 多租户系统，支持 1000+ 租户，每个租户有独立的用户、数据和配置。要求数据严格隔离、租户级别的限流和资源配额、支持按租户计费。单租户最大 10 万用户，总用户 5000 万。

### 核心挑战

1. **数据隔离**：如何保证租户间数据绝对隔离
2. **租户路由**：请求如何快速路由到正确的租户上下文
3. **限流隔离**：大租户不能影响小租户（防止"吵闹邻居"）
4. **资源配额**：不同付费等级的租户有不同的资源上限

### 设计方案

```
三种隔离方案对比:
┌──────────────────────────────────────────────────────────┐
│  方案          │ 隔离程度 │ 成本  │ 适用场景             │
│  独立数据库     │ 最高     │ 最高  │ 金融/医疗等高安全     │
│  共享库独立Schema│ 高      │ 中高  │ 中大型租户           │
│  共享库共享表   │ 中      │ 最低  │ 小型租户/海量租户     │
└──────────────────────────────────────────────────────────┘

混合方案（推荐）:
┌──────────┐    ┌──────────┐    ┌──────────────┐
│ 大型租户  │    │ 中型租户  │    │  小型租户     │
│ 独立库    │    │ 独立Schema│    │  共享表       │
└──────────┘    └──────────┘    │  tenant_id   │
                                └──────────────┘
```

**租户路由**：
```
请求流程:
Client -> Gateway -> TenantResolver -> 数据源路由 -> Service -> DAO

TenantResolver:
1. 从请求头/Header 中提取 tenantId（或从 token 解析）
2. 查缓存获取租户配置（数据源、Schema、配额）
3. 设置 ThreadLocal 中的 TenantContext
4. 数据源路由根据 TenantContext 切换数据源/Schema

数据源路由 (AbstractRoutingDataSource):
public class TenantDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TenantContext.getTenantId();  // ThreadLocal
    }
}
```

**数据隔离（共享表方案）**：
- 所有业务表增加 `tenant_id` 字段
- MyBatis 拦截器自动追加 `WHERE tenant_id = ?` 条件
- 唯一索引包含 `tenant_id`：`UNIQUE(tenant_id, user_id, email)`
- 所有写操作自动填充 `tenant_id`

**租户限流隔离**：
- 每个租户有独立的限流配额（如免费版 100 QPS，企业版 10000 QPS）
- 限流 key = `rate_limit:{tenant_id}`
- Redis 令牌桶算法实现分布式限流
- 超限时返回 HTTP 429，不阻塞其他租户

**租户配置管理**：
- 租户级别配置存储在 `tenant_config` 表（key-value 结构）
- 热点配置缓存在 Redis，变更时推送更新
- 功能开关通过配置控制（如"租户 A 启用 AI 功能"）

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 数据源路由 | Spring AbstractRoutingDataSource | 透明切换、MyBatis 兼容 |
| SQL 拦截 | MyBatis Interceptor | 自动追加 tenant_id 条件 |
| 租户限流 | Redis 令牌桶 | 分布式环境统一限流 |
| 配置管理 | Apollo / Nacos | 多环境、热更新、灰度发布 |
| 租户缓存 | Redis + Caffeine | 租户配置多级缓存 |

### 面试追问

**Q1：如何防止 SQL 注入绕过 tenant_id？**
> tenant_id 从 Token 解析而非请求参数传入。MyBatis 拦截器在 PreparedStatement 层面追加参数，不拼接 SQL 字符串。数据库层面也可以用 RLS（行级安全策略，PostgreSQL 原生支持）做兜底。

**Q2：租户数据量差异很大，如何避免大租户拖慢共享查询？**
> ① 按租户做分库，大租户独立库；② 共享表场景下按 `tenant_id` 做分区（Partition），查询自动命中分区；③ 查询超时控制，单租户查询超过 N 秒自动中断。

**Q3：租户要求数据迁移怎么办？**
> 从共享库迁移到独立库：① 停止该租户写入（维护窗口）；② 按 `tenant_id` 导出数据；③ 导入到新库；④ 更新租户路由配置；⑤ 恢复写入。在线迁移：双写 + 数据校验 + 切读。

**Q4：如何实现租户级别的计费？**
> 计费事件（API 调用次数、存储用量、活跃用户数）通过 Kafka 事件流收集，Flink 实时聚合到计费系统。不同维度的用量分别统计，月末出账。

**Q5：多租户系统的测试怎么做？**
> ① 隔离测试：确保租户 A 不能访问租户 B 的数据（安全测试用例）；② 性能测试：模拟多租户并发场景，验证限流和资源隔离；③ 数据工厂：每个测试用例使用独立的测试租户，tearDown 后清理数据。

### 踩坑点

- **ThreadLocal 泄漏**：TenantContext 用 ThreadLocal 存储，请求结束后必须清除（Filter 的 finally 中），否则线程池复用时租户上下文串了
- **定时任务的租户上下文**：定时任务不在 HTTP 请求上下文中，需要手动遍历所有租户设置 TenantContext
- **数据库连接池隔离**：共享数据源时，一个慢查询租户可能耗尽连接池。需要按租户配额限制并发连接数
- **Schema 迁移复杂度**：独立 Schema 方案下，DDL 变更需要对每个租户 Schema 执行，迁移工具要支持批量 Schema 变更

## 14. 灰度发布系统

### 场景描述

设计一个灰度发布（金丝雀发布）系统，支持按用户 ID、地区、设备类型、百分比等维度进行流量分组，逐步放量。要求：规则实时生效、支持一键回滚、A/B 测试数据采集、对业务代码侵入最小。

### 核心挑战

1. **流量染色**：如何根据规则将请求标记为不同分组
2. **规则引擎**：灵活的灰度规则配置和实时生效
3. **A/B 测试**：如何采集和分析不同分组的效果数据
4. **回滚机制**：发现问题时如何秒级回滚

### 设计方案

```
灰度流量路由:
┌────────┐   ┌──────────┐   ┌──────────────┐   ┌──────────────┐
│ Request │──>│  Gateway  │──>│ 灰度路由决策  │──>│  目标服务     │
│         │   │ (染色)    │   │ (规则引擎)    │   │  (V1 稳定版)  │
└────────┘   └──────────┘   └──────┬───────┘   └──────────────┘
                                   │
                                   ▼
                            ┌──────────────┐
                            │  目标服务     │
                            │  (V2 灰度版)  │
                            └──────────────┘

灰度规则示例:
{
  "service": "order-service",
  "rules": [
    { "type": "userId", "values": ["10001", "10002"], "version": "v2" },
    { "type": "percentage", "value": 5, "version": "v2" },
    { "type": "region", "values": ["华北"], "version": "v2" }
  ],
  "default": "v1"
}
```

**流量染色**：
1. Gateway 从请求中提取特征（userId、IP->地区、User-Agent->设备类型）
2. 根据灰度规则决策目标版本
3. 将决策结果写入请求 Header（如 `X-Gray-Version: v2`）
4. 服务间调用时 Header 透传（OpenFeign / Dubbo Filter 自动传递）

**规则引擎**：
- 灰度规则存储在配置中心（Nacos/Apollo），变更实时推送
- 规则支持组合条件：`userId IN [...] AND region = "华北" AND device = "iOS"`
- 百分比分流用一致性哈希：`hash(userId) % 100 < percentage`，保证同一用户始终命中同一版本
- 规则优先级：精确匹配 > 百分比 > 默认版本

**A/B 测试数据采集**：
- 每个请求记录：`traceId, userId, grayVersion, requestTime, responseTime, statusCode, businessResult`
- 数据写入 Kafka -> Flink 实时聚合 -> ClickHouse 存储
- 对比维度：转化率、错误率、延迟 P99、业务指标（GMV、下单率）

**回滚机制**：
1. **一键回滚**：配置中心推送规则，将灰度流量全部切回稳定版（秒级生效）
2. **自动回滚**：监控灰度分组的错误率/延迟，超阈值自动回滚
3. **熔断回滚**：灰度版本健康检查失败，自动降级到稳定版

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 流量网关 | Spring Cloud Gateway | 灰度 Filter 可插拔、Header 操作方便 |
| 规则配置 | Nacos / Apollo | 实时推送、版本管理、灰度发布 |
| 流量染色 | 自研 Filter + Dubbo Filter | 全链路 Header 透传 |
| A/B 测试 | Flink + ClickHouse | 实时对比分析 |
| 监控回滚 | Prometheus + Alertmanager | 指标异常自动触发回滚 |

### 面试追问

**Q1：如何保证同一用户始终命中同一版本？**
> 一致性哈希：`hash(userId) % 100 < percentage`。userId 相同，hash 结果相同，始终命中同一分组。这比随机分配更稳定，用户体验一致。

**Q2：灰度版本的数据库 Schema 变更怎么办？**
> 先执行兼容性 DDL（只加字段、不删字段），新旧版本共用新 Schema。灰度验证通过后，再清理旧字段。不兼容变更需要双写过渡期：新版本写新字段，旧版本读旧字段，后台数据迁移任务补齐。

**Q3：微服务架构下，一个请求链路经过多个服务，如何保证全链路灰度？**
> Header 透传 + 服务间 Filter。Gateway 设置的 `X-Gray-Version` 在每个服务调用时自动传递（Feign Interceptor / Dubbo Attachment）。每个服务根据 Header 决定调用哪个版本的下游服务。

**Q4：如何做流量回放测试？**
> 线上真实流量录制到 Kafka（影子流量），灰度环境消费影子流量执行，对比新旧版本的输出差异。差异超过阈值则阻断发布。

**Q5：如何避免灰度影响线上性能？**
> 灰度流量控制在 5% 以内时，额外资源消耗可控。灰度版本使用独立的资源池（K8s 独立 Deployment），与稳定版本隔离。资源不足时灰度版本降级，不影响稳定版本。

### 踩坑点

- **缓存穿透**：灰度版本的数据格式变化导致旧缓存无法命中。灰度版本的缓存 key 加版本后缀隔离
- **消息队列兼容**：灰度版本发出的消息格式变化，消费者（旧版本）解析失败。消息体中带版本号，消费者根据版本号路由到不同的反序列化逻辑
- **Header 透传丢失**：异步线程池中 Header 丢失。需要将 Header 信息包装到 `TaskDecorator` 中传递到子线程
- **百分比不准**：小流量时百分比波动大（5% 的 100 个请求可能只有 3-7 个命中灰度）。需要足够的请求量才能保证百分比准确

## 15. 链路追踪系统

### 场景描述

设计一个分布式链路追踪系统（类似 Zipkin/SkyWalking），支持 TraceId 全链路传递、Span 记录、采样策略、异常检测、服务依赖拓扑图。支撑 1000+ 微服务节点，日均 100 亿条 Span。

### 核心挑战

1. **TraceId 传递**：跨进程、跨线程、跨异步组件的上下文传播
2. **采样策略**：全量采集数据量太大，如何智能采样不丢关键信息
3. **异常检测**：如何从海量 Trace 数据中快速发现异常
4. **依赖拓扑**：如何实时构建服务间调用关系图

### 设计方案

```
数据采集:
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ Service A │───>│ Service B │───>│ Service C │    │ Service D │
│ (Span 1)  │    │ (Span 2)  │    │ (Span 3)  │    │ (Span 4)  │
└─────┬────┘    └─────┬────┘    └─────┬────┘    └─────┬────┘
      │               │               │               │
      ▼               ▼               ▼               ▼
┌──────────────────────────────────────────────────────────────┐
│              Agent (Java Agent / SDK)                         │
│  拦截 HTTP/RPC/DB 调用，自动创建 Span，传递 TraceId          │
└──────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────┐
│              Collector (采集服务)                              │
│  接收 Span 数据 -> 采样过滤 -> 批量写入存储                     │
└──────────────────────────────────────────────────────────────┘
                              │
                    ┌─────────┼─────────┐
                    ▼         ▼         ▼
              ┌──────────┐ ┌────────┐ ┌──────────────┐
              │ ES (Span) │ │ ClickH │ │ 依赖拓扑图    │
              │ 全文检索   │ │ (聚合) │ │ (Neo4j/ES)   │
              └──────────┘ └────────┘ └──────────────┘
```

**TraceId 传递**：
```
TraceId: abc123 (全局唯一，贯穿整个调用链)
SpanId: 1 -> 1.1 -> 1.1.1 (树形结构，标识父子关系)

Service A: TraceId=abc123, SpanId=1
  -> HTTP 调用 B: Header 透传 (traceId=abc123, spanId=1.1, parentSpanId=1)
    -> RPC 调用 C: Header 透传 (traceId=abc123, spanId=1.1.1, parentSpanId=1.1)

传递方式:
- HTTP: 请求 Header (X-Trace-Id, X-Span-Id)
- RPC (Dubbo/gRPC): Attachment / Metadata
- 消息队列: 消息 Properties
- 异步线程: ThreadLocal + TaskDecorator
```

**Java Agent 无侵入接入**：
- 通过 Java Instrumentation API（`-javaagent:trace-agent.jar`）
- 字节码增强（ByteBuddy/Javassist）拦截关键方法：
  - Servlet Filter → 记录 HTTP 入口
  - HttpClient/OkHttp → 记录 HTTP 出口
  - JDBC → 记录 SQL 执行
  - Redis/MQ 客户端 → 记录中间件调用
- 业务代码零修改

**采样策略**：
1. **全量采样**：开发/测试环境，100% 采集
2. **固定比例采样**：线上按 1%-10% 采样
3. **自适应采样**：根据系统负载动态调整（QPS 高时降低采样率）
4. **关键路径采样**：错误请求 100% 采集 + 慢请求（>1s）100% 采集 + 正常请求 1% 采样
5. **尾部采样（Tail-based）**：先收集完整 Trace，再决定是否保留。保留：异常、慢、涉及关键服务的 Trace

**异常检测**：
- 实时监控错误率（5 分钟滑动窗口），超过阈值告警
- 调用延迟 P99 突增检测（同比/环比）
- 服务依赖链异常模式识别（如 A->B 调用失败率突增）

**服务依赖拓扑**：
```
构建方式:
- 每个 Span 包含 callerService 和 calleeService
- Flink 实时聚合 (caller, callee) 对 -> 计算 QPS、延迟、错误率
- 写入图数据库（Neo4j）或 ES（邻接表）
- 前端可视化（D3.js / G6 拓扑图）
```

### 关键技术选型

| 技术点 | 选型 | 理由 |
|--------|------|------|
| 数据采集 | SkyWalking Java Agent | 无侵入、自动注入、社区活跃 |
| TraceId 生成 | TraceId: Snowflake; SpanId: 雪花+序号 | 全局唯一、趋势递增 |
| Span 存储 | Elasticsearch | 全文检索 TraceId、时间范围查询 |
| 聚合分析 | ClickHouse | 列式存储、聚合查询极快 |
| 依赖拓扑 | Neo4j / ES 嵌套文档 | 图查询天然适合拓扑分析 |
| 告警 | Prometheus + Alertmanager | 指标告警成熟方案 |

### 面试追问

**Q1：全链路 TraceId 在异步场景下如何传递？**
> ① 线程池提交任务时，用装饰器包装 Runnable/Callable，从父线程 ThreadLocal 中拷贝 TraceId 到子线程；② 消息队列生产者将 TraceId 写入消息 Header，消费者从 Header 恢复；③ 响应式编程（Reactor/WebFlux）用 Context 传递。

**Q2：尾部采样（Tail-based Sampling）如何实现？**
> Agent 先将完整 Trace 的所有 Span 发送到 Collector 缓冲区。Collector 等待 Trace 完成（超时 30 秒）后，根据策略判断是否保留。挑战：同一个 Trace 的不同 Span 可能发到不同 Collector 节点，需要按 TraceId 一致性路由（如 Kafka 按 TraceId 分区）。

**Q3：如何从海量 Trace 中快速定位问题？**
> ① 索引优化：ES 按天分索引，保留最近 7 天；② 关联查询：先从告警系统获取异常时间点 -> 查该时间段的错误 Trace -> 展示调用链路 -> 定位具体出错的 Span（服务、接口、SQL）。

**Q4：Java Agent 增强的性能开销有多大？**
> 正常情况下 < 5%。开销主要在：① 字节码增强一次性加载（启动时）；② 拦截方法的额外逻辑（创建 Span、设置 Tag、序列化发送）。采样后实际写入的 Span 更少，开销进一步降低。

**Q5：如何处理 Trace 数据的存储成本？**
> ① 采样减少数据量；② ES 索引生命周期管理（ILM）：热数据 SSD 7 天 -> 温数据 HDD 30 天 -> 冷数据归档到 S3；③ 数据压缩：Span 用 Protobuf 编码而非 JSON；④ 仅存储关键字段，原始日志走日志平台不重复存储。

### 踩坑点

- **TraceId 污染**：异步回调中 TraceId 未正确清理，导致无关请求关联到同一个 Trace。每次请求结束必须清理 ThreadLocal
- **采样偏差**：固定比例采样可能丢失低频但重要的调用链。关键路径采样（错误+慢 100%）+ 正常路径采样（1%）的组合策略更优
- **Collector 单点瓶颈**：所有 Agent 都向 Collector 发送数据，高并发下 Collector 可能过载。解决方案：Agent 端批量发送（攒 100 条或 5 秒发一次）+ Collector 集群水平扩展
- **时钟偏移**：分布式节点时钟不一致导致 Trace 的 Span 时间线错乱。Collector 接收时根据服务端时间做校准，展示时标注"可能存在 N ms 误差"
- **采样率过高导致存储爆炸**：10 亿条 Span 每天，每条 1KB，一天就是 1TB。必须严格控制采样率 + 生命周期管理
